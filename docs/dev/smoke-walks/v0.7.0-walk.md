### 1. ENH-144 — Close-tab focus shifts to the LEFT-neighbor file tab

**What changed.** Before: closing a working-pane file tab (markdown editor, canvas, image viewer) bounced focus to the browser tab, which was disorienting if you were editing several files in a row. Now: focus shifts to the file tab to the LEFT of the one you closed. If the closed tab was leftmost, focus shifts to the new leftmost. Browser stays out of it.

**Why it matters.** Restores tab-shift focus behavior that matches every modern editor (VS Code, Sublime, etc.).

**Repro:**
1. Open three markdown files in separate working-pane tabs: `duo edit /tmp/walk-a.md && duo edit /tmp/walk-b.md && duo edit /tmp/walk-c.md`.
2. Confirm the working-pane strip shows tabs A, B, C in that order.
3. Click tab B (or use ⌘2 / similar shortcut to activate B).
4. Hit ⌘W to close tab B.

**Expected pass.** Tab A becomes active. The browser tab does NOT receive focus.

**Failure mode.** Browser tab becomes active (the old buggy behavior), OR tab C activates (off-by-one bug).

### 6. ENH-156 — HTML verb-split: `duo open` → browser, `duo edit` → canvas

This one's **already on main** (shipped today as commit `7a34e7e` — not in a PR). Walk-anytime.

**What changed.** Before: `duo open <some.html>` and `duo edit <some.html>` BOTH consulted the file's `<meta name="duo-open-in">` declaration to decide the surface, and treated each verb identically for HTML. Now: **the verb itself decides the surface, NOT the file's meta declaration.**
- `duo open <html>` → browser pane (scripts run, buttons fire, interactive — for "show me the thing").
- `duo edit <html>` → canvas mode (source-editable, scripts blocked, buttons inert — for "modify the source").
- The legacy `<meta name="duo-open-in" content="browser">` declaration is **no longer consulted**. Old files with that declaration are harmless (the new default lands them in browser anyway).
- Rare overrides: `duo open --canvas <html>` forces canvas; `duo edit --browser <html>` forces browser.

**Why it matters.** Closes the meta-discipline footgun: agents kept forgetting to add the meta declaration when generating playgrounds, then the playground would open in canvas mode and the user couldn't interact with the buttons.

**Repro:**

   **(6a) `duo open` defaults to browser pane for HTML with NO meta declaration.**
   1. Seed a fixture: `printf '<!DOCTYPE html><html><body><h1>Hello</h1><button id="b" onclick="this.textContent=\"clicked\"">Click me</button></body></html>' > /tmp/walk-verb-open.html`
   2. Run: `duo open /tmp/walk-verb-open.html`
   3. **Expected:** The file lands in Duo's **browser pane** (the right-side WebContentsView, NOT the canvas tab). You can click the button and the text updates to "clicked". Verify via `duo layout`: `main.kind` should be `'browser'`, `main.url` should start with `file:///tmp/walk-verb-open.html`.
   4. **Failure mode:** The file lands in canvas mode (the inert source-editable surface). The button doesn't respond to clicks.

   **(6b) `duo edit` defaults to canvas mode for the same HTML.**
   1. Same fixture. Run: `duo edit /tmp/walk-verb-open.html`
   2. **Expected:** The file lands in **canvas mode** (a tab in the working-pane). Click the button → cursor places into the button text (canvas is contentEditable); no JS fires. Verify via `duo layout`: `main.kind` should be `'page'`, `main.path` should be `/tmp/walk-verb-open.html`.
   3. **Failure mode:** Edit verb lands the file in the browser pane (which would be the override behavior, not the default).

   **(6c) Existing files with the OLD meta declaration still work.**
   1. Pick any playground in `docs/research/` — they all have `<meta name="duo-open-in" content="browser">`. E.g. `duo open docs/research/link-folder-to-repo.html`.
   2. **Expected:** Lands in browser pane (since `duo open` defaults to browser). The meta declaration is no longer consulted but the new default produces the same outcome. No regression.

   **(6d) Navigator double-click on `.html` → browser pane.**
   1. Find any `.html` file in the navigator tree. Double-click it.
   2. **Expected:** Browser pane. (CLI/UI parity per CLAUDE.md § 4.)

   **(6e) `--canvas` override on `duo open`.**
   1. Run: `duo open /tmp/walk-verb-open.html --canvas`
   2. **Expected:** Canvas mode (override forces it). Useful when you want to inspect the source without firing scripts.

**Common failure mode across all sub-tests.** If `duo open <html>` still lands in canvas mode, the verb-split didn't ship — old build still running. Relaunch Duo.

### 7. BUG-125 — Watcher reload propagates to symlinked paths (gated on PR #49 merge)

**What changed.** Before: when you edited a markdown file or HTML canvas in Duo and another agent (Claude Code in another terminal) wrote to that same file via filesystem `Write`, the canvas/editor **silently stayed stale** if the file's path was a symlink. The bug: chokidar (the file-watcher library) emits events with the symlink-RESOLVED path (so `/tmp/foo.md` arrives as `/private/tmp/foo.md` on macOS, since `/tmp` is a symlink to `/private/tmp`). The renderer's `event.path !== path` guard dropped these events as if they were for a different file.

Now: `electron/files-service.ts` maintains a `Map<resolvedPath, originalCallerPath>` per watcher and remaps event paths back to the caller's input before dispatch. Transparent to all four watcher callers (PageTab + MarkdownEditor + 2 navigator hooks).

**Why it matters.** Was a load-bearing assumption: the FOLLOWUP-019 three-layer reconciliation (watcher → silent reload or conflict banner) was the v0.6.15 close-out story for editor-canvas parity. With the symlink bug, that reconciliation NEVER FIRED for `/tmp/` paths — which is exactly where smoke-walk fixtures live, so we never caught it during walks. Real owner repro brought it down: "Claude updates canvases (md, html) in the file system, and the canvas view does not pick up the change."

**Repro — 4 sub-tests covering the relevant combinations:**

   **(7a) Clean canvas reload via symlinked path (the core bug).**
   1. Seed: `printf '<!DOCTYPE html><html><body><p>before</p></body></html>' > /tmp/bug125-walk.html`
   2. Open in canvas mode: `duo edit /tmp/bug125-walk.html` (under ENH-156 default this lands in canvas).
   3. Confirm the canvas shows "before" — don't click into it (keep buffer clean).
   4. From a **regular Terminal.app shell** (NOT a Duo terminal — we want to ensure the write doesn't echo through Duo's own CLI which has different paths): `printf '<!DOCTYPE html><html><body><p>after</p></body></html>' > /tmp/bug125-walk.html`
   5. **Expected (within ~500ms):** Canvas auto-reloads silently to show "after". NO conflict banner appears (buffer was clean — no merge needed).
   6. **Failure mode:** Canvas stays showing "before" indefinitely until you click another tab and come back. That's the bug.

   **(7b) Dirty canvas → conflict banner via symlinked path.**
   1. Same `/tmp/bug125-walk.html` from (7a). Click into the canvas and type a character to make it dirty (you'll see a `●` indicator in the tab title).
   2. From regular Terminal: `printf '<!DOCTYPE html><html><body><p>external</p></body></html>' > /tmp/bug125-walk.html`
   3. **Expected:** An amber conflict banner appears at the top of the canvas, with "Reload" and "Keep mine" buttons.
   4. Click **Reload** → canvas shows "external" + banner clears.
   5. **Failure mode:** No banner appears — your edits silently saved over the external write (data loss).

   **(7c) Markdown editor parity via symlinked path.**
   1. Seed: `printf '# before\n' > /tmp/bug125-walk.md`
   2. Open in markdown editor: `duo edit /tmp/bug125-walk.md`
   3. From regular Terminal: `printf '# after\n' > /tmp/bug125-walk.md`
   4. **Expected:** TipTap editor reloads silently to show "after". Editor-canvas parity confirmed.

   **(7d) Non-symlinked path regression check.**
   1. Repeat (7a) with a path in your project: `printf '<!DOCTYPE html><html><body><p>before</p></body></html>' > ~/Documents/bug125-walk.html`
   2. `duo edit ~/Documents/bug125-walk.html`
   3. External `printf '<!DOCTYPE html><html><body><p>after</p></body></html>' > ~/Documents/bug125-walk.html`
   4. **Expected:** Canvas reloads (would have worked before the fix too — this is the regression check).

**Bonus check — managed-block visible version footer.** Open `~/.claude/CLAUDE.md`. Find the `## Duo workspace integration` block. There should be a new italic footer line: `*Auto-managed by Duo v0.7.0. Re-runs on every Duo install/upgrade; the version above is the source of truth for whether the latest block landed.*` Confirms the latest install ran.

### 8. ENH-158 — Boot-time self-healing CLI shim (gated on PR #52 merge)

**What changed.** Before: `~/.claude/duo/bin/duo` was supposed to be a symlink that Duo's `PtyManager` prepends to every Duo PTY's `$PATH`, so `duo` works in every Duo terminal without shell-rc tweaks. But the symlink creation was `console.warn`-only on failure (silent everywhere a user could see it), AND it only fired on FirstLaunchBanner click — so users who upgraded across Duo versions had the symlink rot without anyone noticing. An enterprise user on v0.6.15 hit `duo: command not found` with FOUR overlapping vestigial install artifacts; the diagnosing agent compounded the problem by misreading "command not found" as a sandbox block.

Now: every app boot calls `installService.ensureCliShim()` which checks the symlink's state (missing / current / stale / broken / non-symlink-file), creates or replaces it as needed, and logs all activity to `~/.claude/duo/logs/install-shim.log`. The symlink target is the in-app CLI binary (`Duo.app/Contents/Resources/cli/duo`) — auto-updates carry the CLI forward automatically.

**Why it matters.** Closes a load-bearing silent-failure surface. After ENH-158, the invariant *"`~/.claude/duo/bin/duo` points at the current Duo's CLI"* is true on every launch regardless of upgrade path or prior install state. Skill+agent recovery-path docs collapse from a three-target try-each list to a single canonical path that's guaranteed to exist post-boot.

**Repro:**

   **(8a) Symlink exists post-boot.**
   1. After Duo launches: `ls -l ~/.claude/duo/bin/duo`
   2. **Expected:** Outputs a symlink (the `l` flag at the start of the permissions string) pointing at something like `/Applications/Duo.app/Contents/Resources/cli/duo` (prod) OR `<dev-path>/cli/duo` (dev).

   **(8b) The shim works.**
   1. From a regular Terminal.app shell (NOT a Duo terminal): `~/.claude/duo/bin/duo doctor`
   2. **Expected:** Outputs the doctor report (transport status, version match, etc.). Confirms the symlink resolves to a working binary.

   **(8c) Boot logs are present.**
   1. `cat ~/.claude/duo/logs/install-shim.log`
   2. **Expected:** Has a recent timestamped line, OR is empty if every boot was a no-op (the symlink stayed current). Either is fine — non-empty just means the shim ran a create/replace.

   **(8d) Idempotency (relaunch is a no-op).**
   1. Quit Duo (⌘Q).
   2. Relaunch Duo from `/Applications/Duo.app` (or `npm run dev` if you're on a dev build).
   3. `tail -2 ~/.claude/duo/logs/install-shim.log` (if it exists)
   4. **Expected:** Either no new line (no-op case) OR a single line per relaunch (not multiple — multiple would indicate retries).

   **(8e) Self-heal after manual breakage.**
   1. Delete the shim: `rm ~/.claude/duo/bin/duo`
   2. Quit + relaunch Duo.
   3. `ls -l ~/.claude/duo/bin/duo`
   4. **Expected:** The symlink is back. (Self-heal worked.)

**Failure mode across sub-tests.** Shim doesn't exist post-boot → boot hook didn't fire; check Duo's main-process console for `[main] ensureCliShim` lines. Shim exists but is a regular file (not a symlink) → the boot-time heal refused to overwrite a non-symlink (look for `refused` action in the log).

### 9. ENH-159 — Browser send-to-Claude carries DOM context + inspect mode (gated on PR #51 merge)

**What changed.** Before: when you selected text in Duo's browser pane and clicked "Send → Duo" (or hit ⌘D), only the literal selected text and the page URL+title made it to your Claude terminal. The agent knew "the user sent something from page X" but had zero structural context — which heading the text was under, which element it came from, etc. Now: the paste carries:
- The quoted selected text (unchanged).
- `> @ <css-selector>` — a precise CSS path to the selected element.
- A fenced `context` block with the enclosing-block surrounding text (capped at 1000 chars).

Plus a brand-new **inspect mode** that lets you click-pick a specific element to send:
- `duo inspect` (or `⌘⇧C` inside the browser pane) toggles inspect mode on.
- Hover any DOM element — a 2px orange outline + size tooltip render.
- Click — captures `{ tag, selectorPath, headingTrail, innerText (capped 2000 chars), key attrs }` and ships it to the active terminal as a structured paste.
- ESC exits.

**Security note.** DOM-derived strings are adversary-controlled (a hostile page could craft them to break out of the paste). Three regression tests pin the sanitization invariants: CR/LF/U+2028/U+2029 strip + dynamic fence length so a 4-backtick run in page content can't close the fence early. (You don't need to test these manually — they're in `sendFormat.test.ts`. Just noting.)

**Why it matters.** "I picked text from this page" + structural context lets Claude reason about what you're pointing at — "the third paragraph under the 'API' heading", "the button labeled Submit inside the login form". Inspect mode covers the case where the addressable unit is an element, not a text range (e.g. an image, a button with no visible text outside it).

**Repro:**

   **(9a) Select-and-send carries DOM context.**
   1. `duo open https://en.wikipedia.org/wiki/Bridge_(graph_theory)` (or any page with structured headings).
   2. Click into a paragraph anywhere in the body. Select a few sentences of text.
   3. Click the "Send → Duo" pill that appears, OR hit ⌘D.
   4. Switch to the Duo terminal that received the paste.

   **Expected pass.** The terminal shows:
   ```
   > <your selected text, one line per ">"-prefix>
   > (https://en.wikipedia.org/wiki/Bridge_(graph_theory) — "Bridge (graph theory) - Wikipedia")
   > @ <some-css-selector>     ← NEW: the selector path
   
   ````context                  ← NEW: fenced block
   <the enclosing paragraph or nearest block's text>
   ````
   ```
   - The `> @` line gives the CSS selector to the element you selected from.
   - The fenced `context` block carries the SURROUNDING text (the enclosing block).

   **Failure mode.** No `> @` line and no `````context` block — pre-ENH-159 behavior, signal stripped.

   **(9b) Inspect mode toggle via CLI.**
   1. `duo inspect` — should toggle ON. (Run `duo inspect --off` to explicitly turn off.)
   2. Move mouse over different elements in the browser pane.
   3. **Expected:** Each element under the cursor gets a 2px orange outline + small tooltip showing the tag + width × height pixels.
   4. Click a specific element (e.g. a heading or image).
   5. **Expected:** The structured paste lands in the terminal:
      ```
      > <inspect> h2#some-id  @ <url> — "<page title>"
      > section: <heading trail like "Section A > Subsection B">
      > selector: <full CSS path>
      > attrs: id=..., role=..., aria-label=..., href=...     (excluding id which is on the headline)
      
      ````text
      <innerText, capped at 2000 chars>
      ````
      ```
   6. ESC inside the browser pane.
   7. **Expected:** Inspect mode exits cleanly (no outline on subsequent hovers). `duo inspect` query returns `{ active: false }`.

   **Failure mode.** No outline on hover, OR clicking the element does nothing, OR ESC doesn't exit.

   **(9c) Inspect mode keyboard shortcut.**
   1. Focus the browser pane (click into the WCV).
   2. Press `⌘⇧C`.
   3. **Expected:** Same behavior as `duo inspect` — toggles inspect mode on. (Chord parity.)

   **(9d) Selection observer is paused during inspect mode.**
   1. Turn inspect mode ON.
   2. Try to select text in the browser pane.
   3. **Expected:** No "Send → Duo" pill appears (mode lock). Selection still happens visually but no pill.

**Common failure mode.** `duo inspect` returns "Unknown command" → PR #51 not merged yet, OR CLI binary stale (run `npm run build:cli && git diff cli/duo`).

- "abc1234 · modified" — detached HEAD with the short SHA.

**Owner directive: clean stays invisible.** Non-repo folders show no chip. Clean repos with no upstream divergence show no chip. The chip only appears when there's signal.

Hover the chip for a tooltip with branch name + work-tree root + change count + ahead/behind detail.

### 12. ENH-151 — `duo clone` CLI verbs ✨ NEW

**What changed.** Three new CLI verbs for cloning GitHub repos:

Structured CloneResult with `errorKind` in `{ bad-url, auth-missing, clone-failed }` for agent branching.
- `duo gh-auth` — probes `gh auth status`; returns `{ ghInstalled, authenticated, host, user, ghNotFound }`.
- `duo git-status [<path>]` — shared with ENH-152a's chip; full snapshot.

**Why it matters.** Agents can now clone repos as part of their flows. Before: agent had to fall through to `Bash` running `git clone` directly, with no auth-state knowledge.

**Repro:**

   2. **Expected:** JSON. If you've run `gh auth login`: `{ ghInstalled: true, authenticated: true, host: 'github.com', user: '<your-username>', ghNotFound: false }`. If not: `{ ghInstalled: true|false, authenticated: false, ... }`.

### 14. FOLLOWUP-020 — `duo close-tab` + `duo close-terminal-tab` CLI ✨ NEW

**What changed.** Two new CLI verbs closing the parity-rule gap surfaced during ENH-143's ⌘W discoverability work. Before: `duo close <n>` only closed BROWSER tabs by id (from `duo tabs`). No CLI counterpart for closing the focused working-pane tab or a terminal tab. Now:
- `duo close-tab` — closes the focused working-pane tab (file editor / canvas / image viewer / browser-mode HTML / etc.).
- `duo close-terminal-tab [<n>]` — closes the focused terminal tab; `<n>` (1-indexed) closes that specific terminal tab.

Pinned-tab gating works identically to the ⌘W chord: a CLI close of a pinned tab still surfaces the "Cancel / Close anyway" `dialog.confirm`.

**Why it matters.** Agents can now write "open + edit + close" workflow scripts without leaving stale tabs accumulating. Closes the CLAUDE.md § 4 parity-rule violation.

**Repro:**

   **(14a) Close the focused working-pane tab.**
   1. Open three working-pane tabs in succession: `duo edit /tmp/walk-c1.md && duo edit /tmp/walk-c2.md && duo edit /tmp/walk-c3.md`
   2. Confirm walk-c3.md is the focused tab.
   3. `duo close-tab`
   4. **Expected:** walk-c3.md closes. Focus shifts to walk-c2.md (left-neighbor, per ENH-144).
   5. Repeat: `duo close-tab` → walk-c2 closes, walk-c1 activates. `duo close-tab` → walk-c1 closes.

   **(14b) Pinned-tab close requires confirm.**
   1. Open a file: `duo edit /tmp/walk-pinned.md`
   2. Right-click the tab → "Pin tab" (or use the equivalent menu).
   3. `duo close-tab`
   4. **Expected:** A confirm dialog appears: "Close pinned tab \"walk-pinned\"? This tab is pinned. Closing it removes the pin and the tab." With "Cancel" / "Close tab" buttons. Click "Close tab" to confirm.

   **(14c) Close the focused terminal tab.**
   1. (Need ≥2 terminal tabs.) ⌘⇧T or ⌘T (or however you open a new terminal — there are several ways).
   2. Switch to the 2nd terminal tab.
   3. `duo close-terminal-tab`
   4. **Expected:** That terminal tab closes. Focus shifts to another terminal tab.

   **(14d) Close the Nth terminal tab by index.**
   1. Open at least 3 terminal tabs.
   2. `duo close-terminal-tab 1`
   3. **Expected:** The 1st terminal tab closes (1-indexed).

   **(14e) Bad index errors cleanly.**
   1. `duo close-terminal-tab 999`
   2. **Expected:** Silently no-op (no crash). Or potentially an error if the index validation kicks in.

   **(14f) Bad arg shape errors loudly.**
   1. `duo close-terminal-tab not-a-number`
   2. **Expected:** "Usage: duo close-terminal-tab [<n>]   (n is 1-indexed)" — clean usage error.

**Failure modes.** `duo close-tab: Unknown command` → CLI binary stale. Close-tab CLI doesn't close anything → IPC subscriber wiring issue in App.tsx. Pinned-tab close skips the confirm → pinned-state lookup missed.

### 15. BUG-124 — `~/.claude/duo/logs/` mkdir-p at boot ✨ NEW

**What changed.** Before: the renderer's `writeConflictLog` (used by BUG-122's diagnostic logging for save-conflict banners) tried to write to `~/.claude/duo/logs/last-conflict.log`. The directory didn't exist by default — `~/.claude/duo/` was created by install-service on FirstLaunchBanner click, but `logs/` wasn't included. The dev-stderr flooded with `ENOENT: rename last-conflict.log.duo.tmp → last-conflict.log` errors on every save-conflict repro. Now: a fire-and-forget `fs.mkdir(~/.claude/duo/logs, { recursive: true })` runs from `app.whenReady()` after `createWindow()`.

**Why it matters.** BUG-122's diagnostic logging feature was silently broken (writeConflictLog is wrapped in try/catch so the user saw no banner, but the production-readable log was never written). Now repros of BUG-122 + similar conflict banners capture diagnostic data the owner can paste back.

**Repro:**

   **(15a) Logs dir exists.**
   1. After Duo launches: `ls -d ~/.claude/duo/logs/`
   2. **Expected:** Directory exists.

   **(15b) Dev-stderr no longer floods on conflict.**
   1. Trigger a save-conflict (e.g. open a markdown file, dirty it, externally `Write` to the same file via Claude Code's tools).
   2. Watch the dev console (or the background-process log Duo writes to).
   3. **Expected:** No `ENOENT: rename last-conflict.log.duo.tmp` lines. (If you DO see them, the mkdir didn't run — boot hook failed.) Instead, you should see a `last-conflict.log` file written under `~/.claude/duo/logs/`.

   **(15c) Diagnostic file written on conflict.**
   1. Same trigger as (15b). After the banner appears: `cat ~/.claude/duo/logs/last-conflict.log`
   2. **Expected:** JSON object with timestamp + diagnostic detail (the BUG-122 diagnostic format).

**Failure modes.** Logs dir missing → boot hook failed; check the main-process console for `[main] BUG-124 logs-dir mkdir failed:` warnings.
