## Idea capture (filled in as conversation unfolds)

### Idea 1 — File navigator overhaul ✅ understood

**Geoff's seed (verbatim):** "should now be two sub panes, top and bottom;
top is the `~/.claude/` if it exists, filtered to `CLAUDE.md`, `skills/`,
`agents/`; lower is the old/existing file navigator, but it should pin to
the current CWD; ditch the three-column 'deeper' view, and stick to
collapsing folders"

**The deeper intent (Geoff's expansion):**
> "I want the user level context to be easier to find/manipulate, esp the
> user level claude.md and the user level skills; it may make sense for
> this user level content to be collapsible; and it's worth second
> guessing my filter idea or at least making this toggle-able; for
> product managers that are non technical, distinguishing between user
> and cwd level context will be unintuitive; this will be a reminder
> that claude has access to both buckets of context; that is related to
> the pin-to-cwd intent — I always want it to be obvious to the user
> what context the agent has."

**Resolved understanding:**

The navigator's PRIMARY job becomes **teaching non-technical PMs that
the agent reads from two layers of context (user + project)**. Visual
separation is the pedagogy. Concrete shape:

- **Top pane — "Your Claude settings"** (label, plain English; avoid
  the literal `~/.claude/` path).
  - Default view: **curated three only** — the `CLAUDE.md`, `skills/`,
    `agents/` that PMs actually edit. Toggle to show the rest of
    `~/.claude/` (mcp, hooks, plans, projects, bin, etc.) for power
    users.
  - Collapsible header so the pane can be hidden when not in use.
  - Same interaction model as the lower pane: click-to-open into the
    WorkingPane (editor for `.md`, canvas for `.html`, etc.).
- **Bottom pane — "This project"** (label, plain English).
  - **Pinned to the current CWD.** Doesn't follow agent-driven moves
    away from the project root. (Pinning is itself a pedagogical
    signal: "this is YOUR project, separate from your settings.")
  - **Top-of-pane group: project Claude context** — surfaces
    `./CLAUDE.md`, `./.claude/`, `./tasks.md` etc. when they exist.
    Same visual treatment as the top pane's curated-three.
  - Below that group: the normal project-file tree.
  - **Drop the three-column-deeper view** (Stage 10 D11). Stick to
    inline collapsing folders, both panes.
- **File ops symmetry:** click-to-open everywhere; eventually
  rename/delete/reveal-in-Finder context menu, shared across both
  panes (this comes from the existing `Navigator polish & ergonomics
  pass` backlog item, NOT in scope for the overhaul itself).

**Where it lands in the roadmap:**

This is a substantial enough rethink to warrant its own stage card,
not a sub-item of Stage 10. Provisional: **Stage 22 — Navigator dual-
pane overhaul (context pedagogy)**. Folds-in interaction:
- Existing Stage 10 (file navigator) stays as the foundational stage;
  Stage 22 supersedes its three-column-deeper sub-pattern (D11) and
  the "follow-mode" semantics get re-examined under pin-to-CWD.
- The existing `Navigator polish & ergonomics pass` backlog bundle
  (file ops, double-click, "Go to" path input, hover-claude on
  folders) plays alongside but isn't a prerequisite for Stage 22 —
  the overhaul is the visual reorg, the polish bundle is the
  interaction layer.
- Idea 5 (quick-docs menu) and the help/FAQ backlog item probably
  get a third visual surface (top-bar menu, not nav pane), but
  the labeling pattern Stage 22 establishes ("plain English for
  non-technical PMs") sets a standard the rest of the app should
  inherit.

### Idea 2 — Banner-above-terminal nudge to launch Claude ✅ understood

**Geoff's seed (verbatim):** "Make a new feature if possible which detects
when a terminal session is not in Claude mode and standard sheets a small
banner above it that says launch Claude with duo and which performs the
operations to launch Claude with duo"

**The deeper intent (Geoff's expansion):**
> "I want the easiest path to be opening claude w duo context — I think
> we have other mechanisms for this; but until we have claude hooks, I
> think we need to consider UX hooks to drive behaviors that increase
> the likelihood of users starting claude sessions w any flags we need
> for duo to thrive."

**Honest assessment of overlap with shipped/pending Stage 19 work:**

| Surface | Coverage |
|---|---|
| **Stage 19a (shipped)** | Env signals (`DUO_SESSION`, `DUO_SOCKET`, `DUO_VERSION`, `TERM_PROGRAM=Duo`) auto-set in every Duo PTY. Once claude starts, it sees "I'm in Duo." Doesn't help start claude. |
| **Stage 19c (shipped)** | Split-`+` defaults new tabs to claude; ⌘T = claude; ⌘⇧T = shell; install banner when claude isn't on PATH; last-kind persisted. **New-tab path solved.** |
| **Stage 19b (pending)** | SessionStart hook + PATH shim + priming.md. Agent-side context once claude is running. Doesn't help start claude. |

**Gap that remains:** Non-technical PM sitting in a shell tab. Routes
in: last-kind persistence, Stage 21c session-restored shell, explicit
⌘⇧T or split-`+` right-side. From there, the only paths to claude are
`+` → click claude (2 clicks) or ⌘T (muscle memory). For a technical
user that's fine. For a non-technical PM, a visible banner is
**pedagogy** — same theme as Idea 1.

**Resolved understanding (ship as Stage 19d):**

- **Detection:** `TabSession.kind === 'shell'` (Stage 19c data plane is
  authoritative). No process-watching needed.
- **Banner UX:**
  - Renders above the xterm in shell tabs only.
  - Copy: "Looking for Claude? Click here to start an AI session in
    this tab" (or similar, plain English per Idea 1's labeling
    convention).
  - Dismiss button (×) — per-tab, sticky for that tab only.
  - Settings toggle in app prefs: "Show 'Launch Claude' hint on
    shell tabs" — default on; gives power users a global mute.
- **Click handler:** `pty.write(activeTabId, 'claude\n')` — cheapest
  implementation. Reuses the existing PTY + its DUO_SESSION env.
- **Scope:** ~150 LOC. New `<LaunchClaudeBanner>` primitive (same
  pattern as `<WriteWarningBanner>`); renderer-only feature; no new
  CLI verb (clicking the banner is equivalent to typing `claude`,
  which is already what the user could do).

**Where it lands in the roadmap:**

**Stage 19d — Mid-tab launch-claude banner.** Sub-stage of Stage 19,
slots after 19b (passive priming). Independent of 21 — could ship
sooner if Trailblazer onboarding feedback prioritizes it. Ties into
Idea 1's pedagogy theme: both are "make context visible to
non-technical PMs."

### Idea 3 — Distro skill-pack support (build-time bake-in) ✅ understood

**Geoff's seed (verbatim):** "Add a mechanism where the installation script
could load arbitrary skills to the user level skills folder for example
one of our distro's could have it put the AIP skills into the user folder
on duo installation"

**The deeper intent (Geoff's expansion):**
> "I have built a 'starter pack' of skills that help product managers
> onboard to claude code and configure connectors to our local
> environment; I don't want to force these on non-capital one users of
> duo; but I want a simple path to create a distribution for capital one
> users, where we define/add a folder of these skills, and the duo
> installer, while it is adding the duo agent and skill to ~/.claude/,
> also adds the pack of other skills."

**Resolved understanding (ship as Stage 18b):**

- **Distribution mechanism: convention folder.** `extra-skills/` in
  the repo root, gitignored. Build picks it up if present; vanilla
  Duo source has no folder there → standard .dmg ships unchanged.
  Capital One workflow: clone duo → drop `extra-skills/` folder in
  → `npm run dist` → bundled .dmg includes the pack. No build flags
  to remember.
- **Pack scope (v1): skills + agents.**
  - `extra-skills/skills/<name>/SKILL.md` (+ companion files) → copy
    to `~/.claude/skills/<name>/`.
  - `extra-skills/agents/<name>.md` → copy to `~/.claude/agents/<name>.md`.
  - **NOT in v1:** CLAUDE.md fragments, external-domains.json entries.
    Defer to a later iteration if a distro needs them.
- **Pack manifest:** required `extra-skills/PACK.json` declaring
  pack name (`"aip-pm-starter"`), version, optional display name
  ("AIP — Capital One"), and explicit file list. Build-time
  validation: missing manifest = build fails with a clear error;
  files in the folder not declared in manifest = warning.
- **Conflict policy: ask per-conflict on first install.**
  - Installer compares pack file list against `~/.claude/skills/`
    + `~/.claude/agents/`.
  - If any collide, the consent sheet (Stage 18) lists them with
    radio choices: `[Skip all collisions]` `[Overwrite all]`
    `[Decide each]`. Per-collision UI for the third option.
  - Pre-existing user content is never silently clobbered.
- **Provenance: pack manifest in `~/.claude/duo/installed-packs.json`.**
  - Installer writes `{packs: [{name, version, files: [...]}]}`.
  - Enables future tooling: `duo packs list` CLI verb, "Provided by
    AIP" badge in Idea 1's dual-pane navigator's top pane,
    refresh-on-update logic later.
  - v1 has no UI for this — just the data-plane manifest.
- **Update lifecycle (deferred to v2):** when Duo auto-updates
  (Stage 21c), do bundled skills refresh? Skip on first ship; tackle
  when Stage 21c lands and there's a real update path.

**Where it lands in the roadmap:**

**Stage 18b — Distro skill-pack support.** Sub-stage of Stage 18
(first-launch self-install), since the consent sheet is the natural
host for the per-conflict UI. Specifically:
- 18a: vanilla first-launch installer (already specced; pending).
- 18b: extends the installer's copy step to read `PACK.json` + walk
  `extra-skills/` + handle collisions.
- Cross-refs Idea 1's labeling convention (top-pane navigator should
  surface "Provided by …" labels per the Pack manifest), Idea 5's
  quick-docs (a distro might also want to ship docs — possible 18c
  follow-up).

### Idea 4 — Convention-based actions in canvas HTML (Claude ↔ HTML loop) ✅ understood

**Geoff's seed (verbatim):** "Create convention where a button click
within a duo HTML file could fire an event that triggers an action in
terminal for example could invoke a user on boarding scale or something
like that"

**The deeper intent (Geoff's expansion):**
> "I'm picturing users having html documents that serve roles like
> training aids or even just a personal dashboard; I could imagine a
> button that says, 'check my slack for anything urgent' in a local
> html file… I could imagine claude code operating and live generating
> training content, eg. read this paragraph then click next when you're
> ready to move on; or claude code administering a quiz in the html
> viewer, and the user hitting multiple choice buttons, then claude
> code knowing what the response was and resuming the lesson."

**The architecture insight: no Claude Code hooks needed.**

Two layers, both achievable today:

**Layer 1 — Convention-based one-way actions (no page scripts).**
The canvas iframe is sandboxed without `allow-scripts` (PRD H4/H8). But
the canvas runtime (distinct from page scripts) already injects
listeners — same pattern as `commentAnchors.ts`. Convention:

```html
<button data-duo-action="claude:run"
        data-duo-prompt="check slack for anything urgent">
  Check my Slack
</button>
```

Canvas runtime delegates clicks on `[data-duo-action]` to a dispatcher
keyed on the action name. **No page scripts required. No Stage 17e
dependency.** Buttons render normally; canvas runtime intercepts clicks
before any default behavior.

**Layer 2 — Bidirectional Claude ↔ HTML conversation.**
Combine Layer 1 with a small CLI tweak: add `--enter` flag to `duo
send` (which today writes to active terminal's PTY without Enter per
G11). With `--enter`, button clicks can pipe responses directly into
claude's stdin as user prompts. Claude reads → grades → renders next
content via `duo html set / replace / append` (already shipped in 17b).
Full quiz / lesson / dashboard loop. ~10 LOC for the `--enter` flag.

**Resolved understanding (ship as Stage 23):**

- **Trust model: path-restricted** to `~/.claude/duo/` + user-marked-
  trusted folders. Files under `~/.claude/duo/` (Stage 18b distro
  destination + Idea 5 quick-docs home) auto-trust. Other folders:
  buttons render with a ringed warning state; clicking shows a
  one-time "Trust this folder?" prompt with [Allow once] [Always
  allow this folder] [Never].
- **v1 action vocabulary (3 actions):**
  1. `claude:spawn` — opens a new claude tab with `data-duo-prompt`
     pre-typed (reuses Stage 19c `dispatchNewTab({ kind: 'claude',
     cmd })`).
  2. `terminal:send` — writes `data-duo-text` to the active
     terminal's PTY. Optional `data-duo-enter="true"` appends `\n`
     (this is the new `duo send --enter` semantics).
  3. `browser:open` — routes `data-duo-url` through Stage 8's `duo
     open` (in-app browser pane) or Stage 5 v2's `duo external`
     (system browser, per `external-domains.json`).
- **Stage 23a — Convention runtime + 3 actions.** ~200 LOC.
  Canvas-runtime delegated listener; trust check; dispatcher to
  three handlers. New skill section in `skill/examples/` showing
  the `data-duo-action` convention.
- **Stage 23b — `duo send --enter` flag.** ~10 LOC. CLI parser
  change + pty.write call appends `\n`. Plumbing checklist (CLAUDE.md
  §4) for the new flag.
- **Stage 23c — Worked examples + demo (load-bearing for adoption).**
  The convention is unfamiliar enough that documentation alone
  isn't enough — users need to *see it work*. Two-part shipment:
  - **In the standard Duo source:** bundled reference HTML files
    in `skill/examples/canvas-actions/` — quiz template, lesson-
    with-next-button template, personal dashboard template, "check
    my slack" button. Demonstrates the loop end-to-end so Claude
    knows the pattern when authoring (and so any agent reading
    the skill at session-start can crib from it).
  - **In the Capital One AIP distro (Stage 18b):** a live demo
    page in `extra-skills/quick-docs/welcome.html` (or similar)
    that ships in the distro's `~/.claude/duo/quick-docs/`
    folder — auto-trusted per the path-restricted trust model
    (Stage 23a) and accessible from Idea 5's quick-docs menu.
    First-launch experience for an AIP user includes a working
    "click here to start the onboarding agent" button that
    actually fires Stage 23's `claude:spawn` action. Strongest
    possible demonstration: the user sees the new interaction
    pattern AS THEY ONBOARD.
  - Tutorial doc (Stage 23 PRD's "Patterns" section): walks
    through each of the three action types with a runnable
    snippet. Lives in `docs/prd/stage-23-canvas-actions.md`.

**Where it lands in the roadmap:**

**Stage 23 — Actions in canvas HTML (Claude ↔ HTML loop).** Ships
**ahead of Stage 21** (per Geoff). Sequencing:

- Stage 23 ships *alongside* Stage 18 (installer) so first-launch
  ships with an interactive welcome page that uses the convention.
- Stage 23 *requires* Stage 17b (✅ shipped — `duo html *` ops) and
  Stage 19c (✅ shipped — `dispatchNewTab`). Ready to pull in now.
- Cross-refs Idea 5 (quick-docs menu) — the menu surfaces files
  that USE the Stage 23 convention. Idea 5 is the navigation; Stage
  23 is the interaction model.

**Future expansions (deferred, not blocking v1):**
- Bigger action vocabulary (`duo edit`, `duo reveal`, `duo
  selection-format`).
- Form submission convention (`<form data-duo-action="...">` for
  multi-field input).
- Page-script opt-in (Stage 17e) for richer in-page logic (state,
  animations) — orthogonal to actions, but the action convention
  works either way.

### Idea 5 — Pin WorkingPane tabs (reframed from "menu") ✅ understood

**Geoff's seed (verbatim):** "Add a menu for duo that stashes quick docs
and which is accessible use case would be something like on boarding
content or always available quick references for product managers
Capital one"

**The deeper intent (Geoff's expansion):**
> "I think there's a simple implementation: we create a mechanism to
> pin certain tabs, make it take extra effort to close them; I could
> imagine a lot of use cases — eg we ship w a pinned html file that is
> FTUX guidance (powerful when combined with the idea 4 primitive we
> discussed); could also imagine a person keeping a persistent task
> list pinned (I would do this!); the menu approach is a different
> version of this; eg even more persistent than pinning."

**The reframe:** Skip the menu. Ship **pin tabs** instead — far simpler,
solves the same use cases, and slots beautifully into the existing
tab strip without adding new chrome.

**Resolved understanding (ship as Stage 24):**

- **Pin scope: WorkingPane tab strip only, any tab type.** Browser
  tabs, canvas, markdown editor, preview tabs — all pinnable.
  Terminal tabs (middle column) are NOT pinnable in v1.
- **Pin UX:**
  - Right-click → "Pin tab" / "Unpin tab" context menu.
  - Pinned tabs render with a pin icon (leftmost in the tab strip
    establishes visual hierarchy).
  - `⌘W` on a pinned tab triggers a small confirmation modal:
    "This tab is pinned. [Unpin and close] [Cancel]." Right-click
    → Unpin always works without confirmation.
- **Storage: `~/.claude/duo/pins.json`** — per-user, survives Duo
  reinstalls + updates.
  - Schema:
    ```json
    {
      "pins": [
        { "type": "html-canvas", "path": "/Users/.../welcome.html",
          "source": "distro:aip-pm-starter" },
        { "type": "browser", "url": "https://wiki.capitalone.com",
          "source": "user" },
        { "type": "editor", "path": "/Users/.../tasks.md",
          "source": "user" }
      ]
    }
    ```
- **Distro-supplied default pins** — Stage 18b distro pack format
  grows an optional `pins` array in `PACK.json`. Installer merges
  these into `~/.claude/duo/pins.json` on **first install only**
  (NOT on Duo update — respects user removal).
- **Restart persistence:** pinned tabs are the highest-priority
  entries in Stage 21c session restore. Pinned ALWAYS restores;
  unpinned tabs restore best-effort.
- **Cross-refs:**
  - **Stage 23 (Idea 4):** the FTUX pinned welcome page uses
    `data-duo-action` buttons. Pin + canvas-actions = the full
    onboarding loop.
  - **Stage 18 + 18b (Idea 3):** default pins ship with the
    installer / distro pack.
  - **Stage 21c:** pinned tabs anchor the session-restore behavior.
  - **Idea 1 (Stage 22 navigator overhaul):** pinned tabs could
    optionally surface in the navigator's user-context section
    as a "Pinned" sub-list. Defer to a polish iteration.

**Where it lands in the roadmap:**

**Stage 24 — Pin WorkingPane tabs.** Independent of most other
stages; pulls in cleanly anytime after Stage 23 (so the FTUX page
can use `data-duo-action`). Sequencing: Stage 23 + Stage 24 + Stage
18 ship as a coordinated trio for first-launch UX.

**Future (deferred, NOT v1):**
- Top-bar menu (Help → Quick Docs) for occasionally-referenced
  content the user doesn't want as a permanent tab. Revisit if
  pinning proves insufficient.
- Pinned terminal tabs (persistent shell sessions across restart).
  Different restore semantics; defer until felt.

### Idea 6 — Post-redirect chrome banner (context for confused users) ✅ understood

**Geoff's seed (verbatim):** "Duo opens certain URLs in the default
system browser if it could wrap that session in some chrome for example
a return to duo button and or a message that says this page is not
supported within duo please talk to the AXT team"

**The deeper intent (Geoff's expansion):**
> "What problem this solves — confused user landing in Safari with no
> context."

A non-technical PM clicks a link in Duo, suddenly lands in Safari,
doesn't know why or how to get back. The chrome is for context +
user empathy.

**Resolved understanding (ship as Stage 25):**

- **Surface: post-redirect banner only.** No pre-prompt modal (would
  add friction; non-technical PMs don't read pre-confirmation
  dialogs anyway). After `shell.openExternal` fires, Duo flashes a
  small banner above the WorkingPane.
- **Banner content:**
  - Default copy: "Sent `<host>` to your default browser. ⌘Tab to
    find it."
  - Optional per-domain `reason` text appended from
    `external-domains.json` ("This wiki uses internal SSO that Duo's
    embedded browser can't currently handle.").
- **Auto-dismiss after ~5 seconds.** User can ✕ dismiss earlier. No
  blocking interaction.
- **Schema for `external-domains.json` — backward-compatible
  extension:**
  ```json
  {
    "domains": [
      "claude.ai",
      "chatgpt.com",
      {
        "host": "wiki.capitalone.com",
        "reason": "Internal SSO not supported in Duo's embedded browser."
      }
    ]
  }
  ```
  - String entries (current format) keep working.
  - Object entries opt-in to per-domain `reason` text.
  - **Contact-link mechanism (`mailto:`, slack channel, etc.)
    deferred** — Geoff said "ignore that part." v1 just shows
    the reason as banner text; future iteration can add a
    clickable contact action when felt.
- **Distro support (Stage 18b cross-ref):** Stage 18b's
  `extra-skills/PACK.json` can ship domain entries that get merged
  into the user's `external-domains.json`. Cap One's distro pre-
  populates entries for internal hosts with friendly reason text.

**Where it lands in the roadmap:**

**Stage 25 — Post-redirect chrome banner.** Small ship (~80 LOC):
new banner primitive (similar to `<WriteWarningBanner>` but
auto-dismissing); schema migration in `external-domains.json` reader;
hook into `shell.openExternal` call site in `electron/main.ts`.

Sequencing: Stage 25 is independent of most other stages; can ship
anytime. Combines well with Stage 18b (distro-supplied per-domain
reasons make the Cap One context legible). Probably slots after
Stage 23/24 (which directly serve the FTUX path) and before Stage
21 polish.

### Cross-stage interactions to call out in roadmap.html

The six ideas are deeply interconnected. Roadmap.html's stage cards
need to surface those cross-refs explicitly so future readers see
the dependency graph:

- **Stage 18 (FTUX) + Stage 18b (distro packs) + Stage 22 (navigator)
  + Stage 23 (canvas actions) + Stage 24 (pinned tabs):** the FTUX
