Context

Today Duo can open a folder, edit it, and run terminals inside it — but it has no path from "folder exists on disk" to "folder is a tracked GitHub repo." Users hit this in four flavors:

U1 · Brand-new folder, never on GitHub

Beginner started a project locally. Wants it on GitHub for backup + sharing. Not a git repo yet.

U2 · Existing folder + existing remote

Folder of code from a teammate / old machine. Repo exists on GitHub already. Wants to connect the two.

U3 · Local git repo, no remote yet

Already git init'd (maybe by a tool, maybe by you). Need to attach a GitHub remote — new or existing.

U4 · Distro pack publishing

Pack builder finished a pack via the workshop. Needs to push it to org / personal GitHub so a cohort can install from it. Crosses paths with ENH-149's gh-auth story.

"Link to GitHub" needs to handle all four without being four different flows. The decisions below shape how.

The two flows, visualized

Flow A · Create new GitHub repo from this folder

Folder isn't on GitHub yet. We make it.

┌──────────────────┐    ┌────────────────────┐    ┌─────────────────────┐    ┌──────────────────┐
│ git init         │ →  │ git add . + commit │ →  │ gh repo create      │ →  │ git push -u      │
│ (if not a repo)  │    │ (if no commits)    │    │   --source=. --push │    │ (sets upstream)  │
└──────────────────┘    └────────────────────┘    └─────────────────────┘    └──────────────────┘
                                                  │ name + visibility
                                                  │ pulled from modal
                                                  └─→ remote URL returned

Flow B · Connect to an existing GitHub repo

Repo already exists on GitHub. We wire the local folder to it.

┌──────────────────┐    ┌──────────────────────┐    ┌──────────────────────┐    ┌───────────────────────┐
│ git init         │ →  │ git remote add       │ →  │ git fetch origin     │ →  │ Decide: push, pull,   │
│ (if not a repo)  │    │   origin <url>       │    │ (probe remote state) │    │ or branch-only?       │
└──────────────────┘    └──────────────────────┘    └──────────────────────┘    └───────────────────────┘
                                                                                │
                  remote-has-commits + local-has-commits → conflict gate ───────┘
                  remote-empty + local-has-commits        → push -u
                  remote-has-commits + local-empty        → fast-forward pull

Flow B's conflict gate is the genuinely-hard case. The other three branches are mechanical. See Decision 2 for the policy.

Pre-state inventory

Before running either flow, we read what's already true about the folder. The matrix below is what the modal's preview section displays:

Pre-state Flow A (new) reaction Flow B (existing) reaction Risk
.git/ absent Run git init in pipeline Run git init in pipeline Safe
.git/ present, no commits Stage + initial commit, then push Add remote, fetch; remote-empty → push, remote-has-content → pull Safe
.git/ present, has commits, no remote Push existing history as new repo Add remote, fetch; potential conflict on push Confirm
.git/ present, has remote already Refuse OR offer "replace remote" Refuse OR offer "replace remote with <new-url>" Block
Uncommitted changes in working tree Stage + commit (initial only) Block until user commits / stashes Confirm
Empty folder (no files at all) Allowed — pushes empty repo + README skeleton Allowed — fetches whatever's on the remote Safe

Decisions

Decision 1 · Entry-point shape

One menu entry with new-vs-existing radio, two separate entries, or CLI-first?

Where the user reaches for "link this." Affects the File menu, FileTree context menu, and whether duo gh-link is the primary surface vs. a wrapper.

Decision 2 · Pre-state risk policy

When the folder is already a git repo / has a different remote / has uncommitted changes — what do we do?

The genuinely-hard part of this feature. Each of the Confirm / Block cells in the pre-state table follows one of these three policies.

Decision 3 · Default visibility for new repos

When the user picks "create new repo," what's the default visibility?

Tiny but consequential — accidental-public-push is the canonical "oh no" moment in onboarding flows. Modal still surfaces the choice; this is just what's pre-selected.

Decision 4 · Multi-host gh / GitHub Enterprise

Should the modal expose a host picker — and when?

Crosses ENH-149's enterprise-Mac story. Your work-machine ended up not running gh at all in the end; if it gets installed it'll likely be configured against github.com only. But the cohort distribution scenario (U4) is exactly where GHE hosts show up.

Decision 5 · Post-link behavior

After "Create + push" / "Connect" succeeds, what happens next?

The 5 seconds after the operation finishes. Small UX move that signals success and points at the next action.

General comments / shape pushback

Anything not captured by the 5 decisions above — naming pushback (duo gh-link vs duo link vs duo publish?), use-case I missed, surface I shouldn't ship, edge case I should explore before coding.

What we're explicitly NOT deciding here (defer / out-of-scope)
  • gh authentication path. Closed by ENH-149 → ENH-150 v2: pack-supplied integrations[] + Doctor panel. If gh isn't authed when the user opens "Link to GitHub," modal points at Doctor (or runs gh auth login --web inline per ENH-150 Q3).
  • SSH key flow. v1 assumes HTTPS + gh's web auth. SSH-only users have to drop to terminal. Re-open if the work-machine ends up needing SSH-only.
  • Git LFS. Defer; large-file users can run git lfs install manually before linking.
  • Submodules. If a folder has submodules, link the top-level only. Sub-paths show up unchanged.
  • Branch protection / templates / .gitignore boilerplate. v1 doesn't seed README / .gitignore / LICENSE / branch rules. Users get a blank repo; gh repo create's template flags can come later.
  • Pull / fetch conflict resolution. If Flow B hits a conflict (remote has commits + local has commits + no fast-forward path), v1 surfaces the conflict and points at terminal. We don't ship merge UI.
  • Unlink. "Remove remote" / "Forget the link" — easy enough via git remote remove origin in terminal. Modal could expose it later; not v1.
