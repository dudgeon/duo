Duo Home Screen — twelve visions

ENH-212 UI study 2026-06-12 · shortlist the visions you like, answer the decisions, hit Copy
What this is. Twelve distinct layout visions for a default Duo home screen — a pinned page whose job is re-entry into inactive projects: scan your recent Claude projects, see the last few sessions in each (with a path to scan deeper), glance at recently-edited files, and click to focus an open session or reopen-and-resume a closed one. All mocks use the same sample world: 6 projects, 24 sessions, rendered in the Atelier app aesthetic at roughly half scale. Each mock shows the whole screen unless marked otherwise. Use the Shortlist toggle on the visions worth keeping (pick 2–4), then answer the decision cards at the bottom.

The sample world (shared across all mocks)

duo (142 sessions, active 12 min ago) · home-brain (67, 2 h) · agents-for-everyone (38, yesterday) · work-harness (24, 3 d) · travel (11, 1 w) · field-notes (9, 2 w). Two sessions are currently open (green open pill — clicking those focuses, never duplicates).

Decisions

Shortlist 2–4 visions above, then answer these. The shortlist + answers travel together in the Copy payload.

Decision 1 · Organizing axis

What is the primary organizing axis of the home screen?

This is the load-bearing choice — it selects which visions are even candidates. The stated job is re-entry into inactive projects, which argues for project-grouped; but "what was I just doing" is temporal.

Decision 2 · Density model

Do all projects get equal space, or does activity earn space?

With 6–12 projects and a 1.5–2 screen budget, uniform treatment spends ~40% of pixels on projects you haven't touched in weeks. Variable density spends pixels where re-entry value is high — but the layout shifts between visits.

Decision 3 · Recent files

How do recently-edited files appear?

File-mtime scans of project roots are cheap and truthful. The open question is prominence — and what clicking a file chip does (presumably opens it in the editor/canvas, independent of any session).

Decision 4 · Sorting & depth controls

How much control chrome does v1 carry?

You mentioned "some sorting options are likely useful" and "an opportunity to scan beyond the most recent few." Each control adds chrome to a page whose virtue is calm.

Decision 5 · Project scope & nesting

What counts as a "project" — and what happens to nested ones?

Claude's ~/.claude/projects/ has one directory per cwd, so worktrees, subdirectories you happened to launch from, and nested projects each appear separately. Your 6–12 "real" projects might be 30+ encoded dirs.

Decision 6 · Resume target window

When a closed session is clicked, where does the resumed terminal open?

Open sessions focus their existing terminal (possibly raising another window) — that part is locked. The question is the reopen path, now that multi-window shipped (ENH-191).

Decision 7 · Where Home lives

How is the home screen reached?

The premise is "a pinned page persisted across windows" — note pins are currently per-window state in the v2 session envelope, so a shared Home pin is a new (small) concept either way.

Implementation notes that don't need decisions yet
  • Data source is live, never cached (no-sidecar rule, ENH-183 § D9): project list from ~/.claude/projects/* dir scan; session title / msg count / mtime via the existing claude-session-tracker read ladder; recent files via fs mtime scan of project roots; open-session detection by matching live terminal cwds + captured session IDs.
  • The page can't be a plain static HTML pin. It needs live data in and actions out (focus terminal, spawn claude --resume). That means a privileged surface — likely a dedicated WorkingTab kind (like JsonView) rather than a user-editable page. Surfaced as a model question in chat.
  • Session titles come from the JSONL first-message ladder — quality varies; truncation rules already exist (cleanAndTruncate).
  • Cost guard: title reads only for the visible top-N sessions per project, lazily for "show more".
