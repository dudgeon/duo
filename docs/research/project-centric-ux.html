Project-centric UX — a design exploration

Research ENH-182 Duo · 2026-05-24 · owner-decision playground
What this is. A design exploration of refactoring Duo so a project becomes a first-class organizing primitive — a project switcher, with a session's files, terminals, and browser tabs hanging off a project parent. It compares whole-window directions and the thorny edge cases, weighs pros and cons, grounds the options in how mature IDEs and SaaS tools model "project / workspace / folder," and ends each theme with an inline owner-decision card. The short version (recommended path)

  • Folder-first, not gated. Let people work in any folder immediately; declaring a project is a lightweight, optional upgrade that unlocks (never forces) CLAUDE.md / agents.md / git init.
  • A project is "any folder, that Duo names and remembers." Created implicitly; enriched progressively; aware of — but not defined by — its git repo and its Claude Code project dir.
  • Switch via the title-bar dropdown you already shipped (extend WorkspaceSwitcherDropdown) + a ⌘P type-ahead. Defer the thin left rail until many-project parallel work is proven.
  • One active project at a time; switching is cheap. Tabs from other projects are tagged, not hidden — a session can span projects without a confusing multi-root mode.
  • Workspaces survive as an optional super-container (a workspace holds one-or-more projects) — but that tier is a later decision.

1 · Where Duo is today

The refactor is unusually low-risk for one reason: there is nothing to tear out. Duo has no Project object, no project registry, and no project switcher. "Where am I" is answered by three independently-computed signals that are only loosely linked, plus an orthogonal "is Claude running" probe: 

  TabSession.cwd          per-terminal-tab launch dir   (each tab its own)
  nav.state.cwd           navigator root, localStorage  ('duo.nav.cwd')
        └─ follow-mode ──▸ moves to the active tab's cwd, UNLESS pinned
  getGitStatus(cwd)       on-demand `git rev-parse --show-toplevel`
        └─ workTreeRoot, branch, dirty — recomputed per navigator folder

  claudePresence          process-tree probe: is the `claude` binary alive
                          in the front tab?  (no-pty | shell | claude)
                          ── orthogonal to all of the above ──

And today's "workspace" is not a runtime object either — it's a thin named envelope (WorkspaceFile) wrapping the session-restore snapshot (SessionState: a flat list of terminals, browser tabs, file tabs, the navigator path, split state). Switching workspaces force-flushes state, kills every PTY, tears down browser tabs, and reloads the renderer. The switcher (WorkspaceSwitcherDropdown.tsx, ENH-171) is a title-bar dropdown with a recent list — exactly the chrome a project switcher would reuse.

What does not exist today (all confirmed in-tree):

  • missing Any Project type / registry / persisted list of known projects.
  • missing Any reading of ~/.claude/projects/<encoded-cwd> or sessions-index.json (ENH-177 built it, then reverted pre-cut — not in the tree).
  • missing Any CLAUDE.md parsing or marker-based "this folder is a project" classification. (ProjectClaudeContext only checks for the existence of CLAUDE.md / .claude / tasks.md / AGENTS.md to render a collapsible context group — cosmetic.)
  • missing Any GitHub API integration (Duo only string-parses git remote get-url origin for "Open on GitHub" links).
  • exists & reusable Git work-tree-root detection, peer-repo scanning (BUG-135), per-file dirty dots, the navigator + follow-mode, and the title-bar switcher pattern.

Upshot: a project primitive is a new first-class anchor that the three location signals would derive from — additive, not a rewrite. The hard part is product/UX, not plumbing. That's why the rest of this doc is mostly decisions, not code.

2 · The core fork — gated vs. progressive

You named the biggest decision yourself: "should we let a user use Duo in arbitrary folders / repos / CC-dirs without declaring / creating / selecting a project?" Everything else hangs off this. The prior art is lopsided: the modern default (VS Code, Sublime, Zed, GitHub Desktop) is open a folder and that folder IS your project — zero ceremony. The heavier "you must create/import a project" models (JetBrains, Xcode) pay for richer per-project state with an explicit setup step that would land hardest on Duo's non-engineer PM.

But "no concept at all" is what Duo has now, and it's fragmented. The middle path — progressive — lets you work instantly in any folder, while gently offering to "remember this as a project" so the switcher, per-project context, and one-click CLAUDE.md/git scaffolding become available when wanted.

This sets the ceremony floor for every new user and every "just poke around this folder" moment. It also decides whether multi-project sessions are even expressible.

3 · What is a Duo project? (the 4-way map)

You asked specifically about the relationship between a Duo project, a GitHub repo, and a Claude Code project. They're four different things that usually — but not always — line up on the same folder:

Folder

the filesystem

A path on disk. Always exists. May or may not be a git repo; may or may not have a CLAUDE.md.

Git repo

git / GitHub

A folder with .git/. Has a work-tree root, branch, optional origin remote → a GitHub repo. Can be nested (repo-in-repo, submodules, monorepo).

Claude Code project

Claude Code

Implicit: CC keys sessions/history off the cwd, stored at ~/.claude/projects/<encoded-cwd>. Plus CLAUDE.md / .claude/ as context markers.

Duo project

the new primitive

A folder Duo has named and remembers, that knows about its repo and its CC dir but isn't defined by either. The anchor the three location signals derive from.

6 · What happens to workspaces

You flagged this as a future decision and floated "we might still want workspaces, which could contain one or more projects." Today's workspace is just a saved snapshot of tabs (§1) — it isn't a project container at all. The options range from retiring it to promoting it into the super-container tier (Direction D). Because today's workspace owns no project concept, none of these is blocked by existing data — but the more we keep, the more concepts the user juggles.

7 · Pros & cons, and why it's additive

Pros of going project-centric
  • One coherent answer to "where am I" — replaces three loosely-linked location signals with a single anchor they derive from.
  • Becomes the natural scope for Claude's context (the Cursor/Windsurf/Zed lesson): per-project CLAUDE.md, history, skills, and — later — agent memory.
  • A real home for per-project state Duo can't cleanly hang anywhere today (pinned nav root, recent files, per-project browser tabs).
  • A genuine switcher + recent list — the single most-expected primitive, and a big legibility win for the PM.
  • The obvious hook for one-click "add CLAUDE.md / agents.md / git" onboarding.
Cons / risks
  • A new top-level concept for a persona who wanted fewer concepts — mitigated only if creation stays implicit and ungated.
  • Multi-root/two-tier is a proven confusion generator; easy to over-build.
  • Nested markers + non-git folders + monorepos are genuinely fiddly to get right.
  • Touches the most central surfaces (navigator root, new-tab cwd, session restore, the title bar) — broad blast radius even though it's additive.
  • Per-project persistence means a new store + migration discipline (and the session-restore reload path is destructive today).
Why this is additive, not a rewrite (feasibility note — not a build plan)

From the code map: there's no project logic to replace. A project record would be a new store (e.g. ~/.claude/duo/projects.json), and the three existing location signals get a new source of truth to derive from:

  • Navigator root already lives in one place (useNavigator, duo.nav.cwd) — point it at activeProject.root instead of free localStorage + follow-mode.
  • New-tab cwd seeds from nav state today — seed from the active project instead.
  • Git + CC-dir are already computed per-cwd — attach the results to the project as derived attributes; no new detection needed beyond reading ~/.claude/projects/<encoded> (the reverted ENH-177 work is a starting point).
  • The switcher is the shipped WorkspaceSwitcherDropdown generalized from "recent workspaces" to "recent projects."
  • CLI parity (CLAUDE.md § 4) would add a duo project verb family mirroring the UI — out of scope for this doc, but the existing duo workspace verbs are the template.

The riskiest existing behavior to revisit is that switching today does a destructive renderer reload; a project switch wants to be a live, non-destructive re-point (Decision 4's "cheap switch"). That's the one piece that's more than additive.
