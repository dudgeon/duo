Agent-agnostic Duo v2 — the runtime audit

ENH-189 · REV 5 DECISIONS OPEN 2026-07-09 · audited at v0.13.7-dev · supersedes the rev-4 playground's decision set (D1–D7 folded in, updated)
What this is. A from-scratch re-audit of every place Duo assumes the user's CLI coding agent is Claude Code — not just the repo docs and skills (the rev-4 focus), but the runtime: session storage, presence detection, resume, cron, attention, priming, install, packs, and UI copy. Six parallel code audits at v0.13.7; 46 consolidated touchpoints (rev 4 catalogued 19). Full file:line evidence lives in docs/research/agent-agnostic-audit-2026-07-appendix.md. The decision cards at the bottom replace rev 4's D1–D7 — one walk decides everything.

1 · Headline: the coupling deepened while the decisions sat open

Rev 4 (2026-06-06) found the duo CLI + socket agent-neutral and the Claude coupling confined to a "thin lifecycle skin." Both halves of that are now only half-true. The neutral core is still neutral — all ~100 CLI verbs, the vault/graphbook engine (zero claude references), the PTY layer, the env stamps (DUO_SESSION/DUO_TAB/DUO_WINDOW). But the "skin" is no longer thin: the three biggest features shipped since rev 4 — Home Projects rollup (ENH-212), the Async Catch-Up board + session digests (ENH-231), and scheduled sessions (ENH-223) — are all built directly on Claude Code's private surfaces (the ~/.claude/projects/*.jsonl transcript schema, comm==='claude' process matching, claude --session-id/--resume). The Claude-coupled layer is now Duo's differentiating product surface: the pair-work-awareness layer.

The failure profile is silence. Almost nothing crashes for a non-Claude user — every read is try/catch → empty. A Codex user gets: an empty Home screen, an empty catch-up board, a presence dot that never lights, an attention badge that never fires, no resume pills, cron "Same (resume)" silently downgrading to fresh, a close-guard that silently stops protecting live work, a doctor that false-reds the install, and an agent tab that types claude into their shell (command-not-found, or an "Install Claude Code" banner). The app looks fine and is hollow — with zero signal about why.

3 · The structural reading

Contract types — the maintenance-burden law, updated

Rev 4's law holds: coupling that rides a public contract is durable; coupling that reads a private format is a standing drift liability. The audit sorts today's dependencies:

ContractTypeDependents
claude CLI flags (--resume, --session-id, --append-system-prompt, -p)public (to one vendor)resume pills, cron builders, priming shim, headless gate
CLAUDE.md loader, skills dir, agents dir, settings.json hookspublic but Claude-exclusivepriming, attention, guard, skill/subagent discovery, distro packs
~/.claude/projects/*.jsonl path + record schema + tool-call shapesprivate, reverse-engineeredHome, catch-up board, digests, titles, resume pointers, cron resume probe
comm==='claude' process name; ESC+CR REPL bytes; TUI boot timingprivate, observed behaviorpresence, close guards, Enter semantics, seeded prompts

The uncomfortable finding: the private-contract rows are exactly where the post-June product investment went. Home, catch-up, and digests are built on the highest-drift surface Duo touches — that's a liability even in an all-Claude world (a Claude Code transcript-format change breaks Home), and it's the layer other agents can't reach at all.

The inversion: Duo already owns the PTY

The strategic opening the audit surfaced: Duo doesn't have to scrape another tool's store to know what's happening in its own terminals. Duo spawns every PTY — it sees every byte in and out, the cwd, the process tree, the timestamps. A Duo-owned observation layer can agent-agnostically supply: liveness (process-tree match against a per-agent name set), attention ("output went quiet after a question-mark-shaped burst" / prompt-idle heuristics), session labels (first user-typed line), and activity recency. That's rule-12-clean — Duo observing its own terminals is Duo-owned state, not a mirror. What it can't supply is resume (needs the agent's own session id) and deep history (the agent's transcript) — but resume rides public per-agent CLI (claude --resume, codex resume --last), which is a small, low-drift adapter table. The private JSONL scraping stays what it is today: a Claude-only enrichment, not the load-bearing layer.

Where the seams already are

The code is better factored for this than the count suggests. Single-point seams: presence = one string (claude-presence.ts:193); resume = one builder (buildResumeCommand); spawn = one payload site (dispatchPostSpawnWrite) + one enum; install destinations = one constants table (install-service.ts:71-118); Enter bytes = one gate (TerminalPane.tsx:399). An AgentProfile record threaded through those five seams covers the majority of the functional matrix.

4 · The tactical ladder

Rungs are ordered and mostly independent — each ships value alone; later rungs assume earlier ones.

T1
The honesty pass. Stop lying to non-Claude users: doctor detects which agents are present and scopes its checks (no false-red); first-launch banner says what will/won't activate; copy sweep to "the agent"/"your agent" in the ~16 UI strings + the shipped guides; the install banner's Claude-missing state names the actual situation. No behavior change for Claude users.
upfront: daysongoing: ~zero
T2
AgentProfile seams. A small data-driven registry (claude, codex, gemini, aider, custom…): binary name(s), launch command, resume command template, headless-flag denylist, process-name set, Enter-key byte profile, install-doc channel. Thread it through the five seams (§3). Tab kind becomes kind:'agent' + agentId (migrating persisted 'claude'), cron claude-arm becomes agent-arm, new-tab gains --agent <id>. Presence + close-guard + resume + cron work for any registered agent.
upfront: 1–2 sprintsongoing: low (public contracts only)
T3
Duo-owned observation layer. PTY-level session records (Duo-minted id, cwd, first-prompt label, activity times, agent id) persisted in Duo's own store; Home/catch-up render from it for every agent, enriched by the Claude JSONL reader (and later, optional per-agent enrichers) when available. Attention gains an idle-heuristic fallback for hook-less agents.
upfront: ~a sprintongoing: low — Duo owns the format
T4
Install & skills for everyone. Dual-write the skill to ~/.agents/skills/duo/ (the open standard Codex/Gemini/aider read); optional managed AGENTS.md/GEMINI.md blocks (opt-in, same marker discipline); distro packs decompose per detected agent; doctor + "Your agent settings" pane become multi-root.
upfront: ~a weekongoing: low-moderate (N loader conventions)
T5
Codex depth (only on demonstrated demand). Duo-managed Codex notify hook (agent-turn-complete → thread-id pointer → attention + resume-by-id), codex resume wiring, maybe rollout-JSONL enrichment (high drift — last resort). This is rev 4's §2c plan; it stays parked until a real Codex cohort exists.
upfront: ~a sprintongoing: moderate-high if JSONL parsed
T6
Storage-root migration (optional, anytime). Move ~/.claude/duo/ → ~/Library/Application Support/duo/ (where the socket already lives) with a migration shim. Pure hygiene; nothing functional blocks on it.

5 · Decisions

These replace rev 4's D1–D7 (never walked). Recommendations reflect the new evidence; where a rev-4 recommendation changed, the card says so.

D1 · Posture

What target posture for agent-agnosticism?

Rev 4 recommended "Claude-first, Codex-tolerant" with the adapter abstraction deferred until a third harness. The new evidence: the coupled layer is now the differentiating product surface (Home/catch-up/attention), and it silently hollows out for anyone else — while the seams for a profile are small and ride public contracts. The recommendation moves one notch.

D2 · Code model

How do we model "an agent" in code?

Whatever the posture, the touchpoints need a shape. The audit found five single-point seams — the question is what flows through them.

D3 · Tab & cron kinds

Does kind:'claude' become generic?

The enum appears in persisted session state, cron store, IPC, and heuristics (hasClaudeKindTerminal, rail presence). Rev 4's D4 offered "add a codex kind"; a generic kind ages better.

D4 · Presence & attention

How does Duo know an agent is live / waiting on you?

Presence is one string today. Attention rides Claude hook events; Codex has a notify program; Gemini/aider have nothing. The PTY-observation idea (§3) offers a universal fallback.

D5 · Sessions, Home & resume

What feeds Home, the catch-up board, and resume for non-Claude agents?

Today: Claude's private JSONL, exclusively. The board/digest layer is the deepest private-format dependency in the tree — a drift risk even Claude-only.

D6 · Priming & context

How does a non-Claude agent become Duo-aware?

Claude gets: PATH shim (--append-system-prompt) + SessionStart hook + CLAUDE.md block + skill. Codex has no per-session system-prompt flag at all (rev 4, verified); its channels are AGENTS.md and the skills standard. Gemini has --system-prompt / GEMINI.md.

D7 · Skill install targets

Where does the duo skill (and distro-pack skills) install?

The SKILL.md format is the open agent-skills standard; only Duo's destination is Claude-only. Rev 4's D3 asked this for Codex; the answer generalizes.

D8 · Project markers & context wash

Do AGENTS.md / .agents/ become project markers and get the context wash?

The current exclusion is deliberate and code-frozen (projects-service.ts:103) — this card is the formal request to revisit it. Affects rail qualification, home-rollup folding, and which files get the terracotta agent-context wash.

D9 · Storage root

Does ~/.claude/duo/ stay, or migrate to Application Support?

Pure namespacing: 22 of 26 stores are agent-neutral; the socket already lives in ~/Library/Application Support/duo/. Migration touches ~30 path refs + every installed user's data.

D10 · Copy sweep scope

How far does the "the agent" rename go?

~16 UI strings + the shipped guides (what-duo-does 126 hits, vault/rollup guides, FTUX welcome, enterprise doc) + IPC/type identifiers. Where the mechanism IS Claude (install banner's Claude-missing state, claude-return docs), Claude-naming is honest and should stay.

D11 · Sequencing

What gets committed to upcoming sprints?

The ladder (§4) is designed so T1 ships alone. T2 is the structural move; T3 makes Home/attention real for everyone; T4 is install reach; T5 waits for demand.

Deferred detail — cross-agent surface table, rev-4 mockups, verification caveats

Cross-agent integration surfaces (memory file / skills dir / system-prompt flag / hooks / session store / resume / headless, per agent) are tabulated at the end of the appendix. The Codex facts were verified 2026-05-27 against OpenAI docs + issues (#11588 no append-system-prompt; #8923 no session-id exposure; #4005 notify thread-id) — re-verify at implementation time; Codex moves fast.

UI mockups for a second-agent tab, presence pill, and agent-config pane live in the rev-4 playground (§5a/5b/5d) and still apply under D2=A/D3=A — they become "any registered agent" rather than "Codex".

What this audit did NOT do: live-run Codex/Gemini/aider inside Duo (per the static-review-vs-live-walk lesson, a T2 implementation must live-verify against at least one real non-Claude agent before claiming the profile works).
