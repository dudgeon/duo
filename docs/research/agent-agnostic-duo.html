Agent-agnostic Duo — Claude Code + Codex

RESEARCH ENH-189 Max-effort research sprint · 2026-05-27 · branch claude/duo-agent-agnostic-research-9y1t3
What this is. A decision-bearing audit of every place Duo is wired to Claude Code, scored for what would happen under OpenAI's Codex CLI — works, no-ops, or breaks — with options for each, weighed by upfront build vs ongoing maintenance. The headline: Duo's bridge is already ~90% harness-neutral; the coupling is a thin lifecycle skin. Answer the decision cards and hit Copy decisions at the bottom to round-trip back to Claude.
The one-sentence thesis. The duo CLI + socket bridge are agent-neutral and work with Codex today — what doesn't port is (1) teaching the agent that duo exists and (2) a handful of lifecycle features that read Claude's private on-disk state or shell its private flags. The cheap, durable play is to parameterize the launch/presence/marker layer and degrade the rest gracefully — while treating MCP (the one extension surface both harnesses share) as the long-term, drift-proof spine.

1 · The architecture in three rings

Every Claude-Code touchpoint falls into one of three concentric rings. The further out, the more Claude-specific — and the more it breaks under Codex.

3 · Why it's asymmetric — Claude Code vs Codex extension surfaces

The cost isn't symmetric because the two harnesses give Duo very different hooks. Claude Code offers three ways to inject context (skill, hook, --append-system-prompt); Codex offers essentially one clean shared one (MCP), one repo-invasive one (AGENTS.md), and an opt-in slash prompt.

Maintenance-burden law. Anything that reads another tool's private file format (the rollout JSONL schema) or shells its private flags (--append-system-prompt) is a standing drift liability — it breaks silently on the next upstream release. Anything that rides a public contract (a documented subcommand like codex resume --last, an env var, or MCP) is durable. Every option below is graded on which side of that line it sits.

4 · The cost landscape

Plotting each approach by upfront build (x) against ongoing maintenance (y) sorts them into four quadrants. The recommended near-term moves cluster in the cheap-and-durable corner; the strategic bet (MCP) trades upfront cost for near-zero drift; the things to avoid sit in the high-drift top band.

5c · Teaching Codex that duo exists

No-op

Do nothing

User manually tells Codex about duo each session. Zero build, zero maintenance — but the autonomous-agent magic silently never happens.

Codex-native

/duo slash prompt

Ship ~/.codex/prompts/duo.md. Discoverable in Codex's slash menu, opt-in, non-invasive. Low build, low drift.

Invasive

Auto-merge AGENTS.md

Write a duo block into the project's AGENTS.md. Automatic, but pollutes the user's repo and drifts. High ongoing tax.

Durable

Duo as MCP server

Expose the verbs as self-describing MCP tools. Both harnesses discover them automatically via their own config. Bigger build, near-zero drift — collapses Rings 1 + 2 into one neutral mechanism.

Decision D3 chooses among these (they're not all mutually exclusive — /duo now + MCP later is a sequence).

6 · Decisions

Seven decisions, ordered from the spine (D1) outward. Recommended picks are pre-tagged; override freely and leave notes.

Decision 1 · The spine

What target posture for harness-agnosticism?

Everything else inherits from this. The trade is reach vs. the standing cost of keeping two (or N) integrations honest as both tools ship weekly.

Decision 2 · Abstraction shape

If we go agnostic, how do we model "a harness" in code?

Only bites under D1=B/C. Determines how a new harness (or an upstream change) ripples through the codebase.

Decision 3 · The onboarding gap

How does Codex learn that duo exists?

The single most important question for Codex value: without this the bridge works but the agent never reaches for it. Options aren't mutually exclusive.

Decision 4 · Launch

How do we open Codex as a tab? (mockup 5a)

The tab-kind enum is 'shell' | 'claude' today. This is a UI + data-model choice.

Decision 5 · Presence pill

How do we detect a live Codex process, and what does the pill say? (mockup 5b)

The probe matches comm === 'claude'. The fix is small; the question is how general to make it + the pill copy.

Decision 6 · Session capture & resume

Do we rebuild resume pills for Codex — and how?

This is where the ongoing-maintenance tax is highest. Codex's session store is date-indexed (not cwd-indexed) with a different schema, so per-cwd reconstruction is both harder and a standing drift liability.

Decision 7 · Config pane + doctor

What happens to the ~/.claude navigator pane and duo doctor? (mockup 5d)

Both currently assert Claude paths. For a Codex-only user the pane shows the wrong thing and doctor shows false red.

Recommended throughline (one coherent path)

D1=A · D3=B+plan D · D4=A · D5=A · D6=A (then B) · D7=C (then A).

Translation: lean on the already-neutral core; make only the cheap, durable parameterizations (codex tab kind, presence matcher, marker set, neutral author default); teach Codex via a /duo slash prompt now while scoping Duo-as-MCP-server as the long-term spine that makes the skill/onboarding question harness-neutral for good. Avoid the high-drift moves — parsing Codex's rollout JSONL and auto-writing AGENTS.md — until parity is a proven user need. Degrade the lifecycle features (resume pills, config pane) on Codex rather than reconstructing them from reverse-engineered state. Net: most of Codex's value ships in a small, low-maintenance diff; the durable bet (MCP) is sequenced, not rushed.

If the goal is broader than Codex (Gemini CLI, aider, …), that's the signal to escalate D1→B and D2→B — but only then, since the adapter's ongoing cost is only justified by a third harness.
