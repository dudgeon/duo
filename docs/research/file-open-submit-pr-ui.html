"Submit PR" affordance — UI treatment study

ENH-221 OQ-1 Decision playground · 2026-06-19 · pairs with docs/prd/enh-221-file-open-flow.md
What this is. ENH-221 opens a GitHub doc into an opaque local checkout so it edits like a local file. The moment the working copy diverges from the fetched baseline, Duo surfaces a way to ship those edits back as a pull request (auto-forking when you lack push access). This page is the one open question the PRD flagged — how that "ship it back" affordance should look and feel. Mockups below are static sketches at ~Duo's editor scale; pick a treatment per decision card and hit Copy decisions.

Decision 1

Where should the "Submit PR" affordance live?

It should be invisible until the doc diverges from the fetched baseline (your "button appears when local differs" rule), discoverable without hunting, and not fight the writing surface. Trade-off is always-visible/discoverable (A) vs. appears-on-divergence/attention-grabbing (B, D) vs. quiet-but-tucked-away (C).

Decision 2 · What the button says

Duo's audience spans non-developers. "PR" is GitHub jargon; "propose / suggest changes" is the Google-Docs vocabulary. The confirm sheet can still say "pull request" explicitly once you're in it.

Decision 2

What label goes on the affordance?

The PRD currently writes "Submit PR" throughout. Worth deciding before it hardens into copy across UI + CLI + skill.

Decision 3

How much does the confirm sheet show before you ship?

More preview = more confidence the right thing goes up (and a place to catch "oops, didn't mean to change that"); less = faster, more Google-Docs-casual.

Decision 4 · After the PR is open

Once a PR exists, the affordance has a job to do on the next edit. PRD P7 says subsequent saves update the same PR.

Decision 4

What does the affordance become after a PR is open?

There's now a live PR; you keep editing. The control needs to both link to the PR and let further edits flow to it.
