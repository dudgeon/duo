The persona & the job. You spin up eight jobs, walk away, and forget what they were. You come back and want to review the work — with a reminder, per session, of what the goal was, the most recent instruction, the file it's touching, and what the next steps are. The surface that serves this is a timeline of commingled sessions, not an aggregation of projects. Pass 1 — Features ideal for catching up (data-blind)

Taking the persona literally: you are a manager returning to a team of agents who each worked while you were out. The surface is your standup. These are the features that serve that job best, ignoring for now what data Duo can actually get.

A · The timeline spine

A1 Commingled reverse-chron stream

One interleaved stream of all sessions by last activity — project is a tag, not a section. The core inversion of today's Home.

Needs: per-session last-activity timestamp.

A2 "Since you were away" watermark

A line marking your last visit; everything above advanced since. Turns catch-up into an unread-inbox sweep.

Needs: a persisted "last seen Home" mark + per-session advanced-since.

A3 Activity sparkline per session

A tiny strip showing when each thread was busy — spot the one that went quiet an hour ago vs. the one that just finished.

Needs: turn timestamps over the session's life.

A4 Batch grouping

"You spun up 8 jobs together" → an optional roll-up header with a done/blocked/running tally. The fan-out you launched is itself an object.

Needs: launch-time clustering of sessions.

B · The session briefing card

B1 Goal line

The original ask, one line — "what was this session for?" The top-of-mind reminder the persona names first.

Needs: the session's first instruction.

B2 Your most-recent instruction

"What did I last tell it?" — distinct from the goal; the latest steer, attributed to you (the card labels it "You asked" so it's never confused with the agent's own line).

Needs: the last human turn.

B3 File(s) in flight

What the session is touching right now — the persona's literal ask. Chips, basename only.

Needs: the set of files edited this session.

B4 Next steps

The agent's own plan for what's left — the single most valuable re-entry cue.

Needs: the agent's todo list / stated plan.

B5 "What happened" narrative

One sentence of story: what it actually did since you left. The hardest field — pure summarization.

Needs: a written summary (inference).

B6 State badge

needs-you / working / done / blocked — the triage primitive every other feature leans on.

Needs: liveness + end-of-transcript shape.

C · Triage & attention

C1 State lanes / filter chips

Filter to "Needs you", "Done — review", "Working". Catch-up is triage; the lanes make order obvious.

Needs: the B6 state.

C2 Question / blocker hoisting

If a session ended on a question or an error, that line becomes the headline. The two "need you" cards float to the top.

Needs: detect the session ended awaiting input.

C3 Suggested reading order

"Start with the 2 blockers, then 4 done PRs, leave the 2 running." A one-line plan for your own next ten minutes.

Needs: states + ages, ranked.

C4 Triage gestures

Pin · snooze · mark-reviewed per card, so a second visit shows only what you haven't cleared.

Needs: Duo-owned per-session review state.

D · Reviewing the work · E · Acting next

D1 Diff-first review

For done sessions, one click to the diff / changed files. The work product is the point of "review the work".

Needs: git branch + base to diff against.

D2 Artifact chips

"Opened PR #214", "ran tests: green", "wrote report.md" — the outcomes, linked.

Needs: detect PR/test/file-creation events.

D3 Cross-session file conflicts

Two agents editing the same file → flag it. A hazard unique to parallel async work.

Needs: edited-file sets across sessions.

E1 One-click next action

Each card offers the obvious move: Answer & continue · Review PR · Decide & unblock · Focus. Catch-up → act, no detour.

Needs: state → action mapping (mostly free).

Pass 2 — Pre-hydrating the data Duo can't infer at open

The constraint, restated. Duo has no general-purpose inference API. It cannot summarize a transcript, write a "what happened" sentence, or cluster sessions by theme at the moment Home opens. Whatever the catch-up view shows must already exist as structured data by the time you look at it.

But the inference Home needs already happened — it happened inside each agent while it worked. Duo's job is not to generate understanding at open-time; it's to capture the agent's structured exhaust at rest-points and replay it.

The pleasant surprise: most fields are free

Duo already does deterministic, seek-based JSONL extraction today (electron/claude-session-tracker.ts) — it reads the head of each session transcript for the first user message (the title) and the tail for the last assistant message (the snippet), plus git branch and timestamps, with zero inference. So ten of eleven fields are deterministic — they need plumbing, not intelligence. Only the optional narrative (B5) needs a written sentence, and even that has a no-inference fallback (use the last assistant block) plus an opt-in upgrade (below).

The pre-hydration pipeline — capture at rest, never at open

Reading head+tail of N transcripts (some reach hundreds of MB) on every Home open is the cost to avoid. Instead, compute a per-session SessionDigest incrementally, triggered at turn boundaries while the session is live, and cache it. Home then reads cheap cached digests.

While live

1 · Trigger

The managed Stop / Notification hook (already installed for the attention badge, ENH-225) also pings duo session digest <tab>. UserPromptSubmit refreshes "last instruction". Fires at every turn boundary — the natural rest-point.

On trigger

2 · Extract

A deterministic parser (core/session-digest/) seek-reads the transcript tail and pulls the table above — goal, last instruction, files, todos, state, artifacts. No inference. Reuses the existing JSONL reader.

On trigger

3 · Materialize

Write the digest to a Duo-owned index keyed on session uuid. It's a cache, always rebuildable from the transcript — the transcript stays the source of truth (§D9, see below).

At open

4 · Assemble

Home reads the cached digests, runs the live liveness check it already does, sorts commingled by activity, and renders. Zero heavy parsing, zero inference at open-time.

The timing insight is the whole design: hydrate on Stop, not on open. The moment an agent finishes a turn is exactly when its digest is both freshest and cheap to compute — and it's well before you ever look at Home.

Is the digest cache a §D9 "sidecar" violation? (the honest read)

CLAUDE.md §12 forbids Duo-owned files that mirror another system's state and drift from it. The digest cache sits right on that line, so be deliberate:

  • Why it's acceptable: it's a materialized index, not an authority. Every field is re-derivable from the Claude Code transcript, it's refreshed on real evidence (the Stop hook fired = the session actually advanced), and the transcript remains the source of truth. This is the same posture as the ENH-212 Home snippet read — just memoized instead of recomputed per open.
  • The invariant that keeps it clean: Home must be able to rebuild any digest from the transcript on demand, and must prefer the transcript on any mismatch. The cache is an optimization you can delete at any time with no loss — never a place where the only copy of a fact lives.
  • What is legitimately Duo-owned (not a mirror, so §D9-clean outright): the pin/snooze/seen review state (C4), the "last seen Home" watermark (A2), and the batch-launch grouping (A4) — concepts Claude Code doesn't track at all.

If the owner would rather avoid the cache entirely, there's a no-store variant: extract digests lazily at open but bounded — only for sessions whose JSONL mtime changed since last open, in parallel, tail-only. Slower on a cold open with many huge transcripts, but zero new persisted state. This is decision Q4.

The one field that needs inference — and how to get it without an API

The "what happened" narrative (B5) and any crisp agent-authored "next step" recommendation genuinely need a written sentence. Duo can't write it. But the agent can, while it's running — it is the inference engine, already in the loop. Two mechanisms, both CLI-parity-clean:

  • Agent self-narration via a new verb — teach the skill to call duo session note "<one-line status>" / duo session next "<recommendation>" at natural stopping points. The agent stamps its own digest; Home replays it verbatim. Progressive enhancement: present when the agent narrated, absent otherwise.
  • No-narration fallback — when the agent didn't narrate, show the deterministic last assistant block (today's snippet). Never fabricate; the worst case is exactly what Home shows now.

This keeps the rule intact: inference only ever happens inside a running agent, never inside Duo at open-time.
