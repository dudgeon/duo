What this is. An owner-facing research doc covering three clustered topics: (1) JSON viewer/editor in canvas (Sprint 11 candidate), (2) image viewing in canvas (deeper roadmap), and (3) other data primitives for the PM persona. Each section: spectrum of options → live mockups → library matrix → recommendation. Ends with a clustered roadmap proposal so this whole theme moves as a unit, not as scattered ENHs.

Why cluster. Duo's PM/dev/designer audience opens these primitives in the same workflows — paste an API response from Slack, drag a CSV from analytics, drop a Figma export PNG, look at a Mermaid diagram. Building them as a coherent data viewer surface with shared chrome (toolbar, breadcrumb, copy, search) earns more than each as a one-off tab kind.

1 · JSON viewer/editor in canvas

Scope. A user opens response.json in Duo (drag-drop, duo edit, FileTree click, paste-from-clipboard). Today it falls through to the unknown-file preview. We want a dedicated, useful experience.

Decision · JSON tier
Tier 3 (interactive collapsible tree) or Tier 2 (syntax-highlighted text)?

Tier 3 is the workhorse experience for "I just need to read this API response cleanly" but adds ~7 KB (@uiw/react-json-view). Tier 2 is read-only with syntax color, ~30 lines of work + the lowlight dep already in tree.

Decision · Library pick (Tier 3 only)
If Tier 3, confirm @uiw/react-json-view as the lib choice — or pivot?

The matrix above scored four options; recommendation is @uiw/react-json-view. Three reasonable alternatives if you want to redirect:

Hand-roll vs library — the real tradeoff

Hand-roll (tier 1+2)

  • Zero new deps. Fits the existing lowlight+monospace stack.
  • Probably ~50 LOC for tier 1+2 read-only.
  • Owner controls every pixel; matches Atelier styling instantly.
  • No upgrade churn from a 3rd-party release cycle.

Hand-roll (tier 3+4)

  • Tier 3 (collapsible tree) hand-rolled: ~300 LOC + accessibility work.
  • Tier 4 (folding gutter, search, lint, validation) is editor-engine territory; hand-rolling reinvents what CodeMirror gives you for free.
  • Edge cases (deeply nested objects, circular refs, very-large files) are bug magnets.
  • No upstream improvements when other tools find new patterns.
Recommendation

Tier 3 with @uiw/react-json-view as a new tab kind kind: 'json'

Sprint 11 lands tier 3 (collapsible tree, edit, copy, search) via @uiw/react-json-view at ~7 KB gz. New tab kind so it doesn't have to fit into the canvas iframe (where the script-block restriction would hurt the interactive tree). File classifier maps .json, .jsonl (line-by-line), .har to this tab type.

Tier 4 is parked until a real workflow surfaces ("I'm editing a 2000-line config and the gutter+search would change my day"). When/if that happens, it folds naturally into the CodeMirror 6 migration path discussed for the Obsidian editor (ENH-096 architecture note). Single architectural shift, two payoffs.

Tier 1+2 is the fallback when libraries don't fit (e.g. very large files where the tree's render cost is prohibitive). The new tab can switch to plain text mode for files over a configurable threshold (~1 MB).

Architectural note — why a new tab kind, not the canvas iframe. The canvas iframe (kind: 'page') intentionally blocks scripts so user-authored HTML can't fire side effects. An interactive JSON tree needs scripts. Putting JSON-viewing in the canvas iframe means either (a) breaking the script-block contract for our own primitives (slippery slope) or (b) re-implementing the tree without scripts using only CSS state (unwieldy). A new tab kind 'json' gets a React component just like 'image' and 'pdf' — clean isolation, full interactivity, fits the existing pattern.
Decision · Edit semantics (Tier 3 only — skip if tier = Tier 2 / Defer)
Inline edits in the tree — autosave on blur (markdown-editor pattern), or require ⌘S?

Tier 3 lets the user click a value to edit inline. Once they tab away or click elsewhere, the change either auto-persists (matches the editor's existing autosave) or sits "dirty" until ⌘S (more conservative — explicit confirmation that the JSON is mutated).

2 · Image viewing in canvas (deeper roadmap)

Current state. .png, .jpg, .gif, .webp, .svg already classify to kind: 'image' and mount a basic image preview tab. What's missing is the affordances that make an image tab useful — pan, zoom, fit-window, color picker for designers, EXIF/dimensions display, copy-to-clipboard.

Toolbar: zoom controls, fit-to-window, 1:1 actual-size, dimensions/size readout, copy-to-clipboard. Pan via drag. Pinch-zoom on trackpad. EXIF panel (toggle, optional). Right-click → "Open in Preview.app", "Reveal in Finder", "Copy path".
Recommendation

Image tab v2 — toolbar chrome around an existing <img> base

Hand-rolled. The interactions (zoom, pan, fit) are well-trodden territory; CSS transforms + a simple state machine. ~1 day of work. The PM persona benefit: dragging a screenshot from Slack into Duo currently shows a small image; with proper chrome they can zoom into UI mockups without leaving Duo.

SVG sub-case: render with <img> by default (preserves vector). Toggle to "View source" → opens the SVG XML in the JSON-style tier-4 editor (eventually) or markdown editor (today).

3 · Other data primitives (PM persona)

The PM persona test. A PM working with Claude opens these artifacts daily: API responses (JSON), analytics exports (CSV), config files (YAML), log dumps (JSONL), database snapshots (SQLite), wireframes (PNG/SVG), diagrams (Mermaid), specs (Markdown — already covered). The question is: which of these earn dedicated tab kinds, and which are fine as plain-text editor tabs?

Primitive PM use-case Effort Recommendation
JSON / JSONL / HAR Read API responses · debug Claude tool-use traces · explore webhook payloads · paste a Slack thread JSON S ~3d Sprint 11 P0. Tier 3 via @uiw/react-json-view (above).
CSV / TSV Analytics exports · Looker / Mixpanel downloads · spreadsheet from another team M ~5d Sortable table with column-type inference (number / date / string), summary stats footer (count, sum, avg), filter row. Use papaparse for parsing (~10 KB gz, decade-old but stable). Render with TanStack Table.
YAML GitHub Actions configs · k8s manifests · Duo's own packs S ~1d Same JSON-style tree (YAML parses to a JS object, render identically). Could share the JSON tab kind with a format: 'yaml' | 'json' discriminator.
Mermaid / PlantUML Architecture diagrams · sequence diagrams in spec docs · flowcharts S ~2d Mermaid as a TipTap node extension inside the markdown editor (Obsidian-thread Sprint 13). PlantUML deferred — fewer users, server-rendering complications.

Log files App debug logs · session traces · CI build logs · stderr from a long-running command M ~4d Pairs with ENH-082 (Terminal Context Bar) — the natural home for live log streams is INSIDE a terminal pane, not a separate tab. For static log files: render in a JSON-tree-like view if the lines parse as JSON (JSONL); otherwise plain text with timestamp folding. Defer to Sprint 13+.
Spreadsheet (xlsx) Excel files dragged in L ~3w Skip. Numbers/Excel are 30-second OS-level open. Don't compete.
Image v2 Mockups · screenshots from PM tools S ~1d Sprint 13 candidate (above). Toolbar chrome on existing image tab.
Decision · YAML cohabitation
YAML in the same tab kind as JSON (single chrome, format discriminator), or distinct kinds?

YAML and JSON are isomorphic for the tree-rendering case (both are key-value-with-arrays trees) — see the YAML row in the matrix above. One kind: 'json' tab type with a format field could serve both. Alternatively, kind: 'json' + kind: 'yaml' as separate tab kinds keeps the mental model simpler at the cost of duplicated chrome / classifier rules / future per-format quirks.

4 · Roadmap proposal — clustered

Sprint 11 was previously scoped around the Obsidian autocomplete thread (B.2 + B.4 + ENH-105) plus split-view crash work (BUG-091 / 093). Adding the JSON viewer doesn't fit that sprint cleanly — it's its own theme. Two options:

Option A · Push JSON to Sprint 12

  • Sprint 11 stays focused (Obsidian autocomplete + split-view fixes).
  • Sprint 12 becomes "data primitives" theme — JSON tier-3 + CSV table + YAML reuse.
  • Sprint 13 stays as "Obsidian content fidelity" (callouts, math, mermaid) + image v2.

Option B · JSON in Sprint 11, defer Obsidian split

  • Sprint 11 becomes "data primitives + autocomplete" — broader, less coherent.
  • Splits attention between two themes.
  • Worse: the TipTap Suggestion primitive (the architectural piece earning B.2 + B.4 + ENH-105 together) doesn't ship in one PR.
Recommended

Option A — keep Sprint 11 focused on Obsidian autocomplete, file JSON as Sprint 12 anchor

Sprint 12 becomes "data primitives" theme: JSON tier-3 (P0 anchor) · CSV sortable table (P1) · YAML reuse (P2 polish). Sprint 13 rotates to "Obsidian content fidelity + image v2" (callouts + math + mermaid + image toolbar). Backlinks panel + properties panel (originally proposed for Sprint 12) move to Sprint 14. The shift adds a sprint to the Obsidian thread but earns a clean data-primitives sprint that PM users will feel immediately.
