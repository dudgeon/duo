Frontmatter Panel — design options

BUG-139 follow-up Five decisions to refine the panel that shipped Sprint 18 (commit 5f09077).
What this is. BUG-139's v1 shipped with locked-in defaults (one-line rows, compact-JSON for complex values, raw-YAML edit only, always-expanded, simple truncation). Now that you've used it, pick refinements for v1.1. Each card has 2–4 options with visual mockups of the actual panel chrome — radio-pick + free-form notes + the Copy-decisions footer at the bottom.

1 · Row density / key-column layout

Decision 1

How dense should the property rows be?

v1 uses a 100px key column + value in mono on the same line. Long keys ("frontmatterPanelCollapsed") wrap awkwardly; short value-heavy entries (booleans) leave lots of whitespace.

2 · Type-specific value rendering

Decision 2

Should values be styled by type, or stay uniform mono?

v1 renders every value as monospace gray text. Booleans / nulls / dates / arrays could be more legible with type-aware styling — but that's a contract: people see "true" in green and assume it's actionable.

3 · Per-property edit affordance (v1.1)

Decision 3

How should the user edit individual properties (not the whole YAML block)?

v1 only has the "Edit raw" textarea for the whole block. Quick fixes ("flip `published: true → false`") still require opening + editing + saving raw YAML.

4 · Default expanded / collapsed state

Decision 4

Should the panel default to expanded or collapsed for new files?

v1 defaults to expanded. The chevron-state persists per-doc so once you collapse a file's panel, it stays collapsed. But the FIRST open of any new file shows the full panel — even if the file has 12 properties and you mostly want to see prose.

5 · Long-value truncation behavior

Decision 5

What happens when a value is too long to fit one line?

v1 truncates with ellipsis; the title attribute holds the full value (so a hover-tooltip shows it). No click-to-expand. Long descriptions / URLs get clipped.
