"Choose Vault…" should initialize an uninitialized folder

ENH-242 Decisions Spike · 2026-06-28 · pick a radio per card, add notes, hit Copy decisions, paste back
The problem. Today Settings ▸ Default Vault ▸ Choose Vault… opens a folder picker and calls setDefaultVault(picked). If the folder isn't already a vault (no OKF index.md with okf_version, no .obsidian/), that call throws and you get a dead-end dialog: "Not a vault… Ask Claude to run duo vault init there first." The intent: "Choose Vault…" should be able to create a vault from the chosen folder, not just select an existing one — so a non-technical user never has to drop to the CLI.

Current vs intended flow

Now: Choose Vault… → folder picker → setDefaultVault → throws on non-vault → warning dialog "run duo vault init first" → dead end.

Intended: Choose Vault… → folder picker → if it's a vault, set as default (unchanged); if not, initialize it as a vault, then set as default.

Relevant prior art already in the tree (decisions below lean on reusing it):

  • New Vault dialog — File ▸ New Vault… already does pick-location + format (OKF/Obsidian) + name, calling initVault(root, {format, name}) (core/vault/scaffold.ts, renderer/components/NewVaultModal.tsx). Format defaults to OKF.
  • initVault writes only marker/scaffold files (OKF: a root index.md + static-listing seed; Obsidian: .obsidian/ + a .base + README). It throws on an already-a-vault folder unless --force, and never touches your own notes.
  • duo vault default <path> (CLI) fails the same way the menu does today.

Decisions to lock

Decision 1 — Behavior on a non-vault folder

When "Choose Vault…" picks a folder that isn't a vault yet, what happens?

Initializing writes files (markers/scaffold), so this is the core UX call: how much ceremony before we create the vault, and how much control over format/name.

Decision 2 — Default format

Which at-rest format does the init path default to?

OKF (standard markdown relative links, GitHub-portable) vs Obsidian (wikilinks + .obsidian/). If D1 = the modal, this just sets the picker's default selection; if D1 = confirm/auto, it's the format used outright.

Decision 3 — Vault name

What's the new vault's name (title)?

initVault takes an optional name (defaults to the folder basename).

Decision 4 — Non-empty folder / collision guard

What if the chosen folder already has files (e.g. an existing index.md)?

OKF init writes a root index.md as its marker. If a non-vault folder already has an index.md (without okf_version), initializing could overwrite real content. initVault only guards "already a vault", not "file collision".

Decision 5 — Folder inside an existing vault

What if the chosen folder is nested INSIDE an existing vault?

findVaultRoot can detect an enclosing vault. Nesting a vault inside a vault is generally an anti-pattern (ambiguous link resolution, double-indexing).

Decision 6 — CLI parity

Should duo vault default <path> gain the same init-on-missing?

CLI-parity rule (#4): if the human can create-on-choose from the menu, the agent should be able to from the CLI. Today duo vault default <non-vault> throws like the menu did.

Recommended bundle (if you just want to say "yes, do the sensible thing")
D1 reuse-modal · D2 OKF · D3 basename-editable · D4 safe-refuse-collision · D5 set-enclosing · D6 add-init-flag. Net: "Choose Vault…" (likely relabeled "Choose or Create Vault…") on a non-vault folder opens the New Vault dialog prefilled (OKF, basename), refuses to clobber an existing index.md, sets an enclosing vault instead of nesting, and duo vault default --init gives the agent the same power.
