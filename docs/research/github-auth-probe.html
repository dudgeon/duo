GitHub auth probe — which method works on this Mac?

ENH-149 Status: open / awaiting owner walk on enterprise machine · filed 2026-05-12 · author: Claude
What this is. A walk-through for testing every plausible GitHub-auth path on a Mac so Duo can pick a sensible default for its upcoming File > Clone… / duo clone flow. The target user is a beginner on an enterprise-managed machine. The goal: a one-time browser SSO handoff, no PAT / no SSH key setup, ideally with no admin install and no Homebrew dependency. Walk this on your work machine, mark which methods worked, hit Copy decisions, paste back to Claude.

§ 1 · Why this matters (and the persona)

Duo's persona is a beginner who's paired with Claude Code. Cloning a repo from a URL has to be a no-think operation — open menu, paste URL, click sign-in, done. The two friction points on enterprise Macs are usually:

  • No Homebrew. Lots of corp Macs forbid brew (no admin) or have it installed in the wrong place / wrong arch.
  • SAML-SSO orgs. The token must be authorized for the org via a SAML browser handoff, not just account-authenticated.

So the playground asks: what's the cheapest, most-likely-to-work-on-a-stock-corp-Mac path?

§ 2 · One-shot environment probe

Open a Duo terminal in any folder on the work machine and paste this whole block. It does not change anything — just reports what's installed and how git is currently set up. Copy the output into the textarea below; Claude will read it back from the Copy-decisions payload.

Paste this into a Duo terminal

No changes, no installs. Safe to run on a managed machine.
{
  echo "=== HOST ==="
  sw_vers | sed 's/^/  /'
  uname -m | sed 's/^/  arch: /'
  echo "  shell: $SHELL"
  echo "  PATH (entries):"; tr ':' '\n' <<< "$PATH" | sed 's/^/    /'

  echo
  echo "=== gh CLI ==="
  if command -v gh >/dev/null 2>&1; then
    echo "  path: $(command -v gh)"
    gh --version 2>&1 | sed 's/^/  /'
    echo "  auth status:"; gh auth status 2>&1 | sed 's/^/    /'
  else
    echo "  not installed"
  fi

  echo
  echo "=== git ==="
  git --version | sed 's/^/  /'
  echo "  credential.helper:"
  git config --get-all credential.helper       2>&1 | sed 's/^/    global: /'
  git config --get-all --system credential.helper 2>&1 | sed 's/^/    system: /'
  echo "  github-specific helpers:"
  git config --get-all credential."https://github.com".helper 2>&1 | sed 's/^/    /'

  echo
  echo "=== SSH ==="
  if [ -d "$HOME/.ssh" ]; then
    echo "  ~/.ssh exists; keys:"
    ls -1 "$HOME"/.ssh/id_* 2>/dev/null | sed 's/^/    /' || echo "    (no id_* keys)"
    echo "  agent (ssh-add -l):"
    ssh-add -l 2>&1 | sed 's/^/    /'
    echo "  reach github (5s timeout):"
    ssh -o BatchMode=yes -o ConnectTimeout=5 -T git@github.com 2>&1 | sed 's/^/    /'
  else
    echo "  ~/.ssh does not exist"
  fi

  echo
  echo "=== Git Credential Manager ==="
  if command -v git-credential-manager >/dev/null 2>&1; then
    echo "  path: $(command -v git-credential-manager)"
    git-credential-manager --version 2>&1 | sed 's/^/  /'
  else
    echo "  not installed"
  fi

  echo
  echo "=== Homebrew ==="
  if command -v brew >/dev/null 2>&1; then
    echo "  path: $(command -v brew)"
    brew --version 2>&1 | head -1 | sed 's/^/  /'
  else
    echo "  not installed"
  fi
} 2>&1

§ 3 · Method cards — try each, mark which work

Try the methods in roughly the order below. Stop as soon as one works cleanly — you don't have to test all five. The earlier methods are the ones we'd prefer to default to. For each method: read the steps, run the probe in a terminal, mark the result, jot what happened.

A gh CLI installed via Homebrew + gh auth login --web

Easiest if brew exists

The baseline on your work machine (you confirmed brew install gh already worked there). One-time browser handoff stores an OAuth token in macOS Keychain; git push Just Works afterward because gh registers itself as the credential helper.

  1. Authenticate: gh auth login --web → pick HTTPS → press Enter → it opens a browser to github.com/login/device with a code → click Authorize.
  2. If your work GitHub org uses SAML SSO: after authorizing, open https://github.com/settings/tokens → find the new gh CLI token → click "Configure SSO" → authorize for your org.
  3. Run the probe below to confirm.
Probe
gh auth status
gh repo clone dudgeon/duo /tmp/duo-probe-A
ls /tmp/duo-probe-A/.git && rm -rf /tmp/duo-probe-A

Expect: "Logged in to github.com as <you>" + clone completes with no prompt.

B gh CLI installed via signed .pkg from github.com/cli/cli/releases (no brew)

Best for clean machines

The official gh release ships a signed + notarized .pkg installer that drops /usr/local/bin/gh and a man page. No Homebrew, no Xcode CLT needed. On most managed Macs this installs without admin password because it's a per-user pkg under /usr/local. After install, same gh auth login --web handoff as A.

  1. Find the latest release page (we'd open this in the Duo browser pane): https://github.com/cli/cli/releases/latest.
  2. Download the gh_*_macOS_arm64.pkg file (or _amd64 on Intel — the probe in § 2 tells you which arch).
  3. Double-click the .pkg → Installer.app walks you through it. If your machine rejects the install with "needs admin," try the tarball alternative in the details block below.
  4. Run gh auth login --web as in method A.
Probe
# In a fresh terminal (so PATH picks up /usr/local/bin):
gh --version
gh auth status
gh repo clone dudgeon/duo /tmp/duo-probe-B
ls /tmp/duo-probe-B/.git && rm -rf /tmp/duo-probe-B

Expect: gh version reports + clone succeeds. If gh: command not found, the PKG installed somewhere not on PATH — check /usr/local/bin/gh and /opt/homebrew/bin/gh.

Fallback: tarball (no admin install needed)

If the PKG is blocked: download the gh_*_macOS_arm64.zip from the same releases page, unzip, and copy bin/gh into a folder you own (e.g. ~/.local/bin/gh). Add that folder to PATH via ~/.zshrc. Same gh auth login --web flow afterward.

mkdir -p ~/.local/bin
cd ~/Downloads && unzip gh_*_macOS_arm64.zip
mv gh_*/bin/gh ~/.local/bin/
echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.zshrc
exec zsh   # reload PATH
gh --version

C Git Credential Manager (no gh dependency)

Plain git, OAuth in browser

GCM ships an OAuth-in-browser flow that triggers when you git clone https://<authed-repo>. No gh binary needed. Useful if gh is blocked entirely. Apple's bundled git uses osxkeychain by default, NOT GCM — so this typically requires installing GCM separately.

  1. Install GCM. Options, easiest first: brew install --cask git-credential-manager (if brew exists), OR download the signed PKG from git-ecosystem/git-credential-manager/releases/latest (look for gcm-osx-*.pkg).
  2. After install: git-credential-manager configure — this rewrites your global git config to route GitHub URLs through GCM.
  3. Probe by cloning a private repo over HTTPS — GCM should pop a browser window the first time.
Probe
git-credential-manager --version
git config --get-all credential.https://github.com.helper
git clone https://github.com/dudgeon/duo /tmp/duo-probe-C
ls /tmp/duo-probe-C/.git && rm -rf /tmp/duo-probe-C

Expect: browser pops up on first clone, you click Authorize, clone completes. Subsequent clones use the cached token silently.

D SSH keys (corporate-issued or self-generated)

Setup-heavy, but already common at work

Lots of enterprises pre-provision SSH keys; the user may already have one. Once ~/.ssh/id_* exists and is registered on github.com, git clone git@github.com:owner/repo works with no token, no browser. SAML-SSO orgs require an extra "Authorize this key for <org>" step in GitHub settings.

  1. The § 2 probe showed whether ~/.ssh/id_* exists and whether ssh -T git@github.com recognizes you. If both are good, you're probably done.
  2. If no key: ssh-keygen -t ed25519 -C "you@work.example.com" → press enter at each prompt → copy ~/.ssh/id_ed25519.pub to github.com/settings/keys.
  3. For SAML-SSO orgs: at https://github.com/settings/keys, click "Configure SSO" next to the key and authorize each org you need.
Probe
ssh -T git@github.com   # expect: "Hi <you>! You've successfully authenticated..."
git clone git@github.com:dudgeon/duo /tmp/duo-probe-D
ls /tmp/duo-probe-D/.git && rm -rf /tmp/duo-probe-D

Expect: ssh test prints "Hi <username>!", clone succeeds. If clone hits "Permission denied (publickey)" but ssh -T worked, it's a SAML-SSO authorization issue, not a key issue.

E Plain HTTPS + osxkeychain helper (zero-setup baseline)

Works only for public repos / PAT

Apple's bundled git registers the osxkeychain credential helper by default. Cloning a public repo over HTTPS needs no auth at all. Private repos prompt for username + password, but GitHub disabled password auth in 2021 — so on a fully clean machine, this path requires a PAT (Personal Access Token). The owner explicitly does NOT want this path; we include it as the "what does zero setup give you" baseline.

  1. No install needed. The probe just tries a clone.
  2. If asked for password: STOP. We don't want the user touching PATs.
Probe
git clone https://github.com/dudgeon/duo /tmp/duo-probe-E      # public — should just work
ls /tmp/duo-probe-E/.git && rm -rf /tmp/duo-probe-E

Public repos: succeeds with no prompt. Private repos: prompts for username/password — failure case.

§ 5 · Future-scope sketch — integration config-checker manifest

The owner raised a second topic: enterprise distro packs should be able to declare which integrations matter (gh, brew, Jira PATs, Confluence PATs), and Duo should give pack authors a low-effort way to ship "is this set up?" probes — without Duo managing the secrets themselves. This § sketches the shape; not committing to it yet.

Proposed pattern — integrations[] in PACK.json + per-integration probe scripts

Each pack's PACK.json grows an integrations array. Each entry names a small executable probe that the pack ships, plus the env / config keys the integration expects to exist. Duo runs the probes on demand (e.g. as part of duo doctor) and renders a status panel. Secrets never touch Duo.

{
  "name": "acme-corp-pack",
  "integrations": [
    {
      "id": "github",
      "label": "GitHub access for our org",
      "probe": "checkers/github.sh",
      "required": true,
      "setupDoc": "docs/setup/github.html"
    },
    {
      "id": "jira",
      "label": "Jira ACME-INC instance",
      "probe": "checkers/jira.sh",
      "required": false,
      "needsEnv": ["JIRA_API_TOKEN", "JIRA_BASE_URL"],
      "setupDoc": "docs/setup/jira.html"
    },
    {
      "id": "confluence",
      "label": "Confluence wiki",
      "probe": "checkers/confluence.sh",
      "required": false,
      "needsEnv": ["CONFLUENCE_API_TOKEN", "CONFLUENCE_BASE_URL"],
      "setupDoc": "docs/setup/confluence.html"
    }
  ]
}

Probe contract. A probe is any executable (shell script, Node, Python, compiled binary) the pack ships at the declared path. Duo runs it and reads JSON from stdout:

{
  "status": "ok" | "missing" | "misconfigured" | "unreachable" | "blocked",
  "summary": "Authenticated as geoff@acme.com",
  "detail": "Token has scopes: repo, read:org. SAML SSO authorized.",
  "fixDoc": "docs/setup/github.html#sso"
}

What Duo provides (the framework).

  • duo doctor --integrations — runs every installed pack's probes, prints a status table.
  • A small Doctor panel surface (canvas-rendered) that lists the integrations with their statuses + "open setup doc" links.
  • A pack-builder skill helper: /pack-builder add-integration <id> scaffolds a probe stub, adds the manifest entry, and links the setup doc.
  • An integrations field in installed.json recording last-run status per integration (for fast Doctor-panel rendering without re-running probes on every open).

What Duo deliberately doesn't do.

  • Store, prompt for, or rotate secrets. Secrets live in the user's existing tools — macOS Keychain, 1Password, an env-var manager, whatever IT mandates.
  • Phone home with integration status. Probes run locally; results stay local.
  • Ship default probes. Each pack ships its own; acme-corp-pack's GitHub probe is different from beta-cohort-pack's.

Sequencing relative to this playground. The auth-probe playground is a manual one-off — the owner walks it once on the work machine and we lock in a default. The config-checker manifest is the generalization of that playground: instead of the owner manually checking gh / GCM / ssh, a pack author writes a probe script that does it once and ships it. The two are independent but related — file the config-checker as a separate ENH (ENH-150, sketched below) once the auth probe answers Q1 above.
