File version history — the user-facing surface

ENH-221 Decision Engine + CLI landed (branch claude/enh-221-file-history). This decides the UI. · 2026-06-19
What this is. The version-history engine is built and on its branch: every Duo-mediated save is snapshotted into a durable, append-only store, reachable today via duo history list / show / restore. But a person can't see it yet — there's no UI, so the original complaint ("I can't undo / manage my changes") isn't solved for an actual user. This playground mocks up four candidate surfaces and asks you to pick one + a few interaction details. Pick below, hit Copy decisions, paste back to Claude. The chosen surface gets built + verified live (Electron) next.

What every version of this shows

All four surfaces render the same data — a reverse-chronological timeline of snapshots, each tagged by who wrote it. The differences are where it lives and how much room it gets for a diff.

You — your own saves (autosave checkpoints) Agent — a Claude / duo doc write Restored — a roll-back point

Decisions

Decision 1 · Primary surface

Where does version history live?

The one we design + build + live-verify first. Others can follow.

Decision 2 · What "Restore" does

When the user restores an older version, what happens to the current content?

All routes are safe (the current state is itself a snapshot, so a restore is reversible). This is about the gesture.

Decision 3 · Row content

How much does each timeline entry show?

More detail = more scannable, but a busier rail.

Decision 4 · Diff display

How do we show what changed in a selected version?

Drives how much diff machinery the first build needs.

Context I'm carrying into this (engine facts + already-deferred items)
  • Already built (this branch): the store (~/.claude/duo/file-history/), capture on every Duo-mediated save (fire-and-forget, zero added save latency), 90s autosave coalescing, and duo history list/show/restore. The UI sits on top of these — no engine changes needed for A/B/C/D.
  • Restore is always safe regardless of D2: it writes through the normal save path, so the pre-restore state is itself snapshotted and an open editor reconciles via the watcher.
  • Still deferred (separate from this UI decision): capturing external / raw-Edit writes that bypass Duo (needs a watcher-side capture); an on-open baseline snapshot; duo history diff on the CLI.
  • CLI parity: whatever the UI can do, the CLI already mostly mirrors (list/show/restore). A UI "diff" would want a matching duo history diff.
