Off Electron? Stack alternatives & the Claude-design loop

Research · ENH-238 2026-06-28 · Duo v0.13.1 · owner-decision artifact
What this is. You asked: should Duo move off Electron — native macOS, a different React approach, or a hybrid — and would that buy a tighter feedback loop with Claude Design? This evaluates each candidate against Duo's real lock-in points (measured from the codebase) and against the thing you actually want (the design round-trip). Decisions to record are at the bottom.

The short version

Your React isn't the blocker — its packaging is. Duo already renders in React (~53k LOC, 237 components). The Claude-design loop is weak not because you lack React, but because that React only runs inside Electron, where there's no component preview and Claude can't even screenshot the dev build. The fix is to let the existing UI render in a plain browser — not to change stacks.

Going native would make the design loop worse, not better. SwiftUI / React-Native-macOS render to AppKit, not the DOM. There's no browser preview, Claude is far weaker at them than at React-web, and Claude Design's design-system import targets web components. Native optimizes the axis you're not complaining about (polish) at the direct expense of the one you are.

Tauri is a footprint play that fights Duo's reason for existing. Its macOS webview is WebKit (WKWebView), which has no Chrome DevTools Protocol — and duo open/eval/dom/inspect are all CDP. You'd lose the browser-control premise or have to bundle Chromium anyway (erasing the win).

Recommendation: don't migrate. Spend ~2–4 weeks unlocking the loop you already have (component preview + a browser-runnable renderer + a @duo/ui design kernel). Keep one strategic hedge alive (engine/shell split) only if shell-portability ever becomes a real goal.

1. The reframe: what actually blocks the Claude-design loop

Claude Design (Anthropic Labs) is real and it's what you're reaching for: it imports a design system by reading your codebase + design files (colors, typography, components), builds against it, auto-corrects against the system, then ships a "Handoff to Claude Code" bundle that lands the change in your repo. The iteration loop — generate → render → observe → correct — is its core.

None of those three stages is gated on having React. Duo has React. They're gated on three things, all fixable without touching the stack:

What the loop needsDuo todayWhy it's blocked
Render a component in isolationMissingNo Storybook / Ladle / standalone renderer entry — the UI only boots inside the full Electron app.
Let Claude observe the renderBrokencomputer-use can't reach the dev Electron build (known; screenshots return wallpaper). So even the full-app loop is unobservable to the agent.
Import the UI as a design systemPartialTokens live in duo-atelier.css + Tailwind; components aren't extracted into an importable, previewable kernel. Import fidelity is highest against standard web/React/Tailwind — which Duo mostly is.

So the design-loop goal is an argument for keeping a web/DOM React UI and against native — and the actual work is preview infrastructure, not migration.

2. Does Claude Design require React? (the honest answer)

Not strictly — but it strongly favors a web / DOM UI, and React specifically is the highest-fidelity target. Three reasons, each independent:

  • Training depth. Claude's strongest UI idiom is React + Tailwind (+ shadcn) — that's what Artifacts and the web-artifacts toolchain are built on. Output quality on SwiftUI / Flutter / RN-macOS is materially lower.
  • Observability. The generate→screenshot→iterate loop needs a renderable surface the agent can capture. A browser DOM is trivially screenshot-able and previewable; AppKit / Flutter's own canvas is not, in the same agent-driven way.
  • Design-system import + round-trip. Claude Design reads component libraries and auto-corrects against them; the handoff lands via Claude Code into your repo. Both ends are strongest when the components are web components. SwiftUI has no equivalent import path today.

Conclusion: a web React UI is the best possible substrate for this loop. Duo already has it. The strategic mistake would be leaving it for native.

3. Duo's three hard requirements (what any stack must satisfy)

Measured from the codebase — these are the constraints that decide feasibility:

  • A CDP-controllable embedded Chromium. The whole premise — "Claude Code reads & drives the browser" — rides Chrome DevTools Protocol through Electron's webContents.debugger (electron/cdp-bridge.ts, ~2,150 LOC). duo open / eval / dom / inspect / selection / screenshot / console / network are all CDP. This is the single biggest lock-in. Only Electron (or raw Chromium/CEF embedding) provides it. WebKit webviews do not.
  • node-pty terminals. Node runtime in the main process (core/pty-manager.ts). Re-implementable per platform (Rust portable-pty, Swift openpty/NSTask) but it's real work plus a new IPC contract.
  • The local Unix-socket CLI bridge. The duo verb surface (60+ commands). The protocol is portable JSON, but every handler currently routes into Electron-backed systems.

The renderer is the most portable layer (~50% of components are pure presentational). The main process (~20k LOC across electron/) is the least portable — and ~50–60% of that is the CDP+WebContentsView browser engine that has no equal outside Chromium.

5. Per-option detail

A · Stay Electron, unlock the loop Recommended ~2–4 wk · reversible

Add a component-preview harness (Storybook or Ladle) + a browser-runnable renderer mode with the window.electron bridge mocked, and extract the pure presentational components into a @duo/ui package that runs in both Electron and a plain browser.

  • Gets the tight loop: Claude edits a component, HMR renders it in a browser, screenshots + iterates — no Electron boot, no blind dev build.
  • Makes Claude Design sing: @duo/ui + the Atelier tokens are exactly the importable design system the round-trip wants.
  • Zero loss: CDP browser control, terminals, socket CLI, distribution — all untouched.
  • Doesn't reduce Electron's memory/binary footprint (but that isn't the stated pain).

B · Tauri (Rust + system WebKit) Footprint only ~8–12 wk · high risk

  • ~3–10 MB binaries vs ~100 MB+; much lower idle memory; Rust backend; keeps the React frontend.
  • macOS webview = WKWebView (WebKit), no CDP. Duo's browser-control premise breaks: you'd rebuild it on WKWebView's async JS-message bridge (no DOM/Network/Accessibility protocols) — strictly weaker — or bundle CEF and lose the size win.
  • Rewrite main.ts (~5.8k LOC) + socket handlers in Rust glue, node-pty → portable-pty, IPC model swap, updater + menus.
  • Only sensible if you re-scope Duo to not need CDP-grade browser control — which is most of why Duo exists.

C · Native macOS (Swift / SwiftUI / AppKit) Against the goal 6–12 mo · extreme risk

  • Best performance, smallest footprint, native fidelity, Sparkle updates, deepest macOS integration.
  • Degrades the design loop hardest — Claude weak at SwiftUI, no browser preview, no Claude-Design import target. Directly contradicts the request.
  • ~80%+ rewrite; the 53k-LOC React investment is discarded; browser pane → WKWebView (no CDP) or embedded CEF.

D · React Native macOS Worst of both 4–8 mo · high risk

  • React-the-language, but renders to AppKit — no DOM. You pay native rewrite cost and don't get the browser-preview/screenshot loop. Embedded browser + CDP + node-pty still break.

H · Hybrids worth keeping on the table

  • H1 — Design-kernel extraction (pairs with A, recommended): the structural form of A. @duo/ui becomes a permanent dual-target package; the design loop is a standing capability, not a one-off. ~+1–2 wk over A.
  • H2 — Engine/shell split (strategic hedge): formalize CDP + pty + socket into a headless "Duo engine" so the UI shell could later swap (Electron → Tauri → native) without touching the engine. Big refactor; justified only if shell-portability becomes a real goal. Keep as an option, not a now-move.
  • H3 — Tauri-shell + CEF "someday": if footprint ever becomes the dominant pain, a Tauri shell embedding Chromium for the browser pane could shrink app chrome while keeping CDP. High effort; revisit only on a footprint trigger.
Measured lock-in numbers (from the codebase scan)
  • 110k LOC total · renderer 53k (237 .tsx) · core 27k · electron 20k · shared 6k · cli 3.7k.
  • 7 files import from electron; the heavy ones are main.ts (5.8k), cdp-bridge.ts (2.15k), browser-manager.ts (1.5k), preload.ts (1.1k).
  • Browser control = WebContentsView (browser-manager.ts:298) + CDP via webContents.debugger.attach('1.3') (cdp-bridge.ts:1180). No equivalent on WebKit webviews.
  • Renderer portability ≈ 50% pure presentational (survives any web stack) / ~48% coupled to window.electron IPC (needs a bridge abstraction).
  • No existing Storybook / Ladle / standalone renderer entry — the gap that A fills.
