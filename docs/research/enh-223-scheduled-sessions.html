Scheduled Claude sessions (cron) — plan & decisions

Decision round ENH-223 draft for sign-off 2026-06-20 · run a Claude Code command on a schedule, inside Duo, interactively
What this is. A plan to let Duo create, view, and manage scheduled ("cron") jobs that launch Claude Code in a project — starting with interactive (non-headless) sessions only. A job is a saved recipe: a working directory, a Claude command you compose, a periodicity, and whether each run continues the same session or starts a fresh one. Duo's scheduler fires the job while Duo is running, opens a real terminal tab seeded with your initial instruction, and then hands control to you — Duo only ever does session start + initial instruction; all actual execution stays interactive.

How to use this page. §0–§3 establish the shape (the hard constraint, the locked answers you already gave, the create flow, the Home surface). §4 holds the open decisions — pick a radio per card, add notes, hit Copy decisions at the bottom, paste back to Claude. Recommendations are tagged.

0The one hard reality that shapes everything

Interactive runs require Duo to be open. Because every run is a real interactive Claude Code TUI session inside a Duo terminal tab (no headless -p), there is nothing to run into when the app is closed or the Mac is asleep. This is the opposite of a system crontab, which runs headless daemons regardless. So Duo's scheduler is an in-app timer that only fires while a window is open, and the honest framing for v1 is: "these run when Duo is running."

Two future paths to true unattended runs are logged, not built (see §6): (a) a system scheduler (launchd) that launches Duo at the scheduled time, and (b) the eventual headless -p path — which is exactly what the feature flag below gates off until it's deliberately enabled. v1 is interactive, app-open-only, on purpose.

4Open decisions

Ten calls. Each shapes the build; recommendations are tagged. The four locked items in §1 are not repeated here.

Decision 1 · Storage shape & scope

Where do job definitions live, and are they app-global or per-window?

CLAUDE.md #12 (no-sidecar) allows Duo-owned concepts the external system doesn't track — a schedule is exactly that. The question is which file, and whether a job belongs to a window or to the app.

Decision 2 · Initial-instruction delivery

How is the user's instruction handed to Claude at run time?

"Use Claude Code primitives where possible." Claude Code accepts a positional prompt in interactive mode (claude "do the thing") — it seeds the first message and stays interactive. The alternative is to spawn a bare shell and synthesize keystrokes.

Decision 3 · Same-session-vs-fresh semantics

What does "continue same session" actually resume — and what if it's gone?

"Fresh" is easy: a new session per run (claude "…"). "Same" needs a session id to resume. Per ENH-183 D9, Duo may store a pointer captured on real evidence — so a job records the uuid of the session its last run created, then resumes that. The edge is when that session no longer exists.

Decision 4 · Headless (-p) enforcement

How strictly does Duo prevent a job from running headless?

The constraint is firm: -p/--print is gated behind a feature flag that defaults OFF and isn't in the UI. The question is how the gate is enforced on the command string (and which other non-interactive triggers count).

Decision 5 · Missed-run default

Out of the box, what happens to a run missed while Duo was closed?

You chose "preference (global + per-job)." This sets the default the preference starts at. Catch-up collapses multiple missed occurrences into one run.

Decision 6 · Home surfacing layout

How do jobs render on Home — and where do orphan-project jobs go?

You said inline under the parent project, aggregated when the project isn't visible. This pins the exact treatment. Home today shows ~2 hero projects + a spine; not every project with a job is on screen.

Decision 7 · Create / manage entry points

Where can a human (and the agent) create and manage jobs?

CLI parity is a hard rule (CLAUDE.md #4): whatever the human can do, the agent must do from the CLI. The question is the UI surface set for v1.

Decision 8 · Scheduler engine

How does Duo compute next-fire times — dependency or hand-rolled?

The app is currently pure setTimeout with no cron library. Presets are trivial; the advanced cron-expression field needs a parser + human-readable preview.

Decision 9 · "Waiting on user action" tab indicator

Do we build the attention badge now, and how does it detect "waiting"?

You flagged this as a good opportunity — a tab badge when a session (cron or normal) is waiting on you. The clean primitive: a Duo-managed Stop hook (fires when Claude finishes a turn and waits for input) — plus a permission-request signal — that writes to Duo's existing Unix socket (the same channel the CLI uses), correlated back to the tab by session id. Terminal-bell capture is a cruder fallback.

Decision 10 · Run landing window (multi-window)

Which window receives a run, and what if no window is open?

Jobs are app-global (D1), but runs need a window to land in. Duo's default resolution is the lowest-id "primary" window, by identity.

Logged future ENHs (not in this scope):
  • ENH-222 — System-scheduler launch. A launchd agent that launches Duo at a job's time so runs fire even when the app was closed. The honest path to "unattended-ish" without going headless.
  • ENH-225 — "Waiting on user action" tab indicator (Decision 9) — built on Claude Code's Notification/Stop hooks; applies to all sessions.
  • Headless (-p) runs. The whole point of the default-off feature flag: a future, deliberately-enabled mode where a job can run autonomously start-to-finish. Off until designed (permissions, safety, output capture).
  • Full run history / log view — beyond v1's last-run-+-status.
Open questions tracked, not forgotten
  • Permission prompts during a run. An interactive run will hit tool-permission prompts — that's expected (it's interactive), and the D9 badge is how you find it. No auto-approve in v1.
  • Overlapping fires. If a job's previous run tab is still open/active when the next fire arrives — skip, queue, or open a second tab? (Proposal: skip with a "still running" note.)
  • Timezone / DST — presets are local-time; the parser choice (D8) determines DST handling for advanced expressions.
  • Sleep/wake. A fire whose time passed during system sleep is treated like a while-closed miss (D5) once the app wakes.
  • Env / shell. Runs inherit the same PTY env stamps as any Duo terminal (DUO_SESSION, DUO_WINDOW, etc.).
