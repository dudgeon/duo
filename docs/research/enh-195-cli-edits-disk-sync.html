The one root cause

Duo keeps the editor buffer in sync with disk by guessing whether a disk change is "our own save echoing back" or "a real external edit." It guesses by comparing disk bytes against the editor's serialized view of the document through a hand-tuned normalizeForEchoCompare() — a regex stack grown one quirk at a time (BOM, CRLF, trailing-ws, soft-breaks, HTML entities, autolinks). That single guess is behind all three symptoms:

   external write ───▶ │   "echo or real edit?"  guess              │
   (Claude's Edit,     │   normalize(disk bytes) vs normalize(      │
    git, cloud sync)   │                 editor's SERIALIZED view)  │

                          │                 │                  │
              guesses "real"        guesses "echo"      can't be asked

BUG-166 (2026-05-26) added a byte-exact disk snapshot (lastSeenDiskBodyRef) that mostly fixed the markdown false-positive — but the fix is incomplete: the fallback path still compares against the serialized view, the HTML canvas never got the byte-exact ref at all, and the sanctioned CLI write path (applyDocWrite) never registers its echo — so even a correct duo doc write can false-positive in the autosave window ("the false positive right after I applied a change"). That last bit is why goals 1 and 3 are entangled, exactly as you suspected.

Why Claude reaches for the filesystem (goal 1 is a capability gap, not just nagging)

  • No surgical markdown verb. duo doc write --replace-selection targets your cursor (the agent can't set it); --replace-all resends the whole doc. "Change line 12 of an open .md" has no good CLI path → Claude uses Edit. (The HTML canvas does have surgical duo html set/replace/append.)
  • JSON/YAML has no edit verb at all.
  • Claude can't even ask "is this file open in Duo?" The skill tells it to check duo nav state → working tabs — but that field doesn't exist. No verb lists open file tabs.
  • The "never Write/Edit an open file" rule lives only in the on-demand skill + subagent. The always-loaded priming.md omits it and actively frames duo edit as an open/read substitute → "open with duo, edit with Edit" = the exact bug.

The 4 forks I need you to decide

Decision 1 · Goal 1 capability

How much new CLI edit-surface should I build?

The capability gap is the real reason Claude uses Edit. More surface = more plumbing (each verb spans cli/duo.ts + SKILL.md + agents/duo.md + CLI-COVERAGE.md + the renderer handler), but directly removes the incentive to bypass the editor.

Decision 2 · Goal 1 enforcement

How hard should Duo push Claude off the filesystem for open files?

Guidance alone is weak (the skill may not even load on a plain "edit this file" request). A PreToolUse hook catches it mechanically — but hooks add latency to every edit and live in your settings.json.

Decision 3 · Goal 2 responsiveness

When disk changes externally and your buffer is clean, how should the reload feel?

Today a clean-buffer external edit the normalize stack deems "cosmetic" (rewrapped paragraph, CRLF, <↔&lt;, an added autolink) is silently swallowed — the editor never reloads. Since the buffer is clean you lose nothing by reloading; the only real cost of always-reloading is disorientation ("the doc moved under me — what changed?"). A change-highlight removes exactly that cost — and the wash layer already exists (JustAdded, used today for CLI writes), so it's cheaper than it sounds.

If you pick highlight — the design defaults I'd use (override in notes)
  • Lifetime: the wash survives the reload and clears on your first doc-changing edit (your "until buffer changes"). Scrolling/clicking don't clear it.
  • Additions + changes washed; deletions get a thin left-margin tick (you can't wash absent text). Say the word if you'd rather ignore deletions entirely.
  • Granularity: inline word-level ranges from the diff (tracked-changes feel), not whole-paragraph blocks.
  • Big rewrites: if one external write changes more than ~half the doc, skip the wash and show a one-line "reloaded from disk" note instead — washing everything is just noise.
  • Multiple reloads while away: highlight = diff vs the last version you actually saw, recomputed each reload (two agent writes accumulate, not just the latest).
  • Off-screen changes: v1 highlights in place; a "↕ N changes from disk" jump-pill is an easy fast-follow.
  • Treatment: the same accent wash CLI writes use, but steady (no 6s fade) until cleared.
Decision 4 · Goal 3 UX (touches a lock)

When an agent edit lands on a file you have unsaved edits in, what happens?

Today: the "changed on disk — Reload / Keep mine" banner (locked by BUG-085). Once edits route through verbs (echo-clean) + A3 lands, this becomes rare — it only fires on a genuine raw-filesystem divergence. Changing the banner itself means revisiting a locked UX.

Decision 5 · Architecture (you raised this — revisits a lock)

Should the watch/echo/conflict machinery be one shared primitive, or stay mirrored across the two surfaces?

The DECISIONS.md lock keeps the editing surfaces parallel — TipTap-markdown vs "the canvas IS the page" contentEditable — for sound reasons (PRD-H1: wrapping the canvas in TipTap would schema-rewrite hand-authored HTML). But that rationale is entirely about the editing contract; it never really covered the reconciliation machinery (watch disk → echo-vs-external → reload-or-banner), which is the same state machine on both surfaces and differs only in injectable bits (serialize, reload, normalize, dirty-test, the canvas anchor-loss banner). Two divergent copies is exactly why BUG-166's byte-exact fix landed in markdown but silently skipped the canvas. This reshapes how Tier A (A1/A2/A4/A5) is built.
