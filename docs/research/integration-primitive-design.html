Integration primitive — design playground

ENH-150 v2 Status: open / awaiting owner walk before intent lock · filed 2026-05-13 · supersedes the § 5 sketch in github-auth-probe.html
What this is. A complete shape proposal for the integration primitive Duo will ship for distro packs — covering what lives in the main framework, what pack builders supply, how the two compose, and how it surfaces to the user (Doctor panel + inline pointers + CLI). Mockups are grounded in Duo's actual app palette (same Atelier tokens). Four shape decisions are open at the bottom; walk through and pick before I file the concrete ENHs and start the build.

§ 1 · The principle (refined)

After your enterprise walk and pushback on my "never install" over-correction, the principle that holds across every Mac (personal, enterprise self-service, locked-down) is:

Detect → validate → guide → optionally run (with consent). Duo never invents an install command. It runs probes the pack author shipped. When a probe says "missing," it surfaces the remediation steps the pack author declared. Those steps come in two flavors: tell (instructions the user follows) and run (a pack-authored command Duo can execute on the user's behalf with explicit confirmation). The framework is the engine; the pack is the content. Switching from "personal Mac" to "enterprise Mac" is a pack swap, not a code change.

This keeps your three boundary cases working without code branches:

  • Personal Mac — default Duo pack ships standard public-internet install commands (e.g. /bin/bash -c "$(curl -fsSL …install.sh)" for brew). User confirms each run step.
  • Enterprise Mac — IT-supplied pack overrides those entries. Its brew install step might be open "macappsto://app/com.acme.SelfService" or simply a tell step pointing at the org's catalog. gh's install step might be brew install gh (because the IT pack knows brew is the right path) or another catalog entry.
  • Locked-down Mac — pack ships only tell steps. Duo runs nothing; it surfaces the org's runbook URL.

§ 2 · Architecture — two layers

┌──────────────────────────────────────────────────────────────────────────┐ │ FRAMEWORK (ships in Duo main) │ │ · Manifest schema: PACK.json `integrations[]` │ │ · Probe runner — executes probe scripts, reads JSON status │ │ · Setup-chain walker — resolves `depends`, orders steps │ │ · UI: Doctor panel (canvas surface) + inline pointer strip │ │ · CLI: `duo doctor` / `duo doctor --integrations` / `duo doctor fix ID` │ │ · Trust model: probe sandbox + per-run confirmation prompts │ └──────────────────────────────────────────────────────────────────────────┘ ▲ ▲ calls probes│ │renders runs steps │ │status + actions ▼ ▼ ┌──────────────────────────────────────────────────────────────────────────┐ │ PACK CONTENT (ships per pack author) │ │ · `integrations[]` array in PACK.json │ │ · `checkers/.sh` probe scripts (the pack ships them) │ │ · `setupSteps[]` declarations — `run` / `tell` / `depends` │ │ · Setup docs (HTML / markdown) the `tell` steps link to │ │ · Optional override of another pack's integration (priority field) │ └──────────────────────────────────────────────────────────────────────────┘ Default Duo pack ships its own integrations[] entries (gh, brew). Enterprise packs override them. Lock semantics decided in § 8 Q2.

The framework is content-agnostic: it knows how to ask a probe "are you OK?" and how to walk a remediation chain, but it doesn't know what Homebrew is, what gh is, or how to install either of them. Every concrete install command lives in pack content.

§ 3 · What ships in Duo main (the framework)

3a · PACK.json schema additions

The PackManifest gets one new optional top-level field: 

// shared/types.ts — additions
export interface PackManifest {
  // ...existing fields (name, version, defaults[], etc.)...
  integrations?: PackIntegration[];   // NEW
}

export interface PackIntegration {
  id: string;                          // "github", "brew", "jira", etc.
  label: string;                       // "GitHub CLI" — shown in Doctor panel
  priority?: number;                   // override resolution; default = 0
  required?: boolean;                  // true → fail-fast on first launch
  probe: string;                       // relative path to executable probe
  requires?: string[];                 // declared deps (binaries on $PATH)
  setupDoc?: string;                   // relative path to setup HTML/MD
  setupSteps?: SetupStep[];            // ordered remediation chain
}

export type SetupStep =
  | { type: "depends"; integrationId: string }
  | { type: "run"; description: string; command: string;
      confirmText?: string; timeout?: number }
  | { type: "tell"; text: string; link?: string;
      copyCommand?: string; waitForUserSignal?: boolean };

3b · Probe contract

A probe is any executable the pack ships at checkers/<id>.sh (or any path declared in integration.probe). The framework invokes it with no arguments, captures stdout, parses as JSON: 

// probe contract — stdout JSON
{
  "status": "ok" | "missing" | "misconfigured" | "unreachable" | "blocked",
  "summary": "Authenticated as you@acme.com",      // 1-line for Doctor row
  "detail": "Hosts: github.com, ghe.acme.com",     // 1-2 lines for expanded view
  "fixHint": "Run `gh auth login --web` to add another host",  // optional
  "version": "2.45.0"                              // optional, surfaced in Doctor
}

Non-zero exit code or non-JSON output is treated as {status: "unreachable", detail: stderr}. Probes get a 10-second default timeout. Probes are never given network access by Duo (they can do their own outbound, but Duo doesn't inject any token / env that would let a malicious probe phone home). See § 8 Q4 for the trust-model decision.

3c · CLI verbs (per CLAUDE.md § 4 plumbing checklist)

VerbWhat it does
duo doctorExisting health check, extended with an "Integrations" section that lists each integration + status dot + summary line.
duo doctor --integrationsIntegration section only — agent-friendly subset of doctor.
duo doctor inspect <id>Print one integration's full detail + remediation chain (read-only).
duo doctor fix <id>Walk the remediation chain in the terminal — prompt before each run step; print tell steps and pause for user signal; resolve depends recursively.
duo doctor openOpen the Doctor panel in the canvas (mirrors the menu entry).

3d · IPC + renderer surfaces

  • IPC channel integrations-list — main returns current snapshot (id, status, summary, last-probed-at). Renderer pushes on pack install/uninstall + every probe re-run.
  • IPC channel integration-run-step — renderer invokes for each run step; main runs the command with PTY pipe so output streams to the panel; user can cancel.
  • Doctor panel — a new kind: "doctor" WorkingTab (sibling of page / browser / editor). Renders the integrations list, expands on click to show the chain mockup in § 5b, owns the run-step UI.

Override resolution: when both packs declare integrations[].id === "brew", the pack with the higher priority wins. The default Duo pack uses priority: 0; enterprise packs use higher numbers. § 8 Q2 captures the precise tie-breaking rule.

§ 8 · Decisions to lock before I file the ENHs

Four shape decisions where I want your steer. Each one's "recommended" is what I'd ship if you didn't push back — feel free to redirect.

Q1 · Confirm UX for `run` steps
When a setup chain has multiple run steps, does Duo confirm each one individually, or ask once and then run the rest?

Affects trust posture + friction. Per-step is safest (user sees every command); bulk is smoothest. Pack authors can flag a step as "never auto-run" regardless.

Q2 · Override resolution when multiple packs declare the same integration id
When the default Duo pack ships integrations.brew AND an enterprise pack also ships integrations.brew, who wins?

Affects how packs compose. Pack authors need a predictable model.

Q3 · First-launch posture for the Doctor panel
When Duo finishes its first launch and detects that an integration marked required: true is missing, what happens?

Beginner-on-enterprise persona: surfacing setup proactively trains the user that Duo can help them; staying quiet respects "I'll set it up when I need it."

Q4 · Probe trust model
Probes are arbitrary executables that pack authors ship. What constraints does Duo enforce when running them?

Same security question Stage 23's canvas-action trust model wrestled with. Pack authors are not always trusted (someone downloads "acme-corp.dpack" from a Slack channel — a malicious probe could exfiltrate env vars).

General comments / shape pushback
Anything you want to push back on, ask about, or add?

E.g.: schema-field naming (setupSteps vs setup vs remediation), Doctor-panel placement (own canvas tab vs sidebar vs menu), whether required: true is even a useful concept, missing integration types you'd want to model, etc.
