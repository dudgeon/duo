Workspace switcher — design playground

ENH-167 v2 2026-05-22 · post-v0.7.5 · 4 owner decisions

Context. v0.7.4 shipped workspaces as a file type, with Save / Open / Open Recent in the File menu and a name badge in the title bar. After a day of real use, the next question is whether to add an always-visible switcher for the workspaces you bounce between most — and if so, where it lives, how it looks, and what gestures it supports. Five mockups below show the candidate positions; four decision cards below those distill the choices into pickable options. The mockups are stylized — they show position and shape, not pixel-final visuals.

Decisions

Q1 — Position

Where does the always-visible switcher live?

This is the dominant call. The five mockups above are the candidates. Pick one (or "Combination: A + E" / similar) — palette-only is also a valid no-permanent-UI answer.

Q2 — Switch gesture

How does clicking the switcher actually swap workspaces?

Independent of Q1 — applies to whichever position you picked. The "click → in-place reset" follows the existing Open Workspace flow (prompt to save current, then load).

Q3 — Identification

How do users tell workspaces apart at a glance?

Today: name only. Listed in order of "saved at" → "lastOpenedAt". For switchers with limited width (rail pips, floating chip), a name-only display can be cryptic — color or emoji helps.

Q4 — Creating a new workspace

How does a new workspace get created from the switcher?

Today: File menu → Save Workspace As… (or untitled state + Save Workspace…). The switcher could either reuse that path or offer an inline create gesture.

Deferred / out-of-scope for v2 (open if interested)
  • Cross-machine path rewriting on workspace open. Today: absolute paths persist; opening on a different machine silently drops missing ones. Separate ENH; rewriting requires a per-workspace "root" hint or fuzzy-match logic.
  • Workspace tags / categories (multi-tag classification, like Notion). v2 ships a single color tag at most; multi-tag is a v3 thing if it becomes useful.
  • "Save workspace to GitHub" gesture — commit the `.duo-workspace` directly via `gh repo create` or `gh release upload`. Useful for shareable named setups but a separate command, not a switcher concern.
  • Auto-workspace by directory — open Duo from `~/Projects/foo` → auto-load the workspace named "foo" if it exists. Convenient but pre-supposes a strong convention.
  • Workspace-aware Claude session restore — each `claude` terminal still starts fresh on workspace load. Claude Code does conversation persistence; out of scope for Duo.
