Option A — Unlock the Claude-design loop (no migration)

Plan · ENH-238 2026-06-28 · Duo v0.13.1 · phone-reviewable
What this is. The detailed build plan for Option A from the stack study: make Duo's existing React renderer previewable outside Electron so Claude (and Claude Design) get a tight generate → render → observe → correct loop — without changing the stack, losing CDP browser control, or touching distribution. Pros/cons, the Claude Design round-trip impact, the broader design-ops changes, and the Storybook question are all answered below. Decisions to record are at the bottom.

The shape in four moves

1 · Mock the boundary, don't refactor 30 files. There are 478 window.electron.* call-sites and no abstraction layer. We add one createMockElectron() factory typed against the existing ElectronAPI interface — so a bridge change breaks the mock at compile time.

2 · Run the whole app in a browser tab. A preview entry sets the mock before mounting <App/>. The full shell renders on localhost — Claude drives it with the preview tools immediately.

3 · Add a fast component harness. Write Storybook-format (CSF) stories, run them in Ladle (Vite-native, <500ms HMR). Portable to Storybook later, zero rewrite.

4 · Feed the round-trip. Run /design-sync to emit a committed DESIGN.md; optionally extract a @duo/ui kernel so import + handoff are high-fidelity, not approximate.

1. Why this is the right unlock (the seam, measured)

The renderer is the portable half of Duo, but it's welded to Electron at runtime: 478 references to window.electron.* across ~30 files, exposed by electron/preload.ts and typed by interface ElectronAPI at shared/host-api.ts:1066. Crucially, there's no useBridge hook or context — every component reaches the global directly. That sounds bad, but it's actually the easy case: because access is global, we can satisfy all of it by setting window.electron once, before React mounts. No call-site edits.

There's even a working template: renderer/hooks/useNavigator.flicker.test.ts already fakes window.electron.files.list()/.watch() to drive a component under test. We generalize that into a typed factory covering all ~30 sub-APIs.

Boot needs a real handful of mocks to not crash: env.windowId (read synchronously), sessionState.load() → files.exists() batch (App.tsx:747), pty.onData subscription (App.tsx:169), vault.getDefault(), browser.onTabsChange(). Everything else can be a no-op stub. That's the entire Phase 0 surface.

2. The plan, phased (with LOE)

0

Mock seam + browser-runnable renderer 1–2 days

  • Create renderer/test-support/mock-electron.ts → createMockElectron(overrides?): ElectronAPI. Typed against the real interface; subscriptions return no-op unsubscribers, async invokes resolve fixtures.
  • Add renderer/preview/index.html + main.preview.tsx: set window.electron = createMockElectron(fixtures) before importing App, then mount it. Add an npm run preview:ui Vite entry serving it as a plain web app.
  • Fixtures: a small test-fixtures/ (sample SessionState, DirEntry[], a markdown doc) so the shell boots into a realistic state.
Outcome: the full app shell renders in a normal browser tab. Claude uses preview_start/screenshot/snapshot on it — the tight loop exists before any component work.
1

Component preview harness — CSF stories in Ladle 2–3 days

  • Add @ladle/react (Vite-native; 1.2s cold start, <500ms HMR — matches electron-vite's Vite).
  • Write CSF *.stories.tsx for leaf components first: ThemeToggle, CollapsedPaneRail, AddressBar, Breadcrumb, ImageView toolbar, TabBar.
  • One global Ladle decorator injects createMockElectron() so half-pure components (AddressBar → browser.historySuggest, Breadcrumb → files.kind) render with no per-story wiring.
  • npm run stories. This is the per-component loop — far faster to iterate a button than to boot the whole shell.
Outcome: isolated, hot-reloading component canvas. Each story doubles as living documentation + (Phase 3) a test.
2

@duo/ui kernel + DESIGN.md for the round-trip 3–5 days

  • Extract the pure-presentational components + the token layer (renderer/styles/globals.css CSS vars, already the single source of truth, bound into tailwind.config.mjs) into a @duo/ui package consumed by both Electron and the preview/Ladle.
  • Run /design-sync (Claude Code → Claude Design) to import the kernel and emit a committed DESIGN.md — color/type/spacing tokens, component inventory, dark-mode variants — as the round-trip source of truth.
  • Kill the token duplication: globals.css stays canonical; generate (or lint) skill/references/duo-atelier.css from it so playgrounds and app never drift.
Outcome: Claude Design imports a real kernel, not an approximation; handoffs land in components Claude can immediately preview.
3

Design-ops hardening 2–4 days · ongoing

  • Visual regression: Lost Pixel (Ladle-native, free, CI) or Chromatic (needs Storybook). Catches the recurring-UI-regression class your retro keeps re-fixing — turns it into a gate.
  • Agent-parity verb: a duo preview / duo stories CLI verb (or a design-loop skill) so the agent invokes the loop in one step — same as the human clicking it.
  • Story-tests: run stories as Vitest tests (render + interaction assertions) — the harness doubles as coverage.
  • CI: build stories on PR; fail on a broken story or a visual diff.
Outcome: the loop becomes a standing capability with a regression gate, not a one-off.

Totals: the loop is usable after Phase 0 (~1–2 days). Phases 0–1 ≈ ~1 week. Through Phase 2 (round-trip-ready) ≈ ~2 weeks. Phase 3 is incremental.

3. Pros & cons

Pros

  • Keeps everything: CDP browser control, node-pty, the socket CLI, signed distribution — untouched.
  • ~1–2 weeks, near-zero risk, fully reversible (additive files; no stack change).
  • Unlocks the agent design loop and the Claude Design round-trip at once.
  • Free byproducts: component test coverage, visual-regression gate, living docs, a token single-source-of-truth.
  • The mock is typed against ElectronAPI — drift from the real bridge becomes a compile error.

Cons / risks

  • Doesn't reduce Electron's memory/binary footprint (out of scope — that's a different goal).
  • The mock factory is real surface to maintain; un-typed, it would silently drift (mitigated above).
  • Two render paths to keep working (Electron + browser-preview); a CI smoke on the preview entry guards it.
  • Half-pure components need fixtures to look right; heavy ones (MarkdownEditor 2.9k LOC, FileTree 2k) are deferred, not free.
  • @duo/ui extraction (Phase 2) is a moderate refactor — defer-able if you only want the loop.

4. Impact on the Claude Design round-trip

Claude Design's loop has three legs: import the design system from your repo, generate & auto-correct against it, hand off to Claude Code which lands the change. Here's what each leg looks like today vs. after this plan:

Leg 1 — Import (repo → Design), via /design-sync. Today: tokens are clean (globals.css), but components aren't isolated, so "checks output against your components / computed styles" approximates. After: isolated CSF stories + a committed DESIGN.md = high-fidelity import, not a guess.
Leg 2 — Generate & correct (in Design). Today: builds against an inferred system. After: builds against the real @duo/ui kernel and auto-corrects against DESIGN.md before you see it.
Leg 3 — Handoff (Design → Claude Code → repo). Today: the change lands in an Electron app Claude can't screenshot — the loop dead-ends, unobservable. After: Claude Code edits the component, previews it in Ladle / the browser entry, screenshots, and iterates. The loop closes.

Net: the round-trip goes from a blind handoff into an unobservable app to an observable, component-isolated, token-backed loop. The single biggest unlock is Leg 3 — and it's delivered by Phase 0 alone.

5. Should we make Storybook files?

Yes — write Storybook-format stories, but run them in Ladle. The format (CSF — Component Story Format, the *.stories.tsx convention) is the industry standard, and Ladle consumes the exact same files. So you get the portable, well-understood story format and Ladle's Vite-native speed — which matters because a slow harness kills the agent loop. If you later need Chromatic, addons, or an enterprise ecosystem, point Storybook at the same stories with zero rewrite. Don't pick Storybook-the-tool now; pick Storybook-the-format + Ladle-the-runner.

6. Other design-ops changes worth making

  • Token single-source-of-truth, enforced. globals.css is canonical; lint/generate duo-atelier.css from it so the app and the playgrounds (this very page!) can't drift. Today they're hand-kept-in-sync copies.
  • Commit DESIGN.md and treat it as a tracked artifact. It's the round-trip contract; review changes to it in PRs like any spec.
  • Make the loop CLI-addressable. A duo preview/duo stories verb (CLI-parity rule) so the agent starts the harness the same way the human does — and the smoke-walk can assert on it.
  • Fold visual-regression into the existing gate. Your retro already flags recurring UI regressions needing durable coverage — a per-story pixel diff is exactly that, automatically.
  • Stories as the smoke-walk substrate. Many smoke-walk items are "does this component look/behave right" — a story is a faster, repeatable home for those than booting the whole app.
  • Keep Electron as the integration surface. The browser preview is for look & interaction; anything touching CDP/pty/sockets still gets verified in the real app. Don't let the mock lull you into skipping integration checks.
