Vault inbox & rollups view — design + rollup-lifecycle proposal

Research Needs decisions 2026-06-24 · feature spike for a new top-level vault surface
What this is. A design proposal for a new top-level Vault view that sits beside the Home tab and is shown when a vault is selected. It lists the vault's inbox (with a capture button) and its rollups (with view links + a create button). The hard part isn't the UI — it's that rollups have no canonical home or registry today, so "list the rollups for this vault" is currently unanswerable. This page proposes a rollup-lifecycle change that makes the view reliable, and asks you to lock six decisions before any code is written.

2 · How it slots into the app (architecture)

This is cheap on the UI side — it follows the Home pattern exactly. Home is a synthesized, never-persisted, pinned slot-0 tab (type: 'home', pseudo-path duo://home) dispatched in renderer/components/WorkingPane.tsx. The Vault view is a sibling:

  • Add 'vault' to WorkingTabType in shared/types.ts.
  • Synthesize a pinned type:'vault' tab (duo://vault/<root>) right after Home when a vault is active; dispatch to a new <VaultView> in WorkingPane.renderFileTab().
  • Data comes through the existing window.electron.vault.* IPC bridge (electron/preload.ts → ipcMain.handle in electron/main.ts → core/vault, the same code paths the duo vault CLI uses). We add two read verbs: list inbox and list rollups (see §4).
The inbox half is already well-defined: capture notes always land in inbox/ with a captured: frontmatter date (core/vault/scaffold.ts), and stale = captured < today − 1 week (the existing processing.base rule). The view just reads inbox/ and the + Capture button calls duo vault capture. The rollups half is the unsolved part.

3 · The rollup-lifecycle problem (the core finding)

"Rollup" is not one thing in the codebase today — it's three different mechanisms, none of which records that it exists anywhere a view could enumerate. There is no registry, no index, no type: rollup — discovery would mean scanning several scattered locations and de-duplicating by hand.

The richest mechanism (ENH-229 rollup artifacts, with embedded snapshot/diff history and source-hash staleness) is exactly what the view wants to surface — but the artifact in rollups/ is an output, not a handle. There's no object that says "this rollup is called X, here's its query, here's where it last rendered, here's whether it's stale." Two authors rendering the same view in two formats produce two artifacts the view can't tell are the same rollup. That gap is what makes a reliable rollups list impossible today.

4 · Proposed lifecycle change — make a rollup a first-class typed note

The fix that's most aligned with the vault's own philosophy (the corpus is the schema; no sidecar; state lives where it belongs): promote the rollup from "an output file" to a typed note — type: rollup, living in rollups/ — that is the durable handle. Everything else (the .base, the rendered HTML) hangs off it. 

rollups/open-milestones.md
---
type: rollup
id: rl-7f3a9c
title: Open milestones by initiative
spec: bases/open-milestones.base   # or an inline ```base block, or a listing: spec
last_render: rollups/open-milestones.html
last_source_hash: 9c1ad4e2f0b7    # stamped at render; staleness = (≠ live corpus hash)
rendered_at: 2026-06-24
---
Open milestones across all initiatives, grouped by owner, with a due chip.
Createstub a type:rollup note (existing duo vault stub machinery) — or a Claude session authors its spec
→
Renderexisting engine renders the note's spec to its artifact; stamps last_* back into the note frontmatter
→
Discovertype == rollup — the corpus already indexes this. duo rollup list = one query, no scan
→
Surfacethe view lists rollup notes; freshness = last_source_hash vs live corpus hash; "view" opens the artifact

Why this is the right shape:

  • Discovery becomes a corpus query. "List the rollups" = "notes where type == rollup" — the exact machinery duo vault schema already runs live, every call, no cache (§D9-clean). No new registry, no sidecar, no scan-and-dedupe.
  • It unifies the three mechanisms. The rollup note's spec: can point at an existing .base, carry an inline ```base block, or hold a listing:-style spec — so OKF and Obsidian vaults both get one durable rollup object, even though the render sink differs.
  • Backward-compatible + incremental. Existing bases/*.base files keep working; a rollup note just references one (spec: bases/foo.base). No migration is forced — you wrap a base in a note when you want it to show up in the view.
  • The artifact stays a pure build-output. The note is the source of truth; the HTML in rollups/ remains regenerable + stamped (the existing ENH-229 snapshot/diff history rides along untouched).
Alternatives considered (and why they're weaker)

A · Convention + scan only — designate rollups/ as canonical, add duo rollup list that scans bases/ + every note for ```base + the rollups/ dir, and de-dupes by mtime. Ships fastest, no model change — but discovery stays a fragile multi-source scan, embedded bases are invisible until rendered, and there's still no named handle (the dedupe problem persists). Good fallback if you want v1 with zero lifecycle change.

C · A manifest file — rollups/index.json listing every rollup + metadata. Simple to read, but it's a textbook sidecar (CLAUDE.md §12 / D9): it drifts from the real .base/artifact state the moment anything is edited out-of-band, and the project has an explicit invariant against exactly this. Rejected on principle.

B (recommended) avoids both: no scan (it's a corpus query) and no sidecar (the note is the corpus). It costs a new type: rollup template + teaching the render verbs to stamp last_* back into the note.

5 · Decisions to lock

Decision 1

Rollup discovery model — how does the view know what rollups exist?

This is the load-bearing decision; everything else follows from it. See §3–§4.

Decision 2

What does "the selected vault" mean for this view?

There's no app-level "selected vault" state today — vault is derived per-op from the active file's enclosing folder, and there's a separate machine-global default vault (Settings → Default Vault / duo vault default).

Decision 3

When does the Vault tab appear, and where?

Home is a pinned slot-0 tab. The Vault view would be its sibling.

Decision 4

"Create new rollup" — what does the button do?

You floated both a prefilled Claude session and another mechanism. Authoring a good rollup spec needs the live corpus (real type/enum names), which is Claude's strength.

Decision 5

Inbox list — scope and "view this item" behavior

Inbox = notes in inbox/. The + Capture button calls duo vault capture (the ⇧⌘N twin) and opens the new note.

Scope of the first slice
