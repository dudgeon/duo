OKF vault mode — PRD & decisions

Decision round ENH-216 draft for sign-off 2026-06-13 · a second at-rest serializer so Duo vaults publish to GitHub
The dilemma. Obsidian vaults are the popular format today, but the highest-value future use case is knowledge bases that render and resolve on github.com and in any tool — which points at standard markdown links with relative paths (the shape the proposed Open Knowledge Format standardizes). Duo's vault feature (ENH-208) is wired entirely to Obsidian [[wikilinks]], which render as literal text on GitHub.

The proposal. Add an OKF vault mode that keeps the exact authoring ergonomics we have — the [[ ]] hotkey, the type-picker, silent-stub creation — but writes standard markdown relative links at rest. Format is chosen per vault (including a new File ▸ New Vault picker), and the active vault toggles Duo between Obsidian mode and OKF mode.

0The reframe: one graph model, two serializers

The encouraging finding from reading the code: Duo already separates the three things that matter. The gesture ([[ autocomplete + the silent-stub type-picker, WikilinkSuggestion.ts), the filing rule (where a new entity lands, filing.ts · wikilinkCreate.ts), and the at-rest syntax are distinct layers. Only the third is fused to Obsidian.

So this is not a second vault system. The entity / type / edge model in core/vault/ is format-agnostic; OKF mode is a second serializer + a second parser over the same model. Obsidian mode and OKF mode are two ways to write the same graph down.

Key fact that makes this worth doing: standard markdown links render in all three targets — Duo, Obsidian, and github.com. Wikilinks only fail on GitHub. So OKF mode is strictly more portable and still opens correctly in Obsidian — the one thing it trades away is wikilink basename-resolution (links surviving file moves for free), which Decision 5 addresses head-on.

Mode is a property of the vault, not a global app switch. Whichever vault is active (the primary/default, or the one containing the open file) sets the editor's dialect. The open question is the source of truth for "which mode is this vault?"

5The at-rest tradeoffs OKF mode forces

These are where OKF mode genuinely diverges from Obsidian mode. Each wants an owner call; none is purely cosmetic.

5a · Moves & link stability — the real cost of leaving basename resolution

Obsidian mode resolves [[Foo]] by basename, so moving a file breaks nothing. OKF relative links are path-anchored: a move breaks every inbound link. Duo has the whole graph, so it can rewrite inbound links on move — the question is whether we commit to Duo owning moves.

5b · Filenames

Obsidian happily uses Customer Orders.md. On GitHub, spaces become %20 in URLs and some tooling balks; OKF examples use lowercase-hyphenated stems. Slugging lets us put the human name in OKF's recommended title: field and the clean stem on disk.

Decision 6 · Filename convention in OKF mode

5c · Frontmatter edges

Duo encodes typed relationships in YAML (owner: "[[Alice]]"). OKF frontmatter is plain key/value — a wikilink string there is opaque to any consumer, and the body is where OKF expects links. We need a convention OKF mode writes (Duo still resolves it; GitHub never renders frontmatter anyway, so this is about portability + Duo's own graph).

5d · Rollups

.base files and embedded ```base blocks render live in Duo/Obsidian but show as inert code on GitHub. OKF's native "listing" surface is index.md (§6) — a bullet list of links + descriptions — which Duo can generate from the corpus. That turns our rollup into something GitHub renders for free.

OKF §9 requires a non-empty type on every concept doc. Today captures are untyped by default and the scaffolded README.md has no frontmatter — so a default vault fails conformance. OKF mode can stamp type by construction.
