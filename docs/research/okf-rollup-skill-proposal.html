OKF rollups — guidance fix + a dedicated vault/rollup skill?

Decision gate 4 questions ENH-234 · filed 2026-06-24 · owner-reported (photo) · Part A shipped in-branch
Owner report. A photo of an Opus agent asked to "make a rich html rollup of tasks and initiatives from this vault." The agent hand-built a bespoke HTML dashboard, then (after correction) reasoned: "OKF mode — duo rollup expects .base blocks, the views are hand-authored markdown without them, so duo rollup render won't work" → reached for a bespoke playground.

The ask. "Reconcile the docs — and consider adding a new managed skill for vault management incl rollup management; think through the current rollup creation workflow, how a skill would be additive, how it would be deployed via the DMG."

This page. The verified root cause, the current workflow, the deployment reality of shipping a new skill, and four decisions for you — radios + notes, then Copy (or Send to Claude) at the bottom.

Root cause — it wasn't a missing capability

The agent's CLI was fully capable. It runs the repo cli/duo at v0.12.1 — rollup + the ENH-230 listing: support are both present. The failure was contradictory guidance that talked the agent out of the working path.
"Make an HTML rollup of this OKF vault"
→
SKILL.md / vault.md said: "OKF has no .base files — authoring one is a no-op"
→
agent: "so rollup render can't work here"
→
hand-builds bespoke HTML (no Refresh button, no stamp)

…while references/rollup.md simultaneously said "author a .base, render works in both modes." The two surfaces disagreed; the agent believed the scarier one.

✓ Verified empirically (throwaway OKF vault)
duo rollup render tasks.base --html in an OKF vault produced a valid artifact — 2 task rows grouped by initiative, a working Refresh button, and the OKF entity link resolved (href="./initiatives/graphbook.md"). The "rich HTML rollup with a refresh button" the owner wanted is exactly what rollup render --html emits. The agent just never reached it.
Part A — already shipped in this branch. The contradiction is reconciled across rollup.md, SKILL.md, vault.md, .claude/rules/vault.md: OKF doesn't auto-render .base at rest (an Obsidian-live behavior), but a .base is just a query — duo rollup render <base> --md|--html works in both modes. Synced to ~/.claude (the live agent is unblocked). The open question below is Part B: does a dedicated skill add value on top of this?

The current rollup-creation workflow

What an agent must do today to satisfy "make me a rollup/dashboard from my vault":

1. duo vault schema # learn the real type/field/enum names 2. author a .base (the query) # filters + views + groupBy + formula chips 3. duo base lint <base> # advisory; fix "did you mean" until clean 4. duo rollup render <base> --html --open ← the artifact (works in OKF too) — or, for the in-vault canonical index — duo vault publish # index.md; + a listing: frontmatter spec (ENH-230) for grouping 5. on refresh: duo rollup diff → write narrative → render --summary

Friction points the photo exposed

  • Triggering — the agent didn't consult the skill at all until corrected; it went straight to bespoke HTML. unsolved by Part A
  • The OKF/.base contradiction — talked it out of rollup render. fixed (Part A)
  • Three OKF paths blur together — rollup render (artifact) vs vault publish (index) vs listing: (expressive index). clarified (Part A); still a lot to hold
  • Step 2 is hand-authoring — no scaffold; the agent writes .base YAML from scratch each time. open

Deployment reality — what a "managed skill" actually costs

How skills reach an installed (DMG) user today, from the code:

  • electron-builder.yml ships the whole skill/ tree into the app bundle (extraResources).
  • electron/install-service.ts copies it to ~/.claude/skills/duo/ on first launch/upgrade — with hardcoded, per-file copies (SKILL.md, references/, examples/…), registered in ~/.claude/duo/installed.json for upgrade + orphan cleanup. It does not iterate a skills manifest.
  • Claude Code then auto-discovers any folder under ~/.claude/skills/* by its SKILL.md name + description.
  • Precedent: the pack-builder skill ships only via dev sync:claude — not by install-service — so installed users never get it. It's effectively a repo/dev-only skill.
So a new managed duo-vault skill that reaches installed users is real plumbing, not a folder: a source dir, an extraResources entry, new hardcoded copy logic in install-service.ts + its installed.json provenance + orphan-map, an install-service.test.ts case, and the sync:claude update. Plus the SessionStart priming + the managed CLAUDE.md block currently name only the duo skill.

The additivity tension

The duo skill's description already claims vault/rollup: "…work with their knowledge vault / notes… building rollup views…", and it already has dedicated reference spokes (references/vault.md, references/rollup.md) — the depth exists. A second skill that also describes "vault/rollup/notes" gives Claude Code two overlapping triggers to disambiguate — the same unreliability the photo shows (the model picking wrong / not triggering). Separation-of-concerns has to beat that ambiguity cost to be worth it.

One orthogonal idea worth a vote (independent of A–D)

The single highest-leverage capability fix to step 2 is a base scaffolder — e.g. duo base new --type task --group initiative --cols status,owner — so an agent (or you) gets a lint-clean .base without hand-writing YAML. It shrinks "make a rollup" to two verbs in any vault and removes the most error-prone step. That's a small feature, not a skill — Q4 asks whether to pursue it.
