BUG-125 v2 — canvas baseline tracking

Decision gate 4 questions Filed 2026-05-16 · v0.7.0 walk surfaced · parent BUG-125 v1 shipped PR #49
The bug. BUG-125 v1 (PR #49 — symlink-resolved watcher path remap) was supposed to make external writes to canvas-mode HTML files reload silently when the buffer is clean. Walk found: the conflict banner still fires on clean buffers.

Root cause. The canvas baseline isn't the disk content — it's the live serialized DOM after Duo's runtime modifications (data-duo-id anchors, image-selection-tint <style> element, pretty-print formatting). When the watcher compares baseline vs. disk for an external write, they differ — even when no user edits happened.

The pre-save reconciliation correctly sees they differ → fires the conflict banner. The bug is the comparison model: byte-equality on a baseline that includes Duo's own injections.

This isn't unique to symlinked paths — BUG-125 v1 fixed the watcher path-resolution layer but didn't notice the deeper baseline-divergence layer. Any external write to ANY open canvas-mode HTML would trigger the same false-positive banner.

2 · Three resolution options compared

Option A — Always reload on external write (canvas is a view of disk)

Conflict banner fires only when buffer is dirty. Clean buffer + any external write → silent reload, no questions asked. Duo's runtime modifications get re-applied to the new DOM on mount.

Pros: matches owner mental model — "canvas is a view of the file." External writes win.

Cons: if the user (or agent) linked comments to data-duo-id anchors, those anchors break on every external write. Comment-anchor data tied to vanishing IDs.

Option B — Normalize before comparison Recommended

Pre-save reconciliation calls normalize(disk) === normalize(baseline) instead of byte-equality. Helper at core/html/duo-normalize.ts:

  1. Parse HTML (DOMParser).
  2. Strip data-duo-* attributes from all elements.
  3. Remove <style data-duo-style> and other Duo-owned injected elements.
  4. Re-serialize with consistent formatting.

Pros: data-duo-id anchors preserved across external writes (Duo re-applies them on next mount). Conflict only fires when user-meaningful content differs.

Cons: Brittle if new Duo injection lands later without updating the normalizer. Adds a pure helper + 2 call-site swaps (vitest-able).

Option C — Extend the existing echo-guard

The conflict log shows recentlyWrittenSize: 0 — the echo-guard tracks bytes of Duo's own saves, doesn't match external writes. Extend it to: "if normalize(disk) === normalize(baseline), treat as echo of current state."

Pros: Unifies with the existing recently-written guard. One code path.

Cons: Essentially Option B + a misleading code location. Echo-guard is about our own writes; this is about byte-equivalence after stripping Duo content. Different concept living in the wrong place.

Q1 · Resolution option
Which approach should we ship?

All three close the false-positive class. Trade-off is between owner mental model (A) vs. anchor preservation (B/C).

Q4 · Markdown editor parity
Does the TipTap markdown editor have the same baseline-divergence pattern?

Markdown source-of-truth round-trips through TipTap → markdown → TipTap. If any extension injects characters that survive round-trip, the same fix shape applies.

3 · Implementation outline (once decisions land)

  • core/html/duo-normalize.ts (new) — pure helper, vitest-testable with fixture HTML.
  • renderer/components/Page/PageTab.tsx § save-pre-reconcile — swap byte-equality for normalize(disk) === normalize(baseline).
  • renderer/components/Page/PageTab.tsx § file-watcher reload branch — same swap.
  • renderer/utils/conflictDiagnostic.ts — capture both raw + normalized lengths in the log.
  • Vitest fixtures — normalize() preserves user content, strips data-duo-id, idempotent on pre-normalized input.
  • Smoke walk regression items — covering: clean buffer + external simple-write (silent reload), clean + different-content external (per Q1), external that strips data-duo-id (per Q2).

Estimate: 1 dev day for normalize + reconciliation hook + tests. Markdown parity adds ~1 hour if Q4 picks investigate.

Why not just disable file-watching on canvas-mode files?

Considered and rejected. The owner explicitly relies on the watcher to pick up Claude's filesystem edits to canvas files (FOLLOWUP-019). Disabling reload would silently lose external edits to clean buffers — a regression on the very pattern BUG-125 was supposed to fix.
