Folder hierarchy across five knowledge models

Research + decisions rev 4 · OKF blog incorporated Obsidian · Karpathy's LLM Wiki · Google OKF · Duo OKF vault · looplibrary brainkit  ·  2026-06-28
What this is. A contrast of how five knowledge-corpus models lay out folders — and a decision aid for how you approach this in Duo's OKF vaults and looplibrary's brainkit. The first fork is the one you flagged: does the folder a note lives in carry meaning (Obsidian — the tree IS a human hierarchy you browse, like an initiative's work-breakdown or an org chart), or is it just a drawer (the OKF family — meaning lives in type: + links, folders are tidiness)? Obsidian sits at one pole; Karpathy, Google OKF, Duo OKF and brainkit cluster at the other. Nothing in your current stack actually implements Obsidian's semantic-folder model — even Duo's own "Obsidian mode" files flat. But that fork is narrower than it first looks: the cost is authoritative folders, not folders at all — keep the graph canonical and derive the tree from it (Approach 2 below) and you get the human view and the agent view at once. And OKF, read firsthand, plainly permits nested folders and even makes the file path the concept's ID — so a derived primary-axis path is the most OKF-native option, not a deviation.

The second fork only matters once you've chosen "flat + typed": there, Duo OKF and brainkit diverge less on folders than on the content model above placement (maturity ladders, a task primitive, provenance, deliverable-coupling). Decisions at the bottom cover both forks.

Plain-language glossary (no jargon). Two ways a folder can work:
  • A folder that means something (Obsidian-style): where a note sits is information. Initiatives/Apollo/Phase-1/tasks/ tells you this task belongs to Apollo's Phase-1 work-breakdown; Org/Eng/Platform/ mirrors the org chart. You navigate by browsing the tree, and the structure is legible to a human at a glance. Moving a note changes what it means.
  • A folder that's just a drawer (OKF-style): the folder is only a tidy place to keep the file. The note's meaning comes entirely from its type: field and its links — so moving it between folders changes nothing. You navigate by querying type/links or reading a generated index.
(Earlier draft called these "semantic" vs "ergonomic" — same idea, worse words.)

The five models, in one breath each

Obsidian (native / idiomatic) — the divergent one

PKM app since 2020 · folders + [[wikilinks]] + graph · human-first

Folders are a real, human-navigable hierarchy; the file tree is the primary way you understand and browse the corpus.

A vault is a folder of markdown. In idiomatic use, folders carry organizational meaning — PARA, folder-per-project, a nested initiative WBS, a folder tree that mirrors an org chart — and Dataview can even query by folder (FROM "Projects/Apollo"), so placement can be a first-class axis. Crucially, links are [[wikilinks]] resolved by note name, and Obsidian rewrites them on move — so you get meaningful folders AND move-safety at the same time. The cost: it's tool-coupled (.obsidian/, wikilinks aren't standard GitHub markdown) and the folder tree competes with the link graph as "the" structure. Note: vanilla Obsidian doesn't force semantic folders — this is the idiomatic practice + Dataview, which is the philosophy worth weighing.

The first fork: do folders mean anything?

This is the spectrum your feedback surfaced. One pole treats the folder tree as the human hierarchy; the other treats folders as drawers and pushes all meaning into type: + links. Your four "flat" models cluster hard at the right; Obsidian stands alone at the left.

Obsidian

Folders ARE the hierarchy. Nested WBS, org charts, PARA. Human-browsable at a glance; Dataview can query by folder.

Best for: a person navigating structure. Worst for: portability + a single canonical graph.

Duo OKF (rule-bounded middle)

Mostly drawers, but with one semantic concession: a folder-note type (initiative) owns a folder, and only those can be filing parents. Shallow, computed, self-healing.

The only model with a foot in both camps — its folder-note idea is a seed of WBS-style nesting.

Karpathy · OKF · brainkit

Flat drawers. Meaning lives entirely in type: + links (+ for Karpathy, the backlink mesh). Folders never queried; moving a note is a no-op.

Best for: agents + portability. Worst for: a human browsing to understand structure.

Why this matters for your decision. The flat models buy agent-friendliness and portability by giving up the thing Obsidian is best at: a human opening the file tree and immediately understanding the work-breakdown or the org. If a populated brainkit or okf-vault will be browsed by a person to grasp structure (an initiative's WBS, a team map), the flat model makes that harder — you're relying on generated indexes and rollups to reconstruct what a folder tree would have shown for free. The honest gap: Duo has no true semantic-folder mode today — its "Obsidian mode" only swaps link syntax ([[ ]]) and rollup mechanism; it still files flat via D19. So "use Obsidian mode" does not currently get you Obsidian's folders.

Sharpening it — the cost to an agent isn't folders, it's authoritative folders

An earlier draft of this argued "a tree is less expressive than a graph." That was a category error, worth retracting cleanly: nobody is proposing a tree instead of the graph. The link graph (frontmatter + links) is present either way. So the real comparison is graph + meaningless folders vs graph + meaningful folders — and on expressiveness those are identical. A semantic folder adds an index over one chosen edge and removes nothing. It's never "hierarchy OR graph"; it's "graph, with or without a primary-axis projection."

What flat folders actually buy an agent is one hard invariant: "a file's location is meaningless." That invariant is load-bearing — it makes a move a pure relocation (zero semantic consequence), makes "misfiled" impossible (only untidy), and keeps every edge readable/writable in exactly one place. Semantic folders break that invariant for one axis. But the cost lives entirely in whether the folder is the source of truth — not in whether folders carry meaning.

Authoritative folders — you pay

The path is the truth for an edge, or placement is a free-form judgment call.

  • Path duplicates a frontmatter edge → a mirror that can drift (what D9 / "no mirrors" forbid); or the path is the sole encoding of one edge → that edge is special-cased vs every other.
  • Every create/move is a "where does this belong?" judgment → drift across sessions & multiple agents.
  • Moves become semantic acts; path-coupled queries (FROM "folder") silently break on reorg.

Derived folders — ≈ free

The folder is a projection of one frontmatter edge, kept in sync mechanically.

  • Graph stays canonical; the agent still treats the path as meaningless-to-read.
  • One source of truth → no drift; placement is computed, never "wrong."
  • Moves stay free because the tool re-derives the path. This is exactly what Duo's D19 already does — the folder is computed from the filingParent edge and kept in sync by vault mv / relink.

So: no expressiveness loss, and the operational cost is fully avoidable by deriving the folder from the graph rather than treating it as the truth. The one residue is on the human side, not the agent's: a tree forces each note into one primary parent, so for genuinely cross-cutting notes (a meeting touching three initiatives) the browsable tree lies by omission about the other parents. Semantic folders therefore pay off cleanest where the data really is a tree (a WBS, an org chart) and mislead where it's a graph — an argument for applying them selectively, not globally.

Does OKF forbid nested folders? No — and the path is the ID

You flagged that OKF §3 itself uses folder hierarchy, and that OKF may be agnostic on nesting rather than anti-nesting. Read firsthand against the spec: you're right — with one nuance that strengthens Approach 2.

OKF permits nesting; mandates none; forbids none. §3 verbatim: "A bundle is a directory tree of markdown files. The directory structure is independent of the domain — producers organize concepts however makes sense for the knowledge being captured." Nesting is allowed at any depth (§6: an index.md "MAY appear in any directory"); Google's own blog nests sales/{datasets,tables,metrics}/. So OKF is agnostic — folders are not a query axis (relationships live in links; the tree only implies parent/child — see the blog quote below), but they are not discouraged.

The nuance my earlier draft got wrong: OKF folders are not "pure drawers." §4 verbatim: "Concept ID — the path of the concept's file within the bundle, with the .md suffix removed" (tables/users.md → ID tables/users). In OKF the folder a concept sits in is part of its stable identity / address — load-bearing for addressing, just not for queries. That's why bundle-absolute links (/tables/users.md) are the recommended form, and why moving a concept in bare OKF changes its ID.

And the authors state the two-layer model outright — this is the whole synthesis in Google's own words. From the launch blog (Sam McVeety & Amir Hormati, Jun 12 2026): concepts "link to each other with normal markdown links, turning the directory into a graph of relationships that is richer than the parent/child links implied by the file system." So the file system supplies the parent/child axis, and the link graph supplies the richer cross-cutting relationships on top — exactly Approach 2 + the graph. (This also corrects my earlier over-claim that OKF folders carry no relationship meaning: the tree does imply parent/child; the graph is simply richer.) Their own example even files concepts under tables/ / datasets/ / metrics/ folders that mirror the type: field — a real folder-as-derived-projection. And the reference consumer they ship is a graph visualizer, not a folder browser: for reading, the graph is primary; folders are addressing + progressive disclosure.

Why this strengthens Approach 2. A derived primary-axis path isn't bolted onto OKF — it's leaning into OKF's native model, where the path already is the identity. The one thing that makes bare-OKF path-identity painful (a move re-IDs the file and breaks links) is exactly what Duo's stable content-hash id: already fixes — it decouples identity from path, so you get a meaningful derived folder tree and loss-free moves. So Approach 2 (a derived parent/child tree) + the link graph is simply OKF used exactly as its authors describe it — and Duo has already shipped its hard part (the stable id:).

Two ways to get hierarchy without losing the graph

Both keep the link graph canonical; they differ in where the human-browsable tree lives.

Approach 1 — flat files, hierarchy in the index

Files stay flat (OKF IDs flat & stable). The tree is a generated nested-bullet outline in index.md — and you can project several outlines along different axes (by initiative, by person, by quarter), since none is privileged on disk.

Pro: the disk stays a pure graph; zero path-identity coupling; moves never an issue; multiple hierarchies coexist as views; trivially OKF / Karpathy / brainkit-native (it's just their index.md).

Con: the "tree" lives inside one markdown file, not the filesystem — you browse a generated outline, not a Finder/Obsidian/GitHub folder tree (no expand-collapse, no drag); the outline can outgrow the "one screen" budget at scale.

Approach 2 — derived path along one primary axis Your lean · recommended

The graph is canonical; one chosen axis (e.g. the initiative WBS) is materialized as the real folder path, derived from a frontmatter edge and kept in sync mechanically. Duo's stable id: keeps moves loss-free.

Pro: you get the actual filesystem tree (Finder/Obsidian/GitHub) for the axis that's genuinely a tree — real human browsability; OKF-native (path = identity); literally generalizes Duo's D19 folder-note; cross-cutting edges stay links, so the graph survives.

Con: privileges ONE axis (the tree hides cross-cutting parents); needs the sync machinery (Duo has it; bare brainkit does not — it never mints id:); secondary axes still need index/rollup views.

They're not exclusive — and the best answer is probably both. Use Approach 2 for the one axis that is genuinely a tree (the WBS / org), and Approach 1 (index outlines) for the secondary axes that aren't. That directly cancels Approach 2's only real residue — the tree privileging one axis — because the other axes get their own generated views. The graph stays the single source of truth under both. This is also OKF's own stance — per the launch blog, the file system carries parent/child, the link graph carries the richer rest.

Tensions

Human-navigable folders vs the "location is meaningless" invariant — dissolved by derived folders Fundamental

The fork your feedback put back on the table — but narrower than it first looks. It is not "tree vs graph" (the graph is present either way), and it is not "folders cost agents." The only real cost is breaking the invariant that a file's location is meaningless, and that cost is incurred only when folders are authoritative (the source of truth for an edge). Make the folder a derived projection of a frontmatter edge and the cost ≈ 0 — which is exactly what Duo's D19 already does.

Why it matters: you can have the human-browsable tree and the agent-friendly graph; the real decision is just "keep the graph canonical, derive the folder." The residue is human-side — a tree privileges one axis and hides cross-cutting parents — so use it where the data really is a tree. (See Sharpening it and the two approaches above.)

Deliverable-anchored (brainkit) vs deliverable-agnostic (Duo) corpus Significant

brainkit exists to advance a declared work product; Duo's vault is a general work-notes graph with no deliverable sink. Converging formats does nothing to reconcile "organized around producing X" with "organized around remembering things."

Why it matters: if you want Duo's vault to ever produce work products, that argues for porting brainkit's content layer into Duo — which none of the "push brainkit toward Duo" paths do.

Deterministic placement (D19) vs emergent agent convention Significant

Duo computes placement from per-type template meta-keys — reproducible, CLI-driveable, but front-loads schema work. brainkit/Karpathy push placement to agent judgment under a manual, types emerging from use — lighter to start, but unverifiable and drift-prone without a recurring health pass.

Why it matters: the core architectural fork inside the flat pole. You can't have both purities in one corpus.

Stable-id integrity vs tolerate-and-repair vs tolerate-and-break Significant

Four postures on the same move. Obsidian: basename links + auto-rewrite → safe by tool. Duo OKF: stable id: → loss-free. brainkit: plain rel links break, healed by distill — and the agent never mints id:, so Duo's relink is dormant in a brainkit vault. OKF: broken links are explicitly fine.

Why it matters: brainkit ships as a Duo vault but inherits the weaker move contract. Reconciling the no-mint rule with Duo's minting is the highest-leverage, lowest-cost change available.

Duo's OKF dialect vs the bare Google-OKF spec (two dialects under one roof) Significant

Duo layers heading-per-type indexes, D19, id: minting, listing: specs on top of OKF. A brainkit vault (or a Google sample) is also valid OKF but follows different conventions. If "open any OKF bundle in Duo and it just works" is a goal, Duo must decide whether a foreign bundle is read as-is or silently Duo-ized.

Why it matters: a brainkit vault opened in Duo should not be re-filed by D19 behind your back.

brainkit is unvalidated 0.1 — even its spec docs are stubs Significant

brainkit's knowledge/ is empty, and DESIGN.md/FOUNDATION.md contain only "Version ONE of the doc." The loopkit contract it claims to "keep unchanged" is unwritten; loopkit/karpathy-core weren't on disk.

Why it matters: a maturity gap in the spec, not just usage — a prerequisite blocker for any convergence path.

"No mirrors" (brainkit) is stronger and differently-scoped than D9 (Duo) Minor

brainkit polices mirrors at the content level (no synced task list, no clean-twin of a source); Duo's D9 is about not caching the schema/index. Collapsing them into "they agree" hides what brainkit forbids that D9 doesn't.

Paths forward

Decide the folder-meaning fork first — and offer a semantic-folder overlay where humans browse Recommended · first

Affects: both (upstream of all other paths)

Before any format/content work, answer: will a person browse this corpus to understand structure? If yes for some surfaces (an initiative WBS, an org/team map), keep the flat typed graph as the substrate but allow a semantic-folder overlay there — generalize Duo's folder-note idea (an entity owns a folder; children nest under it) into an opt-in, human-navigable subtree, while the graph underneath stays canonical and move-safe via id:. If no, commit to flat and lean on generated indexes/rollups for the human view.

Resolves: the fundamental human-vs-machine folder tension without abandoning the typed graph — you get WBS/org browsability where it pays, flatness everywhere else.

Cost: a second filing mode to design; risk of premature nesting. And note this is new build — neither Duo mode offers it today.

Hybrid: shared OKF format + a shared id: primitive, divergent placement Recommended

Affects: both

Standardize the format (bare OKF) and the one thing that hurts at scale — link integrity — by making stable id: a tool-agnostic primitive both honor (Duo mints + heals; brainkit preserves + may request). Leave placement divergent: Duo keeps D19, brainkit keeps emergent filing.

Resolves: the highest-severity practical tension (moves) without forcing a placement merge. brainkit vaults opened in Duo get loss-free moves.

Cost: changes brainkit's "agent never mints id:" rule; two index generators remain.

Port brainkit's content layer into Duo OKF (not the other way) Recommended

Affects: Duo OKF (unifies your content model)

Every other path pushes brainkit toward Duo's format. The higher-value reverse: Duo's vault has no maturity ladder, no task primitive, no ## Raw provenance — brainkit has all three. Resolves: the content-model gap + deliverable-coupling fork — one richer content model instead of two thin ones; makes Duo's vault deliverable-capable.

Cost: real build in Duo; pair with the prerequisite below to avoid importing unvalidated conventions.

Use Obsidian mode where browsing matters, OKF mode where automation matters Viable

Confidence & corrections — what's verbatim vs. interpretation (read before citing)

Findings were adversarially fact-checked; overall reliability solid. Notes:

  • Obsidian (added rev 2) — from well-established behavior + Duo's own vault docs, not a new web pass. Accurate nuance: vanilla Obsidian does not enforce semantic folders (folders are optional; links resolve by basename regardless). The "folders carry meaning" reading is the idiomatic practice (PARA, folder-per-project, WBS/org trees) plus Dataview's ability to query FROM "folder". The move-safety point (wikilinks resolve by name; Obsidian rewrites links on rename/move) is core behavior. Duo's "Obsidian mode" only changes link syntax + rollup mechanism — it still files flat via D19, so it is not idiomatic semantic-folder Obsidian.
  • Google OKF is real and Google-published. Spec at GoogleCloudPlatform/knowledge-catalog/okf/SPEC.md (v0.1), announced Jun 12 2026 (Sam McVeety, Amir Hormati). "The directory structure is independent of the domain" (§3) is verbatim-confirmed. §6 = Index, §7 = Log. Launch blog read in full (rev 4): confirms path-is-identity ("the file path is the concept's identity") and states the two-layer framing verbatim — the link graph is "richer than the parent/child links implied by the file system." The blog name-checks Obsidian, Notion, Hugo + the AGENTS.md/CLAUDE.md family as the familiar shapes OKF formalizes for interop, and ships a graph-view visualizer (not a folder browser) as its reference consumer.
  • OKF §3/§4 read firsthand (rev 3). "The directory structure is independent of the domain" (§3) confirms OKF is agnostic on nesting — it permits any depth, mandates/forbids none. But §4 is verbatim "Concept ID — the path of the concept's file within the bundle, with the .md suffix removed" — so OKF folders are not pure drawers: the path is the concept's stable identity/address (load-bearing for addressing, not for queries). "Drawer / tidiness" remains an accurate gloss for the query dimension only; corrected from the earlier blanket "drawers" framing. ("Ergonomic" was the same query-dimension gloss.)
  • Karpathy's "LLM Wiki" is the gist karpathy/442a6bf… (Apr 4 2026). Folder core (raw/ + wiki/ + schema + root index/log) and the quotes are verbatim. The gist has no explicit "flat good / nested bad" rule — flat-over-nested is a well-supported structural inference. "LLM-as-compiler" is researcher framing; his metaphor is "Obsidian is the IDE; the LLM is the programmer; the wiki is the codebase." (That metaphor is also why Obsidian sits at the head of the lineage.)
  • brainkit — from dist/brainkit/{README,CLAUDE}.md + templates. It is 0.1 "candidate, pending validation" with empty knowledge/; DESIGN.md/FOUNDATION.md are "Version ONE of the doc." stubs; loopkit/karpathy-core not on disk — so "keeps loopkit's contract unchanged" is currently unverifiable.
  • Duo OKF — code-verified (filing.ts, listings.ts, move.ts, detect.ts). Shipped + mechanism-verified, but scale-untested (watcher deferred). The known-parent re-file step is a documented processing concern, partly doc-asserted vs. code-located.
