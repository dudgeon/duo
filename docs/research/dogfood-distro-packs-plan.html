§ 1 · Confirmation — dev install matches packaged install

✓ Confirmed

Source-install (npm run dev) runs the same install pipeline as the packaged DMG

When a user clicks Install on the welcome banner — whether the app is dev-launched via npm run dev OR launched from a notarized DMG dropped into /Applications — the SAME 13 install operations run with the same effects on ~/.claude/. The check at install-service.ts:425 only branches on ONE op (the help/ copy):

  • Packaged (app.isPackaged === true): help/*.html is COPIED from the bundled extraResources to ~/.claude/duo/help/.
  • Dev (app.isPackaged === false): help/*.html is SYMLINKED from the repo's help/ dir to ~/.claude/duo/help/. Edits in the repo flow live to the user's installed copy without re-running install.

Every other op (skill copy, agent copy, packs copy, settings.json hook, CLAUDE.md merge, PATH shim, CLI install, default pins, external-domains, priming.md, provenance) runs identically in both modes.

Practical implication for the maintainer (who can npm run dev at work but can't install the DMG): every modification described in § 4 below works the same way in dev mode. The smoke-test path is identical.

§ 4 · Recipes — how to modify the install

The owner question this section answers: "if I want to modify the existing main install process: add new markdowns which should be added to the default install, modify the managed duo snippet that lands in user's ~/.claude/CLAUDE.md, etc — what do I do?"

Add a new markdown / HTML doc to the default install (~/.claude/duo/help/)

  • Create the new file under help/ at repo root, e.g. help/beginners-guide.html.
  • That's it — the file is auto-included in the next packaged build (op #4: the files: help/**/* glob covers it). On first launch, install-service either symlinks (dev) or copies (prod) it to ~/.claude/duo/help/.
  • If you want it pinned by default, also edit the default-pins JSON literal at install-service.ts:520-528 (op #8) — add an entry like { kind: 'browser', ref: \`file://${HELP_DEST_DIR}/your-file.html\`, title: 'Duo — Your Title' }.
  • If you want it as the default new-tab landing URL, edit browser-manager.ts:49 (the defaultLandingUrl helper).

Side-effect: existing users get the file on next install (op #4 atomic-replace). Default pins (op #8) are bootstrap-only-if-absent — existing users won't get a new pin retroactively. To add the pin for existing users too, you'd need a one-time migration in install-service (separate work).

Modify the managed Duo snippet in ~/.claude/CLAUDE.md

  • The snippet text is hardcoded in install-service.ts — search for the constant carrying the snippet body (it's the text rendered between the distro-managed markers).
  • Edit the constant. On the next install run, op #10 atomically rewrites the snippet between markers; user-added content outside the markers is preserved.
  • If you've made the snippet wholly new (different shape, not just edits), bump the marker prefix or add a sentinel so old installs detect the version mismatch and re-merge cleanly.

Side-effect: all users (existing + new) get the new snippet on next install. The sticky claudeMdManaged flag means a user who explicitly removed Duo's block stays unmanaged — your edits don't reanimate it.

Add a new auto-opened first-launch canvas (FTUX content)

  • Create a new lesson pack at packs/<your-pack>/ with PACK.json + canvases/welcome.html + (optional) lesson-skill/SKILL.md.
  • Set PACK.json § defaults[] to [{ kind: 'canvas', path: 'canvases/welcome.html', openOnFirstLaunch: true, pin: true }].
  • The PackLoader scans on every boot; the first-launch defaults hook (main.ts:513-547) fires per-pack-version. So a version bump in PACK.json re-fires the auto-open for users who already saw the previous version.

Side-effect: existing users get the new pack mirrored on next install (op #5); the per-pack-version flag in installed-packs.json means the auto-open fires once per (name, version) tuple. Bump the version to re-fire after content changes.

Change the default pinned browser tabs (op #8)

  • Edit install-service.ts:520-528. The defaultPins literal is the single source of truth.
  • Each pin is { kind: 'browser', ref: '<url>', title: '<display>' }. URLs can be file:// for help docs or normal https:// for external links.
  • Bootstrap-only — only fires if ~/.claude/duo/pins.json doesn't exist yet. Existing users won't get the new defaults retroactively.

Side-effect: only NEW installs see the change. Add a one-time migration if you need the change to flow through to existing users.

Add a new domain to external-domains.json (Duo routes these to the system browser)

  • Edit fork.config.default.json (or fork.config.json for forks). The __DUO_BOOTSTRAP_EXTERNAL_DOMAINS__ Vite-injected constant carries the list.
  • Op #6 does an ADDITIVE MERGE — your new entry lands for both new AND existing users on next install. User-added entries stay; user-DELETED defaults come back (the merge compares against current file, not a snapshot). v2 with a "dismissed-defaults" sidecar is queued.

Side-effect: all users get the new domain on next install. Removed-by-user defaults reanimate; that's a known v1 trade-off.

Add a new top-level CLI verb (duo <new-verb>)

  • Follow the plumbing checklist in CLAUDE.md § 4 — Plumbing checklist for a new CLI verb. 8 files touch.
  • Rebuild the binary: npm run build:cli. Commit cli/duo.
  • Update docs/CLI-COVERAGE.md (mandatory). Sync to ~/.claude/ via npm run sync:claude (dev only — the install-service ships skill on first launch).

Side-effect: agent-side discoverability requires the skill update; humans rarely use the CLI directly (Claude Code calls it). The install-service's atomic-replace path means the new verb's docs reach existing users on next install.

Remove an item from the default install (e.g. ENH-135 FAQ removal)

  • git mv help/<file>.html docs/legacy/<file>.html (archive in repo; keep history for code reference).
  • Edit install-service.ts:520-528 if the file was in default pins.
  • Edit browser-manager.ts:49 if the file was the default landing URL.
  • Edit main.ts first-launch logic if the file was a boot-default tab.
  • Smoke walk: fresh install → verify file isn't installed; existing-user reinstall → file removed via the atomic-replace SHA-aware delete (check safeOverwriteDirContents behavior — confirms removal of files-no-longer-in-source).

Side-effect: existing users see the file disappear on next install. If they had pinned it, the pin URL becomes a broken file:// link — handle by also removing from default pins (one-time migration if you care about existing pin state).

§ 6 · Deferred (with reasoning)

Full convergence — Options A/B/C/D from the original draft

The original ENH-134 draft proposed four options for unifying the main-app install with the distro-packs pattern (Stage 21d). The recommendation was Option D — phased: schema unify in Sprint 15, main-app dogfood in Sprint 16+.

Owner takeaway 2026-05-10: "my main takeaway from reading all of this is that we should actually defer changes — but I do want you to tell me what to do if I want to modify the existing main install process; my sense from your research is that there is not a lot of real advantage of converging the main distro approach with the packs approach."

Why defer is the right call:

  • The two patterns serve different audiences. The hardcoded install service exists because it does load-bearing OS-level things (PATH shim, SessionStart hook, CLI binary symlink) that don't belong in a pack manifest. The pack pattern serves enterprise authors shipping content overlays. Forcing them into one shape doesn't pay off — most install-service ops aren't pack-expressible.
  • The schema duplication (PACK.json vs DISTRO.json) is real but small. Two consumers, both internal. The cost of unifying (~2 days) doesn't pay off until we have a third consumer or a new author needs to learn one shape instead of two. We don't.
  • The maintenance burden of the current install-service is OK. 1331 lines, ~13 well-named operations, idempotent, decent comments. Edits are localized. The recipes in § 4 above show the surface area is small per-modification.
  • The surgical move stands. Beginner's Guide as a pack (§ 5) IS a real win because it's content that belongs in the pack-shape (auto-open, per-version re-fire, evolvable independent of Duo).

If the convergence question reopens later (e.g. a real third-party pack author hits the schema duplication, or install-service grows past 2000 lines, or Stage 21d distro packs need to express things only the install-service does today), the original A/B/C/D analysis is preserved in git history at commit 650609b.
