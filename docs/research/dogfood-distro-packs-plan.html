The first-launch defaults hook (separate from install-service)

After session restore, electron/main.ts § 513 fires the first-launch defaults hook:

PackLoader.scan('~/.claude/duo/packs/') │ ▼ for each pack with manifest: │ ▼ needsFirstLaunch(installed-packs.json, <name>@<version>)? │ ├── no ────► skip │ ├── yes ────► for default in defaults[]: │ if openOnFirstLaunch: │ send NAV_EDIT(<packDir>/<default.path>) │ markFirstLaunched(name, version)

So lesson packs are first-launch-aware via PackLoader + installed-packs.json (per-pack-version, not per-app-version). The OTHER content (skill, subagent, help, default pins, CLAUDE.md block) doesn't have this hook — it's bootstrap-only-if-absent or atomic-replace via the install-service.

Default FTUX experience (what the user actually sees on first launch)

After clicking Install on the welcome banner, the user gets:

  1. Two pinned browser tabs — Duo — FAQ (~/.claude/duo/help/faq.html) and Duo — What Duo Does (~/.claude/duo/help/what-duo-does.html). Bootstrapped via op #8 above (the hardcoded JSON literal).
  2. Lesson pack canvases — intro-to-duo/canvases/welcome.html opens automatically (per PACK.json § defaults[]). The claude-code-basics pack is on disk but only fires when the user invokes the lesson skill.
  3. The duo skill + subagent — auto-discovered by any Claude Code session running anywhere on the machine (because they're at ~/.claude/skills/ + ~/.claude/agents/, the canonical auto-discover paths).

The two pack patterns we already have

There are two incompatible-looking pack schemas in the codebase right now:

Pattern A — "Lesson packs"

Stage 28 (v0.6.0+) · INTERNAL ONLY · loaded by core/pack-loader.ts

Lives at packs/<name>/; mirrored to ~/.claude/duo/packs/<name>/.

Files

  • PACK.json — single manifest
  • canvases/*.html — first-launch tabs
  • lesson-skill/SKILL.md — pack-specific Claude Code skill

PACK.json fields

  • schemaVersion: 1
  • name, version, title, description
  • defaults[] — auto-open canvases (kind, path, openOnFirstLaunch, pin)
  • navPins[] — nav-tree pins (v1 stub, not enforced)

Used by

  • packs/intro-to-duo/
  • packs/claude-code-basics/

Pattern B — "Distro packs"

Stage 21d (v0.6.8+) · ENTERPRISE-FACING · loaded by electron/distro-pack-service.ts

Lives at ~/.claude/duo/extra-packs/<name>/ after user install (drop-in zip / .pkg / fork-and-compile).

Files

  • .claude-plugin/plugin.json — Claude Code plugin manifest (identity)
  • duo-extras/DISTRO.json — Duo integration manifest
  • duo-extras/claude-md-snippet.md — optional CLAUDE.md snippet
  • skills/<skill>/SKILL.md
  • agents/<name>.md

DISTRO.json fields

  • requiresDuoVersion — semver range
  • openOnFirstLaunch[] — same shape as Pattern A's defaults[]
  • pinnedFiles[] — equivalent to Pattern A's navPins[]
  • claudeMdSnippet: bool — opt-in for the snippet merge
  • primingAdditions: bool — opt-in for priming.md additions
  • externalDomainsAdditions: bool — opt-in for external-domains additions

Used by

  • External authors via the pack-builder skill
  • Template at examples/distro-pack-template/

The two schemas are semantically overlapping but mechanically distinct. Both have an identity block, a "what version of Duo do I require" version constraint, a "what to auto-open on first launch" list, and (implicit in A; explicit in B) a way to ship skills and agents and doc snippets. But the field names, file shapes, loaders, and install pipelines are different. Pattern A predates Pattern B by ~2 sprints; the duplication has been on the deferred-cleanup list since.

§ 2 · Problem statement

The main app's "default distro" — docs (help/, skill/, agents/), the FTUX-pinned tabs (default pins.json), the auto-opened lesson (intro-to-duo), the CLAUDE.md snippet, the priming.md, the external-domains seed — is hand-rolled in install-service.ts. Enterprise teams shipping their own version of these same things follow a wholly different pattern (DISTRO.json + plugin.json + distro-pack-service).

Dogfooding the pack pattern means EITHER (a) refactoring the install service to consume the distro-pack schema for its own defaults, or (b) keeping the two pipelines but making the Duo defaults expressible AS a distro pack so authors have a copyable reference, or (c) unifying just the schemas without changing pipelines, or (d) some combination.

The cost-benefit changes a lot depending on how much of the install service we want to subsume. Operations 1–5 (content) are obvious candidates. Operations 6–13 (plumbing) are trickier — some are pack-expressible (CLAUDE.md snippet, external-domains additions), others probably should stay hand-rolled (PATH shim, SessionStart hook, CLI binary symlink, provenance file).

§ 3 · Four options for the refactor

Option A — Full dogfood

Most ambitious · ~3-5 days · biggest blast radius

Convert Duo's defaults into a built-in distro pack consumed by the same distro-pack-service enterprise packs use. Kill PACK.json entirely. Refactor install-service.ts to call distroPackService for the bundled distro pack first, then run only the irreducibly-hand-rolled plumbing.

Pros — One install pipeline. Pack authors see Duo's defaults as their reference template (true dogfood). Schema unification kills PACK.json/DISTRO.json duplication. Forks edit one config (DISTRO.json), not install-service.ts. install-service.ts shrinks ~1331 → ~400 lines.

Cons — Big refactor. Need to encode hardcoded behaviors (CLAUDE.md merge, SessionStart hook, PATH shim) into DISTRO.json schema or a "built-in extensions" concept. Stage 21d's distro-pack-service was designed for SECONDARY packs; making it ALSO the primary path raises edge cases (what if bundled pack missing? version-mismatch handling? re-install-on-upgrade).

Effort: ~3–5 days · Risk: regression-touches the load-bearing first-launch flow

Option B — Documentary mirror only

Cheapest · ~1 day · drift risk

Keep the main install hardcoded. Publish Duo's defaults AS a distro-pack-shaped folder in examples/duo-default-distro/ for reference only. Pack-builders see "this is what Duo's own defaults look like" without guessing.

Pros — Cheap. Documentary value. No regression risk. Reversible.

Cons — TWO things to maintain (the actual install-service AND the documentary mirror). Drift risk — install-service edits won't auto-propagate to the example. Doesn't unify the codebase. PACK.json vs DISTRO.json duplication remains.

Effort: ~1 day · Risk: minimal

Option C — Schema unification

Medium scope · ~2 days · high architectural value

Unify PACK.json and DISTRO.json into one schema. Don't refactor the main install pipeline. Pick one canonical schema (probably DISTRO.json + plugin.json since it's Claude-Code-plugin-spec-aligned), port intro-to-duo + claude-code-basics to it. Update core/pack-loader.ts or retire it.

Pros — Removes schema-duplication confusion (the user's likely root concern). No big install-service refactor. Smaller blast radius than A.

Cons — Doesn't actually move main app's docs/skills/agent into a pack. Two loaders still coexist (or pack-loader dies, ripples through main.ts § first-launch defaults hook). The two lesson-pack ports need testing.

Effort: ~2 days · Risk: low (internal-only schema migration)

Recommended

Option D — Phased: C now, A later

Two sprints · ~2 + ~3-5 days · gates each step on smoke-walk

Sprint 15: ship Option C (schema unification, port lesson packs).
Sprint 15 close-out: owner-decision gate on Step 2 via the four AUQs in § 4 below.
Sprint 16+: ship Option A subset per Q1–Q4 answers (built-in duo-default pack consumed by distro-pack-service; preserve hand-rolled plumbing).
Step 3 (later, if pain emerges): move pack-expressible plumbing into DISTRO.json post-install hooks.

Pros — Phased; Sprint 15's Option C is reversible if Step 2 looks bad. Each step gates on a smoke-walk. Final state is a single install pipeline + dogfooded default distro. Owner gets to course-correct between sprints.

Cons — Requires owner buy-in across two sprints. Step 2 needs a fresh PRD-style scoping discussion before code work.

Effort: ~2 days (Sprint 15) + ~3–5 days (Sprint 16+) · Risk: low (Sprint 15) → medium (Sprint 16+, gated)

Why D over A directly

Two reasons: (1) the schema duplication (PACK.json vs DISTRO.json) is a real source of confusion today and worth fixing regardless of whether we go on to A. Skipping to A means doing both pieces in one big sprint with no fallback. (2) The owner question that prompted this doc is half "what ships" (an inventory, answered above) and half "should we use the pack pattern" (a design choice). Option C answers the inventory side fully and gives us a stable substrate for the design choice.
