Worktree lifecycle UX — create & graceful removal

ENH-221 ENH-210 · D5-C 2026-06-18 · high-fidelity flow study · 6 decisions

✅ DECIDED + IMPLEMENTED (ENH-221, v0.11.2 branch claude/eloquent-albattani-7c44d4, owner /smoke-walk pending). This playground is the decision record (D1–D6); the build, findings & deviations live in docs/prd/enh-221-worktree-lifecycle.md.

Two enhancements to the worktree controller (the dropdown shipped in ENH-210 / PR #100).
  1. Create a worktree from the dropdown — a non-technical PM should be able to click the worktree pill and start a brand-new parallel workspace without ever typing git worktree add.
  2. Survive removal under-foot — when an agent merges & deletes the worktree you're viewing, Duo must not throw a render error: it tells you, and reverts the navigator to main.

This is the ENH-210 D5 escalation from B → C. D5 shipped as read-only ("detect worktrees; Claude makes them via git") "as long as Claude knows how to make worktrees." The non-technical-PM persona is the evidence that gates write/lifecycle verbs: a PM can't drive the CLI, so Duo needs a first-class Create affordance — and, once Duo creates them, it owns the teardown story too.

Below: the entry point, then four realistic flow options for Create (Enhancement 1), then the removal-recovery state (Enhancement 2). Mocks render the real dark Duo chrome at the real 216-px navigator width, faithful to FileTree.tsx. Pick per decision-card; hit Copy decisions at the bottom.

Enhancement 1 · Create a worktree from the dropdown

Required substrate (all options share it). Today the pill is only clickable when there are >1 worktrees. To host Create, the pill must become an always-available dropdown trigger — so a PM sitting on a lone main checkout can open it and make their first worktree. And per Duo's CLI-parity rule, whatever the PM can click, the agent must be able to run: a new duo worktree new verb ships alongside (decisions D2–D4 define its flags).

Enhancement 1 — decisions

Decision D1 · Create flow shape

When the PM clicks "+ New worktree", what do they get?

All four reach the same end state (a new worktree, re-rooted). The question is the surface. The PM is non-technical, and Duo's modal track record has a WebContentsView-occlusion hazard.

Decision D2 · Naming model

How is the new worktree's branch / folder named?

Folder lives at .claude/worktrees/<name>, branch at claude/<name> (the current convention). The PM shouldn't have to think in git branch names.

Decision D3 · Does creating also start a Claude session?

After the worktree exists, do we boot an agent in it?

Duo exists to host parallel agent work. A PM making a worktree almost always wants someone working in it — but auto-spawning a session has a cost (a terminal, a running claude).

Decision D4 · Where the new worktree opens

This window, or a new one?

The dropdown already has a per-row "open in new window" button (ENH-210). Create can default either way.

Enhancement 2 · Survive removal under-foot

You're viewing worktree q3-pricing-page-copy. The agent finishes, merges it to main, and runs git worktree remove. The folder the navigator is rooted in vanishes. Today that risks a render error (the nav reads a cwd that no longer exists). Required behavior: no crash, tell the PM, auto-revert to main.

What happens: Duo notices the current worktree's folder is gone (via the existing focus / file-watch re-probe, hardened by a guard on every navigator read), re-roots the navigator to the main checkout, the titlebar chip drops back to ⎇ main, and a dismissible banner explains why the files just changed — with a one-click View on main. No red error screen, no dead tree. The terminal that was in the removed folder is handled per D6's edge-case note.

Enhancement 2 — decisions

Decision D5 · Recovery UX

How does Duo tell the PM their worktree disappeared?

The non-negotiable part: never throw a render error, always end up somewhere valid (main). The choice is how loud the notice is.

Decision D6 · Detection trigger & the live-terminal edge case

When does Duo notice, and what about a terminal still sitting in the dead folder?

Today a chokidar watcher pushes GIT_WATCH_INVALIDATE but the navigator doesn't act on it. A removed worktree may also have an open terminal whose cwd no longer exists.

What building the picks implies (read after deciding)
  • New CLI verb duo worktree new "<desc>" [--from main] [--here|--window] [--claude] + duo worktree remove <path> — CLI-parity with the UI button (rule 4). 4-surface doc sync (cli/duo.ts, skill/SKILL.md, agents/duo.md, CLI-COVERAGE.md) + rebuild the binary.
  • Pill becomes an always-on trigger — clickable even with a single checkout, so the Create row is reachable from a lone main.
  • Backend — Duo now writes git worktree state for the first time (git worktree add off a base branch, slug collision handling). Lives next to core/git/worktree.ts. Note the CLI bundles core — rebuild on core change.
  • Removal robustness — an ErrorBoundary around the navigator + a vanished-cwd guard + a "revert to main checkout" path in useNavigator. This is the crash-prevention spine of Enhancement 2; needs a regression test (recurring-regression rule).
  • Smoke matrix — add: create-from-lone-main, create-from-worktree, removal-under-foot revert, terminal-in-dead-folder.
