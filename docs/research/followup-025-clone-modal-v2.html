Issue 1 · CSS rendering regression (the bleed-through)

"there are visual artifacts/garbage when the modal renders" — owner v0.7.0 walk

The bg-black/40 backdrop is bleeding through what should be a solid modal body. Underlying smoke-walk page text is visible through the modal.

Suspected causes (in likelihood order):

  1. Tailwind variable not resolving inside modal subtree — modal lives in renderer's React shell; if bg-background CSS variable resolves to transparent in this subtree (z-index parent? CSS-variable scope?), the body looks empty.
  2. Stacking-context / mix-blend-mode interference — body container has opacity or blend-mode somewhere up the chain.
  3. WCV occlusion — unlikely; screenshot shows modal as front layer with text bleeding through, not behind WCV.

Fix is probably one CSS line once root cause is found via duo dom .bg-background --computed background-color,opacity on the modal element. No decision needed for THIS issue — just diagnose and fix.

Issue 2 · Default parent directory

Today, the modal hardcodes const DEFAULT_PARENT = '~/Documents' as the parent dir for clones. Owner wants the Navigator's current cwd to win when present.

Q1 · Right-clicked folder vs. Navigator cwd
If the user right-clicked a folder and chose "Clone GitHub repo here…", should the modal default to THAT folder?

Question: does explicit context (the right-clicked folder) win over implicit (Navigator's current cwd)?

Q2 · Right-click on a FILE (not folder)
Should "Clone GitHub repo here…" appear when right-clicking on a file (not a folder)?

If yes, the default parent would be the file's enclosing folder. Trade-off: visibility vs. mental-model simplicity.
