The shape so far (locked)

The design splits into three layers; Obsidian only ever covers the first. Everything at rest is a plain Obsidian vault — markdown, [[wikilinks]], YAML frontmatter, folders, in git — so any human or agent with no graphbook concept reads it natively. Duo adds capture affordances on top, and Claude is the query/synthesis/processing engine that Obsidian users need a plugin zoo for.

Rollups — the new idea, scrutinized

Click a parent entity (an initiative), see a rendered view of its children's state, populated from their frontmatter. The parent→child edges come free from the locked conventions (Legal review.md carries initiative: "[[Q3 Launch]]"), so a rollup is just “notes whose field points at me, projected onto columns.”

Where the constraints landed after the round-1.5 deep-dive: (1) Vault compat is satisfied — the Bases spec was verified against the Obsidian 1.13.0 docs, and the killer feature is this-aware embedding: a ```base block with initiative == this lives verbatim in the initiative template, so every initiative gets a live rollup with zero per-initiative configuration. (2) The no-sidecar concern is refined, not absolute: a deterministic render stamped with generated-at + source hash is a build artifact (like out/), not a drifting sidecar — staleness is detectable by hash. Whether rollups render live, persist as stamped artifacts, or both is now Decision 6 below.

Working evidence (all in docs/research/graphbook-prototype/): render.mjs — a ~400-line mini-SSG with zero new dependencies — parses the same .base files Obsidian reads and renders all 7 bases with 0 formula errors (row counts hand-verified); the child→parent rollup probes that are unsupported in Obsidian succeed in our renderer by design — same definition file, more capable renderer. lint.mjs derives the corpus from frontmatter (5 types, 22 entities, observed enums like status ∈ {on-track, blocked, done}) and catches typo'd types, unresolved entities, bad enum values, unknown functions and view types — each with a "did you mean". Known Bases boundary (per docs): no joins, summaries are terminal, cross-entity computed rollups unsupported.

Three ways to define a rollup

A · Obsidian Bases Recommended

Rollup definitions are .base files (Obsidian's core dynamic-view primitive — YAML filters + views over frontmatter). Duo parses the same file and renders a richer HTML view.

+ Obsidian renders it too (as a table) — zero divergence

+ no invented query format; agent-legible YAML

− Duo needs a .base parser; Bases syntax bounds expressiveness

B · Duo rollup templates

A Duo-own spec: an HTML/markdown template per entity type (e.g. in templates/) with a small query block; Duo's engine fills it.

+ unbounded layout freedom (status boards, timelines)

− invisible in Obsidian — exactly the divergence trap

− we own a query format forever

C · No engine — Claude ad-hoc

No view engine at all. You ask Claude; it greps frontmatter and generates a disposable canvas page on demand.

+ zero build; works today; infinitely flexible

− seconds, not instant; no click-the-entity affordance

− every view is bespoke; no shared definitions

The rollup lifecycle — who does what

Per the round-2 authoring lock (Claude-from-prose + validator). Every step below exists and ran in the prototype except the two marked future.

YOU owner, in prose or the editor CLAUDE agent actions SCRIPT deterministic CLI (lint / render / L0 schema) FILES what lands on disk

Generate — a new rollup, from prose

YOU
"Show me blocked milestones grouped by owner, due soonest first."
SCRIPT
duo graph schema (L0) — derives the corpus live from frontmatter: types, entities, properties per type, observed enum values. The vault IS the schema; nothing is declared.
CLAUDE
Writes the .base YAML against that corpus — vault-wide views land in bases/; per-entity rollups land as a ```base block in the entity template (initiative == this), so every entity inherits it.
SCRIPT
duo base lint (L1) — structural + expression + corpus checks: typo'd type, unresolved [[entity]], bad enum value, unknown function — each with a "did you mean". Findings loop back to Claude until clean.
SCRIPT
render.mjs — reads frontmatter + the .base, evaluates filters/formulas, emits the stamped artifact: generated-at · source hash · as-of date.
FILES
bases/people-load.base (committed, Obsidian-readable) + out/graphbook.html (build artifact).
CLAUDE
duo open the rendered view in the browser pane.
Iteration is prose → re-emit → re-lint → re-render: "add a due column" never touches YAML by hand. The same .base renders natively (plainer) in Obsidian.

YOU
Normal note work, zero rollup awareness: flip a milestone's status in frontmatter, add a milestone via [[…]] ⇥, rename an entity.
FILES
Frontmatter on disk is now ahead of any persisted render — detectably: the artifact's source hash no longer matches the vault.
CLAUDE
Trigger, today: on demand — you ask, or Claude notices the hash mismatch during work and re-renders.
SCRIPT
Re-render. Invalid refs surface per the round-2 lock: warn + render anyway — a renamed initiative shows a loud ⚠ "did you mean", never a blocked or silently-empty view.
SCRIPT
Future: a chokidar watcher re-renders on frontmatter change (live mode), and/or…
CLAUDE
Future: the scheduled processing job re-renders after filing inbox notes, and proposes fixes for the ⚠ flags it finds (rename maps, closest matches) for you to accept.
Where re-render runs — on open (live), persisted on change (mini-SSG), or both — is exactly Decision 6 below. The lifecycle is identical either way; only the trigger differs.
Decision 1 · Rollup definition format

What is a rollup, at rest in the files?

This is the biggest compat fork in the whole design. A is the only option where Obsidian and Duo read the same definition — and the round-1.5 prototype has now pre-validated it: the spec is verified against current docs, the renderer + linter work over real .base files, and the one confirmed gap (cross-entity computed rollups) is covered by our renderer exceeding the spec. Remaining unknown: the in-Obsidian probe walk.

Decision 2 · Rollup surface & trigger

Where does a rollup render, and what do you click to get it?

"Click the parent entity" today opens its markdown in the editor. The rollup needs its own affordance. All options also get a CLI verb (duo rollup <note>) for parity.

Decision 3 · Processing interaction model

When Claude grooms the graphbook (files inbox notes, fixes links, proposes connections), how do its changes reach you?

Processing is refactoring your thinking — trust matters more than speed. Duo already ships CriticMarkup tracked-changes verbs (duo doc insert/substitute + accept/reject), which were built for exactly this shape of work.

Decision 4 · Capture entry point

How does an inbox note start, in the flow of a workday?

Capture lives or dies on friction. The grain is locked (atomic → inbox); this is the ergonomics of the first keystroke.

Decision 5 · First end-to-end slice

What gets built (or assembled) first?

Sequencing, not scope — everything above stays on the map. Option A ships with zero new Duo code: scaffold the vault + templates, write the graphbook skill, live in it for a week, and let real use pressure-test the conventions before any UI investment.

Decision 6 · Rollup persistence (new in round 2)

Does a rendered rollup live on disk, in memory, or both?

You flagged the mini-SSG idea as worth exploring; the build-artifact framing (stamped generated-at + source hash, regenerable, staleness detectable) keeps it on the right side of the no-sidecar rule. The lifecycle above is identical in every option — only the refresh trigger differs.
