Track changes that compose — net-zero edits & the road to Word-grade suggesting

ENH-260 Decision playground 2026-07-08 · owner report → root-cause probe → editor-landscape research → phased proposal Decisions locked 2026-07-08 All six as recommended — implementation in PR #129.
What this is. The owner reported that deleting text you just added in Suggesting mode shows up as an addition plus a deletion, instead of resolving to nothing. This playground (1) maps the full current implementation, (2) shows the four defects a jsdom probe confirmed — with the actual serialized output, not speculation, (3) compares against how Word, Google Docs, Notion, and the ProseMirror ecosystem handle the same scenarios, and (4) proposes a phased fix with six decisions to lock. Walk the decision cards, hit Copy decisions, paste back to Claude.

1 · The reported bug, in one picture

Baseline text Hello world. Suggesting ON. You type XY after "Hello ", then press Backspace once to remove the Y you just typed.

What Word / Google Docs / every ProseMirror suggest-mode does (expected) Hello Xworld   — the Y simply ceases to exist; the pending insertion shrinks
What Duo does today (observed, jsdom probe) Hello XYworld   — Y carries BOTH marks; the saved file says Hello {++X++}{--Y--}world

The saved form is worse than a cosmetic annoyance: {--Y--} is a CriticMarkup claim that "the original document contained a Y here, and I propose deleting it." The original never contained a Y. After save + reload (authorship is not persisted in standard CriticMarkup tokens), Reject all — which must restore the pre-suggestion baseline — injects the phantom Y into the document. The reject-baseline is corrupted, which is exactly the invariant the reload-diff machinery (trackedDiff.ts, ENH-197) goes to great lengths to guarantee: accept-all ⇒ new doc, reject-all ⇒ old doc, exactly.

2 · How Duo's track changes works today

Track changes is a markdown-editor feature (the canvas has no equivalent — deliberate, BUG-138 family). Five cooperating layers:

LayerModuleRole
Storage format core/markdown/criticmarkup.ts CriticMarkup tokens live in the .md source: {++ins++}, {--del--}, {~~old~>new~~}, {==hl==}, {>>comment<<}. Locked decision (Stage 14b Q3): only comments carry author/ts metadata; ins/del/sub stay plain tokens for compatibility with standard CriticMarkup tooling. Consequence: authorship of insertions/deletions is lost on every save.
Editor marks extensions/InsertionMark.ts · DeletionMark.ts · HighlightMark.ts TipTap marks with author/ts attrs, green-underline / red-strikethrough rendering. Both declare excludes: '' — nothing prevents one text run from carrying insertion AND deletion simultaneously, and no layer defines what that means.
Live suggesting extensions/SuggestingMode.ts Two intercepts: (1) appendTransaction stamps InsertionMark on inserted ranges (typing, paste, IME); (2) handleKeyDown catches only the Backspace and Delete keys and wraps the target range with DeletionMark instead of deleting. Every other content-removal route (type-over-selection, cut, paste-over, drag) falls through to a plain ProseMirror delete.
Round-trip markdownCriticMarkup.ts Load: token text → marks (applyCriticMarkupFromText; authors come back null). Save: marks → token text (materializeCriticMarkupToJSON), folding adjacent del+ins into a substitution. On double-marked text, the mark-classifier loop is last-CM-mark-wins → deletion wins.
Review surfaces trackedChanges.ts · TrackedChangesRail.tsx · SuggestingBanner.tsx Collect / accept / reject, per-change and in bulk, with author filter chips. On double-marked text the collector is first-mark-wins → insertion wins. The rail and the serializer disagree about the same character.
CLI / agent path core/markdown/docEdit.ts → duo doc insert|delete|substitute|highlight|accept|reject Pure text-level ops on the source. Anchors match against the stripped-of-tokens view, but any op whose resolved range overlaps an existing token is refused ("split the operation") — there is no compose path, so an agent cannot delete part of a pending insertion either.

3 · Observed behavior — four probes, actual output

All four scenarios were exercised against the real extension stack (TipTap + SuggestingMode + serializer) in a jsdom vitest probe on this branch. These are observed serializations, not inferences. Baseline for each: Hello world, Suggesting ON, author tester.

S1 · the reported bug
Probe 1 — delete part of your own pending insertion

Type XY, Backspace once

doc:        Hello  [X]{ins}  [Y]{ins+del}  world      ← Y carries BOTH marks
file saves: Hello {++X++}{--Y--}world                  ← phantom deletion of never-existed text
rail shows: one insertion "XY"                         ← disagrees with the file
accept-all: removes ins marks, Y's del mark SURVIVES   ← residual suggestion after "accept all"
reject-all (after save/reload): baseline gains a Y     ← reject-baseline corrupted

Root cause. wrapAsDeletionWithView unconditionally addMarks DeletionMark. It never asks whether the range is a pending insertion, whose deletion should be a real tr.delete.

S2 · silent data loss
Probe 2 — type over a selection (also: cut, paste-over, drag)

Select world, type planet

file saves: Hello {++planet++}          ← "world" is GONE, untracked
reject-all: cannot restore "world"      ← original text lost while Suggesting was ON

Root cause. Only the Backspace/Delete keys are intercepted. A type-over is a ReplaceStep that removes the selection before the insertion-stamper runs; nothing reinstates the removed original as a tracked deletion. Cut (⌘X), paste-over-selection, and drag-out take the same untracked path. The module header claims type-over produces a substitution — it doesn't; that only works if the user separately Backspaces first.

S3 · silent data loss
Probe 3 — Backspace adjacent to an existing tracked deletion

Wrap world as a deletion, then Backspace again

after wrap:       Hello {--world--}
second Backspace: Hello {--worl--}      ← the struck "d" (ORIGINAL text) hard-deleted

Root cause. When the previous char already carries DeletionMark, the handler returns false "so the user can back out of the marked range" — which hands the keystroke to the native delete. Native delete removes the struck original character permanently. Word/Docs skip the caret across already-deleted content instead.

S4 · user input swallowed
Probe 4 — type inside a tracked deletion

Wrap world as a deletion, click into the middle, type Z

doc:        {--wo--} [Z]{ins+del} {--rld--}   ← Z inherits the deletion mark
file saves: Hello {--wo--}{--Z--}{--rld--}    ← Z serialized as part of the DELETION
accept-all: Z vanishes                        ← the text the user just typed is destroyed

Root cause. Inserted text inherits marks at the caret position; the insertion-stamper adds InsertionMark but never strips the inherited DeletionMark — the double-mark ambiguity again, resolved (badly) by last-mark-wins at serialize time.

Two structural defects underlie all four: (i) no composition rule — the delete path never inspects existing suggestion marks, and (ii) no exclusivity invariant — insertion+deletion can coexist on one character, and the three consumers (serializer, rail, accept/reject) each resolve the conflict differently.

4 · How the reference editors behave

Research pass over Word, Google Docs, Notion, and the ProseMirror/TipTap ecosystem (primary sources where reachable; several vendor pages were proxy-blocked and are marked as corroborated-secondhand). The convergence is total — no surveyed system ever shows insertion-then-strikethrough for a same-author edit.

Microsoft Word

  • Same author deletes own tracked insertion → the text simply disappears. Word's design assumption (per MVP forum guidance): if you alter your own change, you no longer want the previous one. Not documented on the official support page — but proven by its inverse: the classic Word bug report is "after save/reopen Word stopped recognizing me as the same author, and now deleting my own inserted text strikes it through instead of removing it" (Microsoft Q&A). Strikethrough-over-own-insertion is literally the symptom of Word's identity matching failing.
  • Different author deletes a pending insertion → nested revision. OOXML encodes it as w:del nested inside the original author's w:ins — both attributions preserved; accept removes the text, reject restores the pending insertion.

Google Docs (suggesting mode)

  • Edits inside your own pending suggestion are not tracked as new suggestions — they amend the suggestion in place (deleting part of your suggested text shrinks it; net-zero if you remove it all).
  • The Docs API confirms the cross-author model: elements carry suggestedInsertionIds/suggestedDeletionIds, and an element holds multiple IDs only for "a suggestion within a suggestion made by a different user" — same-user edits mutate the one suggestion.

Notion (suggested edits)

  • Only the basics are documented (blue underline additions, struck deletions, accept/reject). The delete-own-pending-insertion case is not publicly specified; given the feature is explicitly Docs-styled, net-zero is likely but unconfirmed — Notion is not evidence either way.

ProseMirror / TipTap ecosystem — the algorithm in code

  • Fidus Writer (amend_transaction.js): on delete, ranges where mark.type === insertion && mark.attrs.user === user.id && !approved get a real ReplaceStep(…, Slice.empty) — content vanishes; everything else gets the deletion mark. Typing strips deletion marks from the typed text so it can never inherit one. This is the canonical author-scoped variant.
  • prosemirror-suggest-changes (handlewithcare; forked by BlockNote): implemented as a dispatchTransaction decorator that rewrites every transaction before it applies — so every delete route (keys, type-over, cut, paste, IME, drag) is covered by construction, and undo reverts whole suggested ops cleanly. Deletions of ranges inside insertion marks "will actually be deleted"; mixed ranges are split (inserted parts vanish, original parts get the mark, processed in reverse order); typing inside a deletion is relocated to the end of the deletion range so it never inherits the mark.
  • Tiptap Pro Tracked Changes (official docs, verbatim): "suggested insertions are immediately removed from the document; original content is marked with a delete suggestion." Same-author edits merge into one suggestion; nesting happens only across authors; adjacent deletes coalesce keeping the oldest mark's metadata.
  • CriticMarkup ecosystem: the spec is a serialization format and is silent on live composition; nested tokens are undefined and break most parsers (which is what {++X++}{--Y--} flirts with). criticmarkup-emacs does author-aware adjacency merging — adjacent same-author additions merge, different-author ones don't.

6 · Proposed changes — five phases

Ordered so each phase ships value alone; A is the owner's reported bug plus the invariant that prevents the whole defect class.

Phase AComposition-aware delete + the exclusivity invariant — fixes S1, S3; kills the double-mark state

Rewrite the Backspace/Delete handler as a segment walker over the target range:

for each segment of [from, to):
  has own pending InsertionMark  →  tr.delete(segment)          // net-zero
  already has DeletionMark       →  skip; move caret past it    // never re-delete struck text
  otherwise                      →  tr.addMark(segment, DeletionMark{author})

Process segments in reverse document order (position stability), single dispatched transaction. Add the invariant insertion and deletion marks never coexist on one text node: enforced in the suggesting code paths + a dev-mode assertion + a serializer guard, with property tests (accept-all ∘ suggest-ops ≡ typed result; reject-all ∘ suggest-ops ≡ baseline — the same invariant trackedDiff.test.ts already proves for reload diffs).

Phase BCover every delete route via transaction-level rewrite — fixes S2 (type-over, cut, paste-over, drag, IME)

Move suggesting from key-interception to the transaction layer (the prosemirror-suggest-changes architecture): intercept each user transaction, decompose its ReplaceSteps, and re-emit them as tracked equivalents — removed original content is reinstated with DeletionMark (positioned before the replacement, matching trackedDiff's struck-old-then-new reading order), new content gets InsertionMark, own-insertion removals stay real deletes (Phase A's walker becomes the shared kernel). Backspace/Delete keys then ride the same path, and the keydown intercept reduces to caret/boundary UX. This also makes undo revert whole suggested ops cleanly, since history records the rewritten transaction.

Phase CTyping in/around deletions + adjacency polish — fixes S4; matches Word feel

New text never inherits DeletionMark (mechanism per decision D3). Coalesce adjacent same-author same-kind marks so backspacing char-by-char yields one {--…--} token; fold ins-then-del adjacency into substitutions symmetrically with the existing del-then-ins fold.

Phase DCLI composition — duo doc ops on ranges touching existing tokens — fixes S6; agent parity with the fixed editor (per decision D5)

Teach docEdit.ts the same composition rules at the token level: delete/substitute inside a {++…++} shrinks or splits the token; a range spanning token + original text decomposes into token-shrink + {--…--}; refusal remains only for genuinely ambiguous overlaps (e.g. comment anchors). Same 4-surface CLI sync as any verb-behavior change.

Phase EAttribution policy — resolves the "own vs. foreign" question durably (decisions D1 + D6)

Whatever D1/D6 lock: either stay CriticMarkup-pure (authorship is session-scoped, unattributed marks after reload are treated per D1's policy) or extend the on-disk format with attribution metadata. Rail filter chips, the hook-installed DUO_AUTHOR flow, and the vocabulary doc get updated to match.

7 · Decisions to lock

Decision D1

What counts as "your own" insertion for net-zero deletion?

Every reference implementation nets out same-author deletes and marks cross-author deletes. Duo's wrinkle: standard CriticMarkup tokens don't persist authorship, so after save+reload every insertion mark has author: null. The policy has to say what happens to those. (Word has the same failure mode — identity mismatch after save — and it's reported as a bug there, which argues against treating null as foreign.)

Decision D2

How far do we go on delete-route coverage (Phase B)?

Probe 2 is arguably worse than the reported bug: while Suggesting is ON, type-over / cut / paste-over silently hard-delete original text — reject can't restore it. The fix options differ in cost and coverage.

Decision D3

Typing inside a tracked deletion — where does the new text go?

Today the typed text inherits the deletion mark and is destroyed on accept (probe 4). Both reference behaviors prevent that; they differ in where the caret's text lands.

Decision D4

Backspace/Delete at the edge of an existing tracked deletion?

Today the keystroke falls through to a native delete and permanently removes struck original text (probe 3). The consensus is that struck content is untouchable while suggesting — you traverse it, you don't re-delete it.

Decision D5

Should duo doc delete/substitute compose with existing tokens (Phase D)?

Today any overlap with an existing token is refused ("split the operation") — a dead end for the agent when the overlap is a pending {++…++} it should simply shrink. CLI parity (rule 4) says the agent should be able to do what the fixed editor does.

Decision D6

Attribution on disk — stay CriticMarkup-pure, or persist authorship?

Stage 14b locked "plain CM tokens, authors on comments only" for compatibility with standard CriticMarkup tooling. That's why reloaded marks are unattributed — which D1's recommended option works around. Persisting authorship would make D1 airtight (and enable true cross-author nesting later) at the cost of non-standard source.

Appendix — probe methodology, sources, and edge-case ledger

Probe methodology

A throwaway vitest jsdom suite (same harness as suggestInlineCode.test.ts) instantiated the real extension stack (StarterKit + Markdown + InsertionMark + DeletionMark + HighlightMark + SuggestingMode), enabled suggesting with author tester, and drove each scenario via insertContent / wrapAsDeletionWithView — then captured getJSON(), serializeWithCriticMarkup(), and collectTrackedChanges(). All serializations quoted in § 3 are verbatim probe output. The probe file was intentionally not committed; Phase A turns its scenarios into permanent regression tests.

Consumer-disagreement ledger (the S5 invariant violation)

For a char carrying both marks: serializer (extractCmInfo, last-CM-mark-wins by schema rank) → emits {--…--}; rail collector (collectTrackedChanges, marks.find first-wins) → classifies as insertion; accept-all → strips the insertion mark, leaves a residual live deletion mark (banner count never reaches 0 in one click). Phase A's exclusivity invariant makes all three questions moot by construction.

Explicitly out of scope here

  • Canvas-surface track changes (no analog today; parity disposition (b) surface-specific, consistent with the BUG-138 family).
  • ENH-198 (teaching agents to write CriticMarkup instead of <ins> HTML) — adjacent, unchanged by this work, but Phase D strengthens its recommended option (a).
  • Comment threads ({>>…<<}) — composition rules here don't touch the comment rail.
