What this is. Git worktrees are how agents work in parallel — Claude Code spawns them under .claude/worktrees/<codename>, and users make their own with git worktree add. Duo currently has zero worktree awareness: an agent in a worktree shows up as claude · youthful-chebyshev-885712 and the navigator keeps showing the main checkout. This playground decides which surfaces become worktree-aware and mocks up the visual options. Pick a radio per decision, add notes, hit Copy decisions, paste back to Claude.

The problem in one picture

Today, with two agents in flight (one on main, one in a worktree), the terminal strip and navigator look like this:

❯ duo
✳ claude · duo
✳ claude · youthful-chebyshev-885712
Current state. The worktree tab title is the random codename folder. Nothing says "this is a worktree of duo", which branch it's on, or that the other claude tab is the same repo's main checkout.

Three distinct failures hide in there:

  • Identity — the codename basename carries no meaning. Which agent is doing what?
  • Differentiation — main vs. worktree is invisible. Two claude · duo tabs could be different checkouts of the same repo.
  • File access — the navigator stays rooted at the main checkout, so the files the worktree agent is actually editing are nowhere on screen.

What already exists (grounding)

SurfaceCurrent behaviorRelevant plumbing
Terminal tab Title = claude · {cwd basename}, set at spawn (TabBar.tsx). No git info. Live cwd already polled every 5s via lsof (App.tsx), so a tab's real cwd is known.
Navigator Single root per window; git ribbon shows branch + dirty count of the navigator root only. git.status(cwd) already returns {branch, dirty, ahead, behind, workTreeRoot} — the exact fields a worktree UI needs.
Color system Six-hue project palette (pine/harbor/iris/plum/rose/moss) locked for project-coded UI; hash-stable per root. Reusable as-is for per-checkout hues.
Windows Multi-window shipped (ENH-191); duo --window N addressing; per-window navigator + session state. A worktree-per-window mapping is mechanically possible today.
CLI No worktree verb; duo status / duo nav state don't report checkout identity. git worktree list --porcelain gives the full sibling map cheaply, read live (no sidecar — rule 12).

One nuance that shapes everything below: for Claude-managed worktrees, the branch is also a codename (claude/youthful-chebyshev-885712). Showing the branch instead of the folder fixes human-made worktrees (fix-auth-flow) but not agent-made ones. The only truly meaningful identity for an agent worktree is what the agent is working on — which suggests label support, not just better git-string plumbing.

Decisions

Decision 1 · Scope

Which surfaces become worktree-aware in v1?

This sets the sprint's blast radius. Terminal-only is a badge change; adding the navigator changes root-switching behavior; "all surfaces" adds provenance badges to working-pane tabs (the same file open from two checkouts looks identical today) and window affordances. Later decisions detail each surface — this one decides what ships first.

Built: both the terminal tab badge and the navigator Worktrees section shipped. Working-pane provenance badges (the "all surfaces" option C) stay deferred.

Decision 2 · Tab identity

What should a worktree terminal tab's title say?

Today: cwd basename. The candidates below differ in what they treat as the tab's "name". Remember the nuance above — for agent-made worktrees the branch is a codename too, so option D adds a human-editable label on top of whichever git-string default you pick.

✳ claude · youthful-chebyshev-885712
Current. Folder basename — meaningless codename.
✳ claude · ⎇ fix-auth-flow
Option A — branch replaces basename. Great for human-made worktrees; for agent worktrees the branch is claude/youthful-chebyshev-885712, so it degrades to the same codename (Duo would strip the claude/ prefix).
✳ claude · duo ⎇ fix-auth-flow
Option B — repo name + branch chip. Anchors identity to the repo ("this is duo"), branch rides along as a chip. Widest tab; chip truncates on overflow.
✳ claude · auth refactor ⎇
Option D — editable label. Double-click (or duo tab label) renames the tab; default is option B's string until renamed. The agent itself could set its label from its task ("auth refactor"). Glyph keeps the worktree marker.

Partial: v1 ships the default identity — the ⎇ marker + a "Worktree of repo · ⎇branch" tooltip (the B-string). The editable rename (double-click / agent self-label CLI) is DEFERRED. Decision 5 · Lifecycle & CLI

Does Duo manage worktrees, or just display them?

Everything above is read-only awareness. The next rung is verbs: the agent (and the user via UI — parity rule 4) creating, listing, and cleaning up worktrees through Duo. Claude Code already creates its own worktrees, so creation may be redundant; cleanup and "spawn me a parallel agent over there" are the genuinely new powers.

Partial: duo worktree [list] shipped + 4-surface-documented (client-side git read, sandbox-tolerant). getGitStatus now carries isLinkedWorktree/mainWorktreeRoot/repoName, but those fields are NOT yet surfaced in the duo status / duo nav state JSON output — small follow-on. Note here if you want that wired before cut.

Decision 6 · Windows

Should worktrees map to windows (ENH-191), or stay as tabs in one window?

Multi-window shipped with a blank-second-window philosophy. A worktree-per-window discipline gives total isolation (own navigator, own browser, own terminals per checkout) at the cost of window sprawl and weaker cross-checkout glanceability.

Deferred — adjacent questions intentionally not decided here
  • Merge/cleanup UX. "This worktree is ↑3 ahead, dirty, branch merged on origin — prune?" A whole lifecycle surface (diff vs. main, merge gesture, stale-worktree detection). Needs its own PRD once awareness lands; D5-C is the gateway.
  • Working-pane provenance. The same file open from two checkouts is indistinguishable in the canvas tab strip. The fix mirrors D3-B (hue dot on working tabs) — folded into D1-C if chosen, else deferred.
  • Dirty/ahead-behind badges on terminal tabs. The git snapshot has the data; a ✱/↑ tick on the tab is cheap but risks tab-strip noise. Revisit after D2/D3 land and we see real density.
  • DUO_WORKTREE awareness in hooks. The PreToolUse edit-through-Duo hook and skills could behave differently inside a worktree (e.g. don't warn about files open from a different checkout). Mechanical once D5-B fields exist.
  • Discovery edge cases. Nested .claude/worktrees/ vs. sibling-folder worktrees vs. bare-repo layouts; all read live from git worktree list --porcelain so the UI never caches a stale map (rule 12).
