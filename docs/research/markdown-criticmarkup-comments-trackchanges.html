Markdown comments + track-changes via CriticMarkup

BUG-138 Stage 14b–d Sprint 18 architectural gate. 6 decisions owed before code.
Why this is urgent. v0.7.0 ships markdown comments stored in a sidecar <file>.md.duo.json. Owner: "comments that sit outside the file will not be obvious to the agent when it inspects the file." Comments are also lost when the markdown file moves without its sidecar, and invisible in any other editor.

What this gate decides. Migrating to CriticMarkup — the standard markdown convention for comments + track-changes — solves agent-visibility, portability, and unifies the parser/serializer for Stage 14b (track changes) + 14c (Suggesting toolbar) + 14d (agent CLI verbs). Pulling all of Stage 14 forward as one coherent chapter. This playground locks the 6 architectural decisions before we start coding.

CriticMarkup — the standard syntax

CriticMarkup defines four edit operations + a comment marker. Already implemented in Obsidian, Marked, Ulysses, IA Writer, and other markdown tools. Going inline means Duo's comments + track-changes round-trip through any compatible editor + are visible in raw markdown.

The five operations

{++inserted text++} renders as inserted text (insertion).

{--deleted text--} renders as deleted text (deletion).

{~~old text~>new text~~} renders as old textnew text (substitution).

{==highlighted text==} renders as highlighted text (highlight; pairs with comment for anchoring).

{>>comment body<<} renders as 💬 at the position (comment). Body shown in rail / hover.

{==anchor text==}{>>comment body<<} renders as anchor text💬 (comment anchored to a highlighted range).

Current vs proposed

❌ Current (v0.6.7+ via sidecar JSON)

foo.md
─────────────────
This is the body text.
The agent reads only this.

foo.md.duo.json  (separate file)
─────────────────
{
  "comments": [{
    "id": "c-01",
    "body": "Reconsider this section",
    "excerpt": "body text",
    "author": "dudgeon",
    ...
  }]
}
  • Lost when foo.md moves without sidecar.
  • Invisible to the agent doing Read foo.md.
  • Not portable — other md editors render clean text.

✅ Proposed (inline CriticMarkup)

foo.md
─────────────────
This is the {==body text==}{>>id:c-01|author:dudgeon|ts:2026-05-18T12:34:56Z|Reconsider this section<<}.
The agent reads {++ALL of++} this.

foo.md.duo.json  (sidecar — for non-comment metadata only)
─────────────────
{
  "version": 1,
  "recentEdits": [...]
}
  • Travels with the file.
  • Visible to the agent + any other markdown reader.
  • Portable — works in Obsidian / IA Writer / etc.

Decisions to lock

Q1 · Metadata body structure
How do we embed Duo-specific metadata (id, author, timestamp, reply-to) inside CriticMarkup's body?
CriticMarkup itself doesn't define metadata. We need an opinionated extension. The body must round-trip through any CriticMarkup-aware reader without breaking — readers should still see SOMETHING reasonable.
Q2 · Track-changes scope for v1
Which CriticMarkup operations ship in the v1 chapter?
All four operations + comments use the same parser/serializer. Shipping all five is roughly the same coding effort as shipping the parser/serializer for one. The trade-off is UI surface — Suggesting toolbar mode (Stage 14c) per-operation.
Q3 · Author attribution model
Who authored an edit / comment? How do we encode it?
Owner directive: "will need author attribution at least for human and agent." Question is granularity — bare two-role, name-aware, or fully free-form.
Q4 · Agent CLI verb shape (Stage 14d)
How does the agent record its own changes as tracked edits via the CLI?
Owner directive: "need a duo verb for the agent to use track changes for own changes." Question is API ergonomics — explicit per-op verbs, flag on existing write, or auto-diff.
Q5 · Migration trigger for existing sidecar comments
v0.6.7+ users have comments in sidecars. How do we migrate them to inline CriticMarkup?
Each file with sidecar-comments needs a one-shot migration. The re-anchor logic to find where each comment goes in the markdown body already exists; we just need to write the CriticMarkup at those positions.
Q6 · Backward-read tolerance
Once Sprint 18 ships, how does Duo treat OLD sidecar-only comments (e.g. on a file the user hasn't opened since v0.6.x)?
If we hard-cut, files with sidecar-only comments lose them on first open until they get re-migrated. If we tolerate forever, we ship dual-read code for the long haul.

Out of scope (for this gate)

  • Canvas (HTML) comments architecture. Same agent-visibility argument applies but the migration shape differs — HTML can persist comments in custom attrs or comment elements. Sibling decision deferred to a separate playground after BUG-138 lands.
  • Suggesting toolbar mode visual (Stage 14c). When user toggles "Suggesting on," edits are wrapped as track-changes by default; visual treatment matches Google Docs / Word. Locks in implementation once the parser/serializer is done — visual decisions can wait.
  • Side-by-side diff view. Some users will want "view with all suggestions applied" / "view with all rejected" / "side-by-side." Pure UI feature; can come after the data model is stable.
