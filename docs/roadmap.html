Stage 17a.5 candidate — fresh-blank UX + template system

🟡 Owner committed direction F (markdown shortcuts on typing) 2026-04-26 night · directions A–E remain on the books · F's work item lives in the polish & parity card below

The problem. 17a's H17 boilerplate is a single <h1> + empty <p>. Opening a fresh .html is flatter than opening a fresh .md (which at least gets ProseMirror's placeholder hint and discoverable markdown shortcuts). The whole reason to use HTML over MD is structured layout — callouts, comparison tables, status tables, mini-dashboards, embedded checklists, image+caption blocks — and none of that is suggested by what 17a opens with.

The owner's gesture. "Something like a Notion UI with modules for content" — block-based composition with a snippet library, slash-menu insertion, etc. And: users should be able to design and define their own templates / modules.

Five directions explored (subagent, 2026-04-26):

  • A. Curated starter gallery. Fresh .html opens an interstitial picker with 5–8 canonical doc shapes (Status report, Comparison memo, Decision log, Meeting notes, One-pager, Research findings, Launch checklist, Blank). Pick one, get a fully styled, semantically structured page with placeholder copy that reads like a real document. v1: 3 hard-coded templates under electron/templates/html/. Story: ⌘N → report.html → Enter → picks "Status report" → page appears with date / summary / status table / risks pre-skeletoned → types over.
  • B. Live block library with / slash menu. Boilerplate stays minimal-but-tasteful (a real H1, a "/" placeholder line). Discovery happens through the slash menu: callout, table, card grid, status badge row, stat tile. Each block lands as a styled, editable HTML island. This is the Notion mental model. v1: ship 5 of the H18 snippets behind /, inline-styled (no Tailwind dep). Story: ⌘N → blank doc → types /call → picks Callout → fills it → types /comp → comparison table.
  • C. AI-drafted-on-prompt. Fresh .html opens an interstitial that asks "What do you want to make?". Submit → agent drafts a complete styled page using duo html set (17b) → user edits in canvas. Most flagship-persona-aligned, but doesn't help when the user has nothing in mind yet. Story: ⌘N → q2-update.html → "Q2 status update for the platform team, 3 risks, GREEN overall" → ~6s later, drafted page opens.
  • D. Smart-blank with baked-in onboarding. Boilerplate stays bare visually but the page mounts with an inline overlay: "Press / for blocks · Pick a starter ↗ · Ask the agent to draft this for you ↘". Dismisses on first keystroke. v1: static overlay over the existing 17a boilerplate, ~50 LOC. Pairs with anything; doesn't compete.
  • E. User-defined template registry (cross-cutting). Templates live in ~/.claude/duo/templates/html/*.html (global, mirrors external-domains.json precedent) with optional per-project overlay at <repo>/.duo/templates/html/. Each template is just an HTML file with a <meta name="duo-template" content='{"label":"…","preview":"…"}'> tag. New CLI verbs: duo html template list / save <path> / use <name>. "Save current as template" lives in the canvas overflow menu. This isn't its own direction — it's the storage substrate that makes A, B (block packs), and C (agent-learnable conventions) extensible. Without it, A is hard-coded forever.
  • F. Markdown shortcuts on typing (added & committed 2026-04-26 night). When the user types # at line start → wrap line in <h1>; ## → <h2>; - → bullet list; 1. → ordered list; > → blockquote; **bold** / _italic_ → inline marks; ``` → code block; --- → hr. Reuses the same muscle memory PMs already have from Stage 11's TipTap input rules — minus TipTap (PRD H3 rejects ProseMirror for the canvas because the canvas must accept arbitrary HTML and ProseMirror's strict node model can't tolerate that). Owner rationale: "ProseMirror parsing existing HTML, which is more expressive than markdown, sounds really hard. But when the user is typing, we should parse for markdown and style accordingly." So the implementation listens for keydown-on-space (or Enter) and does targeted DOM rewrites at the caret — local, line-scoped, no full-document parse. ~few-hundred LOC of regex + DOM mutation in the same inlineMarks.ts-style module. Doesn't depend on Tailwind / scripts / 17b's IDs / templates. Slash menu (B / PRD H29 / 17e) still ships as additive — F gets you headings + lists + inline marks fast; B gets you styled component blocks (callout, comparison table, status badge) that have no markdown analog.

Selection logic:

  • Least-regret first ship: D + a 3-template seed of A. Smart-blank overlay routes the user to whichever direction matures fastest; three real templates immediately beat the markdown bar. Neither commits the architecture: the overlay is a CSS layer, the 3 templates are 3 files. ~1 PRD.
  • Additive (compose freely): A, B, C, D all stack. A doc can be picked from a starter (A), then have blocks inserted (B), then have a section drafted by the agent (C). Smart-blank (D) is the entry surface. E underlies A/B/C without conflict.
  • Exclusive trade: Only between flavours of B. Tailwind-bound blocks (waiting for 17e script-opt-in) are prettier but block 17a-era users; inline-styled blocks ship today but accumulate visual debt. Pick once, hard to retrofit.
  • PRD mapping: A → new sub-stage 17a.5 (template loader + 3 seeds, ~1 PRD). B → already specced as 17e; lift inline-styled v1 forward to 17b alongside duo html set. C → new sub-stage 17f (agent draft path). D → fold into 17a polish; ~50 LOC, no PRD needed. E → new cross-cutting verb (17b scope, 1 PRD section). Needed before A scales past 3.

Friction points worth flagging:

  • A: if the user picks "Status report" then deletes everything, they've wasted a click. Mitigate with a "Start blank" entry that's visually equal-weight, not buried.
  • B without templates: every doc starts looking the same. Templates reintroduce variety on top.
  • C: what happens on agent error? File half-written. Need transactional duo html set (already in 17b spec) + a "regenerate" affordance.
  • E: no per-project templates dir → fall back to global silently. Empty global → fall back to bundled. Three-tier resolution should be invisible until something fails.
  • Tailwind dependency: if B ships inline-styled, the H18 spec needs a "v1 inline / v2 Tailwind" split documented now, or the team will re-litigate it at 17e.

Subagent's specific first-ship recommendation: ship D + A-seed (3 templates) as 17a.5. Smart-blank overlay with three doors: "Press / for blocks (coming soon)" greyed, "Start from a template ↗" linking to a sheet showing Status / One-pager / Blank, "Ask the agent ↘" greyed. One door is real, two foreshadow B and C without committing to them. The 3 templates live at electron/templates/html/; the registry move (E) happens when the 4th template is requested. Beats the markdown bar without locking the project into Notion-clone, AI-first, or template-marketplace territory.

Stage 17d-B — Lock convention (PRD H19)

⬜ Small. Renderer-only. No CLI surface. Defers cleanly from 17d-A.

The intent. When Duo (or Claude) authors HTML using the H17 boilerplate + H18 component snippets, structurally important elements — the body grid, navigation, footer scaffolding, the outer wrapper of a callout / comparison-table / card-grid — get an opt-in data-duo-lock="structure" attribute. The lock is a convention the editor honours, not a parser-level constraint: the user can still type into descendant text, but the locked element's tag, attributes, and child structure are protected from accidental human edits (drag-to-reorder, keyboard-mediated tag swaps, paste-replacing).

What ships.

  1. Hover affordance. Hovering an element with data-duo-lock="structure" renders a subtle dashed outline (Atelier --paper-rule token) + a small tooltip near the cursor: "Structural element — text editable; layout locked." Implemented via a single delegated mouseover/mouseout listener on the iframe body (no per-element listener); the runtime DOM (outline + tooltip) carries data-duo-canvas-runtime so the serializer scrubs it.
  2. Edit guard (the load-bearing piece). The canvas's MutationObserver gets a pre-write check that walks the mutation target's ancestor chain; if any ancestor carries data-duo-lock="structure" AND the mutation type is structural (added/removed children that aren't text nodes, or attribute changes other than class/style), the mutation is reverted (PM/Yjs would call this an undo; we just reapply the previous serialized state for that subtree). Text-node mutations always pass through. Edge case: agent-driven duo html set/replace/append against a locked element should ALSO be guarded — surface a clear error ("Element #<id> is locked. Use ⌥-click in the canvas to override, or remove the data-duo-lock attribute first."). The CLI's existing html-op handler in htmlOps.ts grows the same ancestor walk.
  3. ⌥-click override. Holding ⌥ while clicking a locked element enters "edit lock" mode for the duration of that selection — the dashed outline goes solid (visual confirmation), the edit guard pauses for that subtree until selection moves elsewhere. Implemented via a small per-element data-duo-lock-overridden sentinel that the edit guard checks alongside data-duo-lock. The override is ephemeral; the serializer never persists it.
  4. Toolbar affordance (optional). When the user's selection is inside a locked element, the toolbar grows a "🔒 Unlock element" button (or "🔓 Lock element" for unlocked). Click toggles the data-duo-lock="structure" attribute. Defers cleanly — the ⌥-click override + the agent's CLI cover most cases. File as 17d-B follow-up if it doesn't fit naturally.

Open question — where do locks come from? The H17 boilerplate (shared/html-boilerplate.ts) currently emits a flat <body> with an <h1> + empty <p> — no <header>/<main>/<footer> wrappers, no locks. 17d-B's value lights up only when the snippet bundle (17d-C) starts emitting locks on snippet outers, AND the H17 boilerplate grows the semantic body wrappers from PRD H17. Recommended sequencing: 17d-C first (or alongside) so locks have something to lock; ship 17d-B as the editor-side honour-the-convention layer once the convention exists.

Out of scope for 17d-B. A "locks panel" sidebar listing all locked elements; bulk lock/unlock UI; per-attribute lock granularity (data-duo-lock="tag-only" etc.); locks that survive across snippet replacement. All defer cleanly.

Browser-pane file:// auto-reload (BUG-130)

✅ Shipped v0.7.1 (2026-05-18). Approach A: chokidar watcher per file:// tab in BrowserManager, 250ms debounce, idempotent across nav-in-page, cleaned up on tab close. Use a different rendering surface (e.g. an Electron BrowserWindow with custom http:// server fronting the local files, or a WCV with a content-script extension that intercepts file:// loads).
