1. What we're styling — the surfaces in question

Three visible elements compose the Split View:

  1. Aux header — the chrome bar above the aux content. Holds the file name, a "promote to main" button, and a close button. Optional in some options.
  2. Divider — the visual affordance between main and aux. Drag-to-resize. Affects how "permeable" the boundary feels.
  3. Aux container — background, border, shadow. Determines whether aux reads as a peer pane or as a subordinate companion.

Each option below makes different choices on these three axes. The mocks are CSS-driven; what you see is approximately what would render in the live app, scaled down.

Option A — symmetric slim header, paper-deep background, peer to main.

Pros
  • Already built; no further work.
  • Reads as a peer pane — the user can treat aux as "another doc I'm editing."
  • Simple structure; easy for v2 (Option B per spec) to add a tab strip.
Cons
  • Doesn't visually signal "companion / transient" — feels like a permanent split.
  • "SPLIT" all-caps is utilitarian, not Atelier; reads as engineery.
  • Drift away from Slack's "subordinate aux" metaphor — but that's a UX intent question, not a constraint.

Option B — Subordinate companion (Slack-faithful)v1

Aux gets a 3px --accent left rule (like Slack's thread sidebar). Header is transparent — no fill — with the filename in italic serif. Smaller chrome height (26px). The accent rule is the visual signal that this is companion content, not a peer.

Option B — accent left rule, italic serif filename, transparent header.

Pros
  • Faithful to the locked Slack-style intent ("transient companion").
  • Atelier-coherent — italic serif matches the rest of the typographic register.
  • Minimal chrome height; max content area.
  • Accent rule signals split-view boundary even when aux header would scroll out.
Cons
  • Italic serif on a tab name might read as "this is special" rather than "this is a working tab."
  • No "SPLIT" label means the user has to recognize the accent rule as the signal — slightly less explicit.
  • Transparent header could blend with the canvas content underneath if the aux file has heavy top decoration.

Option C — no header, floating close circle, right-click for promote.

Pros
  • Most content space — every pixel goes to the file.
  • Cleanest visual register; least "chrome."
  • Clear differentiation from main — the absence of a header is itself a signal.
Cons
  • No filename visible — user has to infer what's in aux from content.
  • Promote is hidden in right-click — discoverability problem.
  • Floating button can be confusing on dark canvases; needs careful contrast handling.
  • If aux content scrolls, close button stays put — but loses the "this is the aux" anchor.

Option D — full tab strip in aux with a "SPLIT" indicator. Identical structure to main; ready for v2 multi-tab.

Pros
  • Symmetric structure — both panes have tab strips, easy to learn.
  • Zero migration cost when v2 (multi-tab aux, locked spec § 5.3) ships.
  • Promote/close fit naturally as right-click menu items on the single tab.
  • The "SPLIT" indicator pill is a small but visible badge.
Cons
  • Doubles tab-strip cognitive cost in v1 — two strips to attend to even though aux has one tab.
  • Pre-pays UI complexity for v2 that may never ship.
  • Reads as "two separate working areas" rather than "main + companion."
  • "SPLIT" indicator doubles up with the file tab — feels redundant.

Option E — drawer shadow, accent pill badge, no structural divider.

Pros
  • Strongest "transient companion" signal — feels temporary, removable.
  • Matches a familiar UX pattern (sheets, drawers in iOS / Material).
  • Accent pill is more decorative than the all-caps "SPLIT" label.
  • No drag-divider on the boundary; resize is a hover-only handle that appears on the shadow.
Cons
  • Most visually "different" from current Atelier — adds a shadow, which the rest of Duo doesn't use heavily.
  • Resize handle is harder to find (shadow isn't a clear drag affordance).
  • Dark-mode shadow needs careful handling — shadows on dark are tricky.
  • Most implementation work — shadow + handle + boundary detection.

4. My recommendation

Option B — Subordinate companion

Pivot from the current Option A by adding a 3px accent left rule to the aux pane and switching the filename to italic serif. Drop the all-caps "SPLIT" label. ~30 min of CSS work.

Why B over A (current): the locked Slack-style spec calls aux a "transient companion" — Option A's symmetric register doesn't carry that signal. The accent rule is the cheapest way to add it without spending the v2 tab-strip implementation cost up front.

Why B over D (tab strip): v2 (multi-tab aux) is queued but not committed. Building the tab-strip-in-aux now pre-pays UI complexity for a feature that may never ship. When/if v2 lands, adding a strip is ~3 hours — not enough to justify shipping that complexity now.

Why not C or E: C hides the filename, which I think is too aggressive — users want to know what's in their split. E adds a shadow that doesn't fit Duo's flat-paper Atelier register. Both are "extreme companion" patterns; B is the moderate companion signal that still keeps everything visible and discoverable.

  • "Switch to B" (recommended) — accent left rule + italic serif filename + drop "SPLIT" label. ~30 min CSS edit.
  • "C" — minimal floating chrome. ~1 hour rework.
  • "D" — full tab strip in aux. ~3 hours; pre-pays v2 cost.
  • "E" — drawer / sheet feel. ~2 hours; introduces shadow to the design system.
  • Mix — e.g. "A's header chrome with B's accent left rule" — call out the combo.
