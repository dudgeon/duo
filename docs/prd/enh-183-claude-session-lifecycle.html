ENH-183 — Claude session description lifecycle

PRD · canonical Supersedes ENH-177 + ENH-181 PRD · Reopens ENH-180 (in limited form) · Sprint 21 / v0.7.9 · Filed 2026-05-24
What this is. The single canonical PRD for how Duo represents a Claude session as a first-class concept attached to each terminal tab — from the moment the session is born, through naming, collapse, restoration, and exit. It replaces the old ENH-177 + ENH-181 PRD (which scoped only workspace-resume) and reopens a narrower form of ENH-180's scope (Duo-driven /rename injection, using free signals — no LLM call).
The reframe (owner directive 2026-05-24). "Terminal/session descriptions are a core feature and we should think through their lifecycle, beyond session save/loading, which is a relatively niche feature." The old PRD treated the banner as a workspace-resume feature with a tab marker bolted on. This PRD treats the session header as a polymorphic surface above each terminal tab — workspace save/restore is one trigger on the surface, not its raison d'être.

1 · Mental model

Each terminal tab in Duo has a session header — a polymorphic surface above the xterm body whose contents depend on whether a Claude session is live in the tab, whether prior Claude sessions exist in the tab's CWD, and what title (if any) the current session has earned. Think of it as the tab title for a Claude session: emergent from work, lightly user-tunable, absent when the work doesn't warrant one.

The session header is quiet by default. Generic shell tabs (no Claude, no Claude history) show no header at all. Tabs that have or once had a Claude session show a small marker on the tab itself and (optionally, on click) an expanded banner in the pane.

Writes to the session title — by user click-to-rename, by Duo's automatic hydration at trigger points, or by Claude's own Haiku summary — all flow through one primitive: /rename <title> via PTY injection. The slash command is the universal write path; Duo, the user, and Claude itself all use it. Reads are a cheap ladder over sessions-index.json with a JSONL fallback when the index is missing.

2 · The state machine

S0 · Quiet claudePresence !== 'claude'
AND no JSONL files exist in ~/.claude/projects/<encoded-cwd>/ No header. Terminal pane is unchanged. Most generic shell tabs.
S1 · Pills claudePresence === 'claude'
AND current session's messageCount === 0
AND ≥1 prior session JSONL exists in the CWD Header shows previous sessions as clickable resume pills. Auto-dismiss on first Return submitted to the new session (D1). § 6 has three mockup variants.
S2 · Named claudePresence === 'claude'
AND a usable title exists OR Duo has auto-hydrated one Tab marker dot by default; click expands to the full banner (title + Save workspace + dismiss). Edit mode on title click. Title is just a title — no provenance badge, no sidecar tracking who wrote it (D9 architectural invariant). User can click and re-rename at any time.
S3 · Restore offer claudePresence !== 'claude'
AND workspace metadata has a lastClaudeSession.id for this tab Header shows "This tab had: <title> — Resume?" with a primary Resume button. Clicking writes claude --resume <uuid> to the PTY. Once claude is running again, transitions to S2.

Note on provenance. S2 has no provenance badge and no sub-states. Once a title lands in Claude's storage (in customTitle via user-driven or Duo-driven /rename, or in summary via Claude's Haiku) it's just a title. Duo does not track who wrote it — see D9 for the architectural invariant. If the user wants to change the title, they click it and re-rename. The same affordance handles all cases.

3 · The /rename primitive (write path)

All session-title writes go through one mechanism: inject \r/rename <title>\n into the live Claude PTY for the tab. Claude processes the slash command, persists the result, and any watchers see the update on the next file-watch tick.

Two invocation modes share the wire:

ModeTriggered byTitle source
User-driven Click banner title → contentEditable → Return Whatever the user typed. Bypasses derivation.
Duo-driven Hydration triggers in § 9 (msg-count threshold, manual workspace save, first session capture) Computed by the D8 derivation ladder — free signals (first user message from JSONL), no LLM call from Duo.
Why PTY injection, not direct file write. Claude owns the persistence layer. If the schema or storage location ever changes, our injection still works because Claude itself performs the write. The 2-line transcript footprint (the /rename line + Claude's ack) is the cost; zero schema coupling is the benefit. Locked in old ENH-181 PRD; carried forward as D7.

4 · The title-derivation ladders

Two ladders run at different times: the read ladder (D5) executes every time the banner renders; the write ladder (D8) executes when Duo needs to invoke /rename to hydrate an unnamed session. Both ladders read exclusively from Claude's own storage (sessions-index.json + JSONL files) — Duo does not maintain a sidecar (D9 invariant).

Read ladder — what the banner displays

RungSourceNotes
1Latest {"type":"custom-title","customTitle":"..."} JSONL entrySet by either user-driven or Duo-driven /rename. Duo doesn't track which — see D9. Title is just a title. Scan JSONL in reverse, pick the last match (most recent rename wins).
2Latest {"type":"ai-title","aiTitle":"..."} JSONL entry Claude's Haiku auto-summary. Surfaces as summary field if a derived sessions-index.json exists (legacy projects only — most newer projects don't maintain that file; see C1 empirics).
3First user message from JSONL (live-read, no persistence)Used when both above entry types are absent. Read fresh every render; not cached (D9).
4Short UUID (first 8 chars of session UUID)Last resort for very-new sessions with no user message yet.

Write ladder (D8) — what title Duo injects when hydrating

  1. Skip — already hydrated. If customTitle or summary already exists, no /rename is needed.
  2. First user message from JSONL, cleaned + truncated. Cleaning: strip <ide_opened_file>…</ide_opened_file> wrappers, collapse whitespace, drop leading "please " / "could you " filler. Truncate to ~60 chars on a word boundary.
  3. Other JSONL signals (first assistant message, first non-system entry) if user-message extraction yields nothing useful — rare edge case.
  4. Don't /rename to a UUID. If the JSONL has no usable content, do nothing; banner displays the UUID via the read ladder.
Why first-user-message is high signal. Empirical sample from this session (16 projects, 20 sessions, 80% summary coverage): every unnamed session had a firstPrompt field that read as a usable title (e.g. "this is interesting -- the app definitely works but the ux i...") — sometimes more direct than the Haiku summary. Free signal; no LLM call needed.

5 · S0 — Quiet

No header. The terminal pane renders xterm content directly. This is the default for any tab the user opens fresh in a CWD that has never hosted a Claude session. No visual, no state, no CLI hook.

6 · S1 — Resume pills (the new behavior)

When the user starts a Claude session (claude, duo new-tab --claude, etc.) in a CWD that has ≥1 prior Claude session JSONL, the session header offers those prior sessions as pills in the same physical space the banner uses. The user can click a pill to resume that session instead (Duo writes claude --resume <uuid> to the PTY). If they ignore the pills and send their first message to the new session, the pills auto-dismiss — the user has signaled they want the new session, not a redirect.

Pills mechanics (shared across variants)

  • Auto-dismiss: first Return committed to the new Claude session (D1).
  • Explicit dismiss: click × (or "Dismiss · keep new session" in Variant B). Pills don't reappear for this session; next fresh session in the same CWD re-shows them.
  • Throttle: if the user dismissed pills less than 5 minutes ago in this CWD, don't reshow on a Claude restart (avoids flicker on crash-restart).
  • Pill order: most-recent first by modified timestamp in sessions-index (or JSONL mtime when index is absent).
  • Show how many: first 3 visible; rest behind "+ N more" / "show all" (D10).

9 · Hydration triggers (the full lifecycle)

The places where Duo invokes /rename automatically:

TriggerConditionTitle derivation
T1 · Idle-threshold messageCount ≥ 3 AND no customTitle AND no summary D12 ladder (first user message from JSONL)
T2 · Manual workspace save User clicks "Save workspace" or chord ⌘S; for each captured tab session that is unnamed D12 ladder; fire-and-forget per-tab
T3 · First session-UUID capture Session tracker observes a new lastClaudeSession.id for a tab; before persisting to workspace metadata, attempts hydration if unnamed D12 ladder; ensures restored tabs always have a name

Autosave does NOT trigger hydration. Captures session UUIDs only. Hydration on every autosave tick would spam the PTY transcript. Save-on-demand earns the cost (D6).

Duo never injects /rename when claude isn't live in the tab. No claude PTY to write to. Hydration only applies to live sessions.

D9 · No Duo-side metadata sidecars (architectural invariant) Locked
Where does Duo store anything it knows about a Claude session — provenance, title cache, message-count cache, hydration history, etc.?
Nowhere of its own. Duo does not maintain any sidecar file, cache, or auxiliary data structure that mirrors, annotates, or extends Claude session metadata. Concretely:
  • The only Claude session writes Duo performs are via /rename PTY injection — which Claude itself persists into its own storage (D4 + D7).
  • All session metadata reads come live from Claude's storage (sessions-index.json + JSONL files). Read every render; never cached on disk.
  • Duo's workspace metadata holds only the per-tab lastClaudeSession.id pointer. It does NOT cache titles, provenance, message counts, hydration history, or any other derived Claude-session field.
  • In-memory renderer state (pills-dismiss throttle, collapsed/expanded flag, edit-mode flag) is allowed but never persisted to a Duo-owned file. Resets on Duo restart.
  • Consequence: no AUTO badge / no provenance tag in the UI. Once a title lands in customTitle we can't tell who wrote it — and that's fine. Title is title. User can click and re-rename any time.
  • Capture-on-evidence-not-speculation (post-walk-1 addition). The single Duo-owned field (lastClaudeSession.id in workspace metadata) is also gated: Duo only captures it for a tab that actually hosted a Claude process during this Duo session — i.e. claudePresence transitioned to 'claude' or 'starting' on that tab. Tabs that simply exist in a CWD with recent JSONLs do not inherit the cwd's most-recent UUID. This prevents S3 ("This tab had: …") from mis-firing on tabs that never had anything. The renderer-side equivalent: an in-memory tabsThatHostedClaude: Set<tabId> updated by the claude-presence probe. Pre-existing pointers from disk (workspace-restore case) are preserved — that's the only legitimate carry-forward across Duo sessions.
Owner directive 2026-05-24: "session name should live in the Claude metadata, not annexed off in some duo specific data structure — your proposed approach risks file system ↔ Claude metadata drift." Earlier drafts proposed ~/.claude/duo/hydrated-sessions.json to power an AUTO badge; that's been removed. If Claude's storage migrates, gets deleted, or is hand-edited, Duo reads the new state on next render — no stale Duo sidecar to invalidate. This invariant also applies to all OTHER fields we read from sessions-index.json: summary, messageCount, firstPrompt, modified, etc. are read fresh, never cached.

14 · Risks + edge cases

R1 · sessions-index.json missing
Active duo project doesn't have one. Renderer must not crash or UUID-only when JSONL would have a derivable title. Mitigation: D5 rung 3 (JSONL live-read) + D8 derivation ladder.
R2 · /rename writes elsewhere than expected
Step 0 verification is gating. If /rename writes to a field other than customTitle, both D5 read ladder and D8 derivation target need adjustment.
R3 · Pills feel noisy to repeat users
A user who starts new sessions often sees pills every time. Mitigation: D10 caps at 3 visible + 5-min dismissal throttle. Future: per-CWD learning "user dismisses X% → auto-hide."
R4 · Restore race — claude not yet running
Workspace restored, captured UUID present, but PTY hasn't run claude --resume yet. S3 (restore offer) is the correct state, not S2. The state machine differentiates by claudePresence.
R5 · JSONL line-count misleading
JSONL contains non-message entries (queue-operation, last-prompt, attachment). Naive line count overestimates. Mitigation: count only type:'user' lines (D12 option 1).
R6 · encoded-cwd convention drift
Claude's path-encoding (/ → -) could change. session-tracker derives encoded-cwd from the tab's actual cwd, not a hardcoded path. Already handled in the cherry-pick base.
R7 · Auto-rename UX feels intrusive
If Duo auto-injects /rename for every unnamed session, the 2-line transcript footprint (the /rename line + Claude's ack) accumulates and could feel noisy. Mitigations: (a) D2 threshold msg ≥ 3 means short throwaway sessions never get auto-named; (b) the transcript lines scroll away as work continues; (c) per D9 there is no persistent AUTO badge cluttering the banner; (d) duo session auto-hydrate off CLI verb lets power users opt out.
R8 · Race — Haiku writes while Duo hydrates
Claude's Haiku writes summary at the same moment Duo writes customTitle via /rename. Both fields end up populated; customTitle wins in the read ladder. But if Haiku writes AFTER our /rename, could Claude overwrite our customTitle? Step 0 verification must cover this race.

15 · Acceptance criteria

  • S0: tab with no Claude session and no JSONL history shows no header.
  • S1: fresh Claude session in a CWD with ≥1 prior JSONL shows resume pills (variant per D10).
  • S1 auto-dismiss: pills disappear within 200ms of the first Return committed to the new session.
  • S1 explicit dismiss: clicking × hides pills for this Claude session; same-CWD next session reshows.
  • S2 collapsed: live Claude session shows the tab-marker (D12 glyph). Click expands the banner.
  • S2 expanded: banner shows title from the read ladder (D5). No provenance badge — banner shape is identical regardless of who wrote the title (D9 invariant).
  • S2 rename: clicking the title enters edit mode; Return commits via PTY /rename; Esc reverts; click-outside commits.
  • S3 restore offer: restored tab with captured UUID + no live claude shows Resume button. Click writes claude --resume <uuid>.
  • T1 (idle threshold): unnamed session with messageCount ≥ 3 gets auto-hydrated via D8 ladder + /rename injection.
  • T2 (manual save): ⌘S runs hydration pass for every unnamed live session.
  • T3 (first capture): session-tracker hydrates a session at the moment its UUID is first captured into workspace metadata.
  • Autosave does NOT trigger hydration.
  • D9 invariant — no Duo-side sidecar. ~/.claude/duo/ contains no file that mirrors, annotates, or extends Claude session metadata. find ~/.claude/duo/ -name '*sessions*' -o -name '*hydrated*' returns empty after a full sprint of use.
  • Workspace metadata holds only lastClaudeSession.id per tab — no title cache, no provenance, no messageCount cache. Inspecting a saved .duo-workspace file confirms this.
  • CLI parity: every UI behavior has a working duo session ... verb that round-trips identically.
  • auto-hydrate toggle: duo session auto-hydrate off disables T1/T2/T3; banners still render normally via the read ladder.
