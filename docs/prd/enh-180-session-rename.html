Claude Code already writes a Haiku-generated summary to sessions-index.json automatically once a session has had a few exchanges. Context — what ENH-177 ships today and why this matters

ENH-177 (built + reverted before v0.7.7 cut — queued for re-ship next sprint) captures the most-recently- modified session UUID per terminal tab on every autosave and, after a workspace switch, surfaces a banner: ⏪ This tab had Claude session 17d05c98 — Resume?. ENH-180 depends on ENH-177 landing first.

The UUID is functional but generic. The owner's stated need: "to help users better manage multiple terminal tabs" — i.e., distinguish a tab that was running "Refactor PTY env vars" from one running "Compile design notes". UUIDs don't communicate that.

Decisive insight. The PTY-injection path is free, fast, and writes to the canonical store. The only catch is that /rename requires an active claude TUI — we can rename live sessions but not historical ones. That's actually fine: we set the title while the session is alive, so by the time it closes (and ENH-177's banner needs to display it), the title is already in sessions-index.json.

Proposed mechanism — end-to-end flow

1Detect. On every enrichBeforePersistHook tick (the 250ms autosave debounce that ENH-177 already runs), iterate the live terminal tabs. For each tab with claudePresence === 'claude', look up the session ID. If we've already renamed this session ID (tracked in ~/.claude/duo/renamed-sessions.json) OR sessions-index.json already has a non-empty summary for it, skip.
2Generate title. Read the session JSONL, find first type: user message, extract text content, truncate to a sentence-friendly window. If the candidate fails the quality threshold (Decision 3), skip.
3Idle-gate. Only fire if the PTY has had no user input in the last N seconds AND claudePresence has been steady-state for M seconds (Decision 4 picks the timings). Avoids mid-typing interruption.
4Inject. Write \r/rename <title>\n via PtyManager.write(tabId, ...). Claude processes the slash command, updates sessions-index.json, prints a brief confirmation in the transcript.
5Mark renamed. Add the session ID to ~/.claude/duo/renamed-sessions.json so we don't re-fire on the next tick.
6Banner read priority (extends ENH-177). sessions-index.json entry's summary → our local cache → first-prompt truncation → UUID. The banner gets the rendered title automatically; no banner change needed beyond reading the new tier.

Decisions to lock

Decision 1 — Visibility footprint
Default-on or opt-in?
The PTY inject costs the user two lines in their transcript per session. That's the entire UX trade-off. Default-on means new users get titles automatically (good); they also see slash-command noise they didn't explicitly enable (mixed). Opt-in means zero noise by default but most users will never discover the feature.
A. Opt-in (Settings menu checkbox, default OFF)Recommended for v1
New checkbox in the Settings menu: "Auto-name Claude sessions". Default OFF. Owner walks it, flips on, validates the footprint feels OK. Risk: low — no surprise transcript content. Cost: low discoverability — most users won't find it until we promote it.
B. Default-on with the same Settings checkbox
Same surface, default ON. Every user gets titles automatically. First-time noise is explained by a one-liner under the resume banner: "Duo auto-names your sessions — disable in Settings." Risk: surprise on first install; complaints from users who don't read the disclaimer.
C. Default-on with a one-time FTUX confirmation
On first claude tab spawn, modal: "Duo can auto-name your Claude sessions using /rename. Each rename adds two lines to your transcript. Enable now?" [Yes, default] / [No, ask again next time] / [Off]. Adds one modal to the FTUX surface. Most considerate of the three.

Decision 2 — Title source
Where does the title come from?
All three options write the result via /rename. They differ only in how the title string is generated before the inject. Quality vs. cost vs. latency trade-off.
A. First-prompt truncation (free, instant)Recommended for v1
Read the JSONL, find first type: user message, take the first sentence or ~50 chars. Apply small heuristic cleanups: drop leading "hey claude" / "hi claude" / punctuation. Quality: medium — captures intent when first prompt is meaningful; produces mediocre titles when first prompt is small-talk. Cost: $0. Latency: ~0s.
B. claude -p Haiku summarization
Spawn claude -p --tools "" --disable-slash-commands --model claude-haiku-4-5-20251001 with the first ~10 messages and a tight system prompt. Quality: high — real summary. Cost: $0 for subscription users (quota); ~$0.10 per session for API-key-only users. Latency: ~5s. Stage 1 still uses first-prompt for instant display.
C. Both — first-prompt for v1, Haiku as an opt-in upgrade later
Ship A first. File a follow-up ENH for B that gates Haiku behind a separate localStorage flag (so cost-sensitive users can stay on free titles). Adds zero complexity to v1 build.

Decision 3 — Quality threshold for skipping
When should we not rename a session?
Some first prompts make terrible titles ("hi", "ok", "go on", "what's next"). We need a skip rule so we don't pollute sessions-index.json with garbage. Looser rule = more titles; tighter rule = fewer but better.
A. Liberal — rename anything ≥ 3 words and ≥ 15 chars
Most sessions get titled. "Hello claude how are you" passes ("Hello Claude How Are You"). Owner-rename via /rename overrides ours anyway. Risk: sessions-index.json has some cringe titles.
B. Moderate — rename when ≥ 6 words OR ≥ 40 chars, AND not in a small-talk denylistRecommended
Skip "hi/hello/ok/go on/what's next/keep going/continue/help" and similar (small canonicalized list, ~15 entries). Otherwise rename. Catches the obvious junk while still being permissive enough for real work prompts. Owner can edit the denylist later (or a CLI verb).
C. Strict — require ≥ 8 words AND clear sentence shape (subject + verb)
Light NLP — check for at least one verb-shaped token (heuristic, not full parser). Most short sessions stay unnamed. Higher signal-to-noise on what does get titled.

Decision 4 — Timing / idle gate
When during a session should we fire the inject?
The PTY is shared with the user — if we inject while they're typing or while claude is streaming a long response, the slash command lands in the wrong place. We need an idle gate: wait for both sides to be quiet, then inject.
A. Generous gate — fire when PTY has been idle for ≥ 5s AND claudePresence has been steady-state for ≥ 10s
Conservative timing. Almost never interrupts. Cost: titles can lag many minutes behind session start on a busy session that never goes idle for 5s.
B. Snappy gate — 2s idle AND 3s steadyRecommended
Strikes a balance. Most sessions get a title within the first minute of normal work (user types prompt → claude responds → 3-second gap before next user prompt = inject window). Some collision risk during very rapid back-and-forth.
C. On-session-end — fire only when claudePresence drops from 'claude' to anything else
Never interrupts. Title is set at the very last moment when claude is closing. Risk: if the user closes the terminal hard (⌘W before claude exits cleanly), we miss the inject. Title visibility is deferred — the user doesn't see "Refactor PTY env vars" in their /resume picker until AFTER they end the session.
D. Manual only — never auto-fire; surface a "Rename this session" button in Duo
No auto-fire ever. The Settings checkbox becomes a manual command. New UI element: a small icon in the terminal tab's chrome that runs the rename when clicked. Highest user control, lowest surprise. Probably underused without strong discoverability.

Risks & limitations

Slash-command rejection in non-interactive modes. If a tab is somehow running claude in a mode that doesn't accept slash commands (e.g. behind a script or wrapper), the inject lands as literal text in the user's prompt. Mitigation: only fire when claudePresence === 'claude' (which means the interactive TUI is the foreground), and confirm via sessions-index.json growth that the rename took effect. If not, mark the session as "no auto-rename" and don't retry.
Race with user typing. Mitigated by the idle gate (Decision 4). Adversarial cases (user types furiously, never idle for 2s) will still miss the inject window — that's fine; we'll try again on the next autosave tick.
Claude Code version drift. If a future Claude Code version changes /rename's syntax or removes the slash command entirely, our inject becomes literal text in the transcript. Mitigation: probe Claude version at install time + skip auto-rename for unrecognized versions. Also: every release-walk verifies a fresh claude install renames correctly.
Privacy. The first-prompt-truncation path reads the user's prompt content. The claude -p path sends conversation content through the user's own claude install (same auth path they already use — no new exposure). Both paths only act on sessions the user is currently running; we never touch sessions from other projects or other users.
Deferred decisions / non-blocking notes
  • Per-cwd opt-out (project-level disable). Wait until at least one user asks.
  • Refresh button for already-renamed sessions (re-summarize over the now-larger conversation). Not in v1.
  • Garbage-collect Duo-spawned summary jsonls (only relevant if we pick Decision 2.B or 2.C). File as a follow-up once we see actual clutter.
  • CLI verb for one-shot rename of a specific session UUID. Defer to v2 — covered by Claude's own /rename already.
