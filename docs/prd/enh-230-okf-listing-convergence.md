# ENH-230 — OKF in-vault listing convergence

> Status: building (2026-06-23). Ledger: [tasks.md](../../tasks.md) § ENH-230.
> Extends [ENH-229](enh-229-rollup-maturity.md) (the portable `duo rollup`
> artifact) and ENH-216 D8 (OKF static listings). Owner-requested 2026-06-23.

## Problem

A "rollup" has two mechanisms in Duo, gated by vault format:

- **Obsidian** — a live `.base` evaluated by Duo's engine (`core/vault/engine.ts`
  + `render.ts`), rendered to a stamped artifact via `duo base render` /
  `duo rollup render`.
- **OKF** — static `index.md` / `log.md` regenerated by `duo vault publish`
  (`core/vault/listings.ts`).

ENH-229 matured the **portable artifact** path (`duo rollup` → GitHub-portable
MD/HTML in `rollups/`). But the OKF vault's **in-vault, canonical** listing —
the root `index.md` a reader actually opens — is still produced by a separate,
**less-expressive** generator: `generateIndex` groups by `type` only and emits
flat bullets. The owner's real shape ("tasks grouped by initiative, status
chips, each row linking its note") is only expressible by dropping to the
foreign `.base` path or a portable artifact, never the canonical listing.

### What is and isn't actually divergent (investigation, 2026-06-23)

The asymmetry is **not** in querying:

- `engine.ts` / `render.ts` read `readNotes(root)` → build one graph → evaluate
  a `BaseDef`. Nothing branches on format.
- `parseLinkish` (engine.ts) already folds **both** `[[wikilinks]]` **and** OKF
  `[Display](./note.md)` rel-links into one `Link` value.
- A markdown serializer for engine output already exists: `render-markdown.ts`
  (`renderBaseMarkdown` / `assembleMarkdownPage`).

The divergence is `listings.ts` — a **parallel** generator (`generateIndex` /
`generateLog`) that shares nothing with the engine and is strictly less capable.
The only *intrinsic* difference between the formats is **live-at-rest**
(Obsidian renders `.base` inside its own app) vs **materialized-at-rest** (OKF
must pre-bake plain markdown). Obsidian's `.base` gives Duo a **file
convention**, not rendering infrastructure — Duo wrote `engine.ts` from scratch.
So the "if only the SOR gave us infrastructure" premise is mostly false; the
complexity is Duo's own duplicated output path, and it can be collapsed.

## Goals

- The OKF root `index.md` listing is **query-driven through the one shared
  engine**, so OKF listings are as expressive as Obsidian rollups (grouping,
  filters, chips, entity links).
- **Reduce** complexity by reusing the engine + `render-markdown.ts` rather than
  growing a second DSL inside `listings.ts`.
- **Back-compatible**: existing vaults publish byte-identically until they opt
  in. No forced migration, no splice-contract change.
- Keep vaults **expressive, flexible, non-brittle** — the owner's framing.

## Non-goals (v1)

- Converging `log.md` (date-grouped by file mtime — not a natural frontmatter
  `groupBy`; stays bespoke).
- Deleting `generateIndex` — it remains the **default base** (the no-spec
  fallback), just no longer the only shape.
- A live file-watcher / auto-publish-on-open (rejected: git churn on open;
  materialized listing stays an explicit build artifact). Staleness surfacing is
  a possible follow-up (an editor banner when the open `index.md`'s embedded
  `source-hash` ≠ the live corpus hash), **not** a link baked into the file.
- Per-directory `index.md` expressiveness — per-dir listings stay `generateIndex`.

## Decisions (D-numbered)

- **D1 — one engine, two sinks.** The OKF index sink reuses `evaluateBaseDef`
  (`render.ts`) + `renderBaseMarkdown` (`render-markdown.ts`) — the exact engine
  + serializer the portable artifact and Obsidian paths use. No new query/render
  code; `listings.ts` *calls* the engine instead of reimplementing grouping.

- **D2 — the spec lives in `index.md` frontmatter under `listing:`.** A
  `BaseDef` (`filters` / `formulas` / `views`, same schema as a `.base`). Chosen
  over a body-embedded ` ```base ` block or a `bases/index.base` file because:
  (a) the frontmatter is **already** byte-preserved verbatim by `spliceRootIndex`
  (D4 OKF marker), so the spec survives publish with **zero splice-contract
  change** and zero risk to the frozen-fixture tests; (b) OKF has no `bases/`
  convention; (c) it's in-band and §D9-clean (read live from the file, never a
  sidecar). The body below the `<!-- duo:listing -->` fence stays fully
  regenerated.

- **D3 — no spec → byte-identical default.** Absent `listing:`, `generateIndex`
  runs exactly as today. A golden test asserts byte-equality on the existing
  fixtures so the upgrade is a no-op for every current vault.

- **D4 — warn-and-render, never break publish (D15-consistent).** A malformed
  expression inside a valid `listing:` spec degrades to ⚠ cells (engine never
  throws). A `listing:` that isn't a usable object (or whose YAML can't be read)
  falls back to `generateIndex` so `duo vault publish` always succeeds. This is
  the one new failure mode and it exists only after opt-in.

- **D5 — entity links reuse ENH-229's `LinkCtx`.** Rows link the notes they roll
  up via `buildLinkCtx(files, root, root)` (hrefs relative to the vault root,
  where `index.md` lives) — OKF rel-md `[Title](./notes/x.md)`, GitHub-portable.

- **D6 — stamp carries a regenerate hint.** The generated stamp gains
  `· regenerate: duo vault publish` (the markdown analog of the rollup
  artifact's "regenerate:" stamp). One-time stamp-line rewrite on the next
  publish after upgrade; idempotent thereafter. No clickable refresh link in the
  file (canvas-mode markdown blocks scripts; the `duo://` MD-refresh intercept is
  ENH-229's artifact-only affordance, and a watching Claude is heavier than this
  surface warrants).

## Impact on existing vaults & rollups

- **Obsidian vaults — zero.** `writeListings` still throws in Obsidian mode; the
  engine, `.base` files, and `duo rollup` artifacts are untouched.
- **Existing rendered artifacts (`rollups/`, `out/`) — zero.** `renderTarget` is
  unchanged.
- **Existing OKF vaults — no-op until opt-in.** Detection-safe (frontmatter
  byte-preserved → `okf_version` marker intact). With no `listing:` key, publish
  output is byte-identical (D3 golden test). The new ⚠-in-a-committed-note risk
  (D4) only materializes once a user authors a spec. The D6 stamp hint is a
  one-time, idempotent stamp-line rewrite on next explicit publish.

## Implementation map

- `core/vault/listings.ts` — `writeListings`: read the root `index.md`
  frontmatter; if `listing:` is a usable `BaseDef`, evaluate via the engine and
  serialize through `render-markdown.ts` → splice below the fence; else
  `generateIndex`. Stamp gains the D6 hint. Splice contract unchanged.
- `core/vault/listings.test.ts` — golden byte-identity (no spec), engine-driven
  body (with spec), malformed-spec fallback, Obsidian still throws, idempotence.
- `skill/references/vault.md` + `.claude/rules/vault.md` — document the
  `listing:` frontmatter spec (OKF mode). No new CLI verb/signature (the
  `duo vault publish` flags are unchanged), so the 4-surface verb sync is
  unaffected; `check:skill-currency` stays green.
