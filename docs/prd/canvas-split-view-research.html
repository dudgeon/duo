Slack desktop: workspace switcher · channel sidebar · main conversation · ONE optional aux pane on the right.

The aux pane is a single slot — the right-side workspace. Opening a new aux content type replaces the current one. There's never a second aux. No nesting.

1.2 Aux pane content types

What can fill the aux slot in Slack:

  • Thread replies — clicking a "Reply in thread" link opens the thread in aux. Most common.
  • Channel details — pinned items, files, members, integrations.
  • Search results — search panel slides into aux.
  • Files / Bookmarks lists — channel-scoped artifact browsers.
  • Slack Canvas — Slack's native doc-like artifact (confusingly also called "canvas") opens in aux.
  • Huddle — voice/video chrome docks into aux when active.
  • Workflow Builder — workflow forms.
  • Apps — third-party integrations that present a panel.

1.3 Behavioral rules — the constraints that matter

1. One aux only. No nesting. Opening a new aux replaces the current one. There is never a "second aux pane."
2. Right-side only. The aux is always on the right edge of the conversation column. No top, bottom, or left aux.
3. Single-slot, no aux tab strip. Slack does not have a "tab strip" within the aux. Replacing aux content closes the previous one.
4. Persistent across nav (mostly). An open thread aux stays open as the user clicks between channels in the main pane. Some content types (e.g. channel details) auto-close when the channel changes; threads don't.
5. Resizable horizontally. The divider drags. Aux can also be temporarily expanded to "full screen" (replaces the main pane visually) and back.
6. Visible close affordance. Every aux content type ships with an "✕" button at the top-right of the aux. One click closes; main reclaims the width.

1.4 Why Slack chose these constraints

  • Cognitive ceiling. Two columns of conversation context (main + aux) is the most a user can attend to without losing orientation. A third would compete.
  • Decision reduction. "Where does this thread go?" → always right. No drag-target ambiguity, no remembering which split has what.
  • Single reset gesture. Closing the aux is one click in a known location. No hunting through nested splits.
  • Smaller-screen graceful degradation. The aux collapses to an overlay/modal on narrow viewports. Mobile-friendly.
  • Author-time predictability. Slack apps and integrations know their content goes "in the aux." They don't need to negotiate which split they land in.

Duo today: terminal column on the left, canvas (working pane) on the right. The canvas holds a tab strip; one tab is "active" and fills the pane. No split.

The canvas slot is type-agnostic — it can host any WorkingTab.kind (markdown editor, page, browser, image, pdf). But there's only ever one tab on screen.

The owner has been thinking about splitting this slot. ENH-041 ("Split the canvas (right pane) into side-by-side panels") was filed during the v0.6.3 walks but left as "Filed — no v1 design yet." This research is the v1 design.

3. Design options for Duo

Four options on the table, ordered roughly from simplest to richest.

Option A — Slack-style: one aux pane, single slot, right-onlyv1

Terminal
$ _
Canvas · main
foo.md faq.html +
# foo.md

main content…
aux
preview.html ×

preview content…

Option A: terminal · canvas (with tab strip) · aux (single slot, no aux tab strip). New aux content replaces existing aux content.

Behavior

  • Single aux slot, no aux tab strip. The aux holds one tab at a time. Opening new aux content closes the current one (with optional confirm if the current is dirty).
  • Right-side only. The split divider lives between canvas (main) and aux. No top/bottom/left aux.
  • Open via: right-click on a canvas tab → "Open in aux" / "Move to aux"; or `⌘\` shortcut on the active tab; or `duo split ` CLI.
  • Close via: ✕ button in aux header; or `⌘\` again; or `duo split close`.
  • Promote: drag aux's tab back to main, OR right-click aux tab → "Move to main."
  • Tab kinds in aux: ANY working-pane tab kind (markdown, page, browser, image, pdf). Same set as main.
  • Pin storage: aux's open path is persisted in session-state-service alongside main's tabs.
  • Keyboard focus: ⌘W targets focused pane's active tab. ⌃Tab cycles within focused pane (main has tabs to cycle; aux has only one, so ⌃Tab is no-op there).
  • No nesting. Aux cannot have its own aux. The "Open in aux" affordance is only available in main; aux's tab-context-menu doesn't expose it.
Pros
  • Matches owner's explicit ask.
  • Simplest to implement (one new pane, one divider, one slot).
  • Easy mental model: "main + companion."
  • Reversible: if v2 wants tabs in aux, that's an extension, not a redesign.
  • Honors the cognitive-ceiling argument (no third pane to attend to).
Cons
  • Power users may want multiple companions side-by-side (e.g. preview + comments + diff). Forces close-and-reopen.
  • Aux tab can't be "pinned" semantically the way main tabs can — replacement model fights pin gating.
  • Drag-from-main → aux requires a UX gesture that doesn't exist today.

Option B — Slack-extended: aux pane with its own tab stripv2 candidate

Terminal
$ _
Canvas · main
foo.md +
main content…
aux
preview notes +
aux active tab…

Option B: same shape as A but the aux has its own tab strip. Multiple aux tabs at once.

Behavior delta vs. A

  • Aux gets its own tab strip with the full main-pane verb set (Pin, Trash, Reveal, Copy path, etc.).
  • Adding new aux content adds a tab (doesn't replace).
  • Aux pin set is independent from main pin set.
  • ⌃Tab within aux cycles aux's tabs.
Pros
  • More flexible — aux can hold multiple companions (preview + comments + diff).
  • Familiar gesture (each pane has a tab strip — symmetric).
  • Better fit for long-running aux content (e.g. "always have my scratch.md open in aux").
Cons
  • Doubles tab-strip complexity: two strips, two pin sets, two ⌘W targets.
  • Aux tabs are easy to forget (out-of-sight in a sidebar).
  • Promotes "open everything in aux just because" — defeats the cognitive-ceiling intent.
  • Owner explicitly framed "one aux sidebar" — Option B drifts toward "two main panes," which is closer to Option C.

Option C — VS Code-style: n-way recursive splitexplicitly rejected

Term
$ _
canvas A
tab content
B
…
C
…
aux D
…

Option C (rejected): any pane can split itself, recursively. Quickly produces 3-, 4-, 5-pane layouts. Owner has called this out by name as the thing to avoid.

Pros
  • Maximum flexibility for power users.
  • Familiar to VS Code / IntelliJ / vim users.
Cons
  • Explicitly rejected by owner — "does not allow infinite split view inception."
  • Cognitive overhead grows fast.
  • Drag-target ambiguity is real — every divider is a potential drop site.
  • Layout state to persist gets tree-shaped (vs. flat for A/B).
  • Defeats Duo's "tools you reach for, not tools you configure" ethos.

Option D — Linked twin views (paired tab kinds, no general split)complement

Terminal
$ _
linked · source
# foo.md

The **content** here…
linked · preview

foo.md

The content here…

Option D: instead of a general split, ship specific paired-view tab kinds (markdown source ↔ preview, .json ↔ form, .html ↔ rendered). Each is a single tab that internally splits.

Pros
  • Easy to design and implement per kind.
  • No new "split" verb to learn.
  • Each twin-view tab knows its semantic pairing (no cross-pane state to coordinate).
Cons
  • Limited to predefined view-pairs — can't split arbitrary tabs.
  • Doesn't cover the "tutorial in main, lesson playground in aux" use case.
  • N pair-types = N implementations.
  • Doesn't satisfy the Slack-style ask directly.

Note: Option D is not mutually exclusive with A. A general split (A) plus a markdown-source-↔-preview twin-view tab kind (D) can both ship; they solve different problems.

4. Use cases / capabilities / limitations (Option A)

4.1 Use cases

Workflow Main pane Aux pane
Edit markdown with live preview foo.md (editor) foo.md preview (page kind, regenerated on save)
Take notes on what you're reading a long article (browser tab or page) scratch.md (editor)
Compare two versions v1.md v2.md (or a diff tab kind, if/when D ships)
Lesson + playground lesson skill instructions (page) interactive playground (page kind with action buttons)
Reference doc + working file project tasks.md (editor) ~/.claude/duo/help/faq.html (page)
Comments rail (future ENH-007) canvas with comment threads comments rail (resolved + open lists)

4.2 Capabilities (what Option A enables)

  • Side-by-side reading + writing. The most-asked pattern — a doc on the left, a workspace on the right.
  • Persistent companion. An aux page can stay open while the user cycles through main pane tabs.
  • Type-agnostic aux. Aux can hold any tab kind, not just preview/diff. Browser tabs in aux, images in aux, PDFs in aux — all valid.
  • Agent-driven companion. CLI verbs (`duo split `, `duo split close`) let an agent open / close aux content for the user — useful for FTUX flows ("welcome.html in main, walkthrough in aux").
  • Resizable. Divider drag adjusts main↔aux split. Memory of last drag position (per existing `prevSplitPct` pattern).

4.3 Limitations (deliberate, by design)

  • No nesting. Aux can't have its own aux. (If two-tier nesting matters later, that's a v3 conversation.)
  • No left/top/bottom aux. Right-only. (Top/bottom would compete with the existing tab strip; left would reorder the visual hierarchy.)
  • Single-slot in aux. No aux tab strip in v1. (Option B keeps this on the table for v2.)
  • No drag from terminal column. Aux is a CANVAS-side companion, not a terminal-side one. Terminal stays single-column.
  • Aux replaces, doesn't queue. If the user opens aux content B while A is in aux, A is replaced. (No "stack of recently-aux'd things" — `⌘⇧T` for browser-tab-reopen has different semantics; this isn't that.)

5. Open questions for owner

Decisions needed before code

  1. Open gesture. Right-click → "Open in aux" only? Or also a keyboard shortcut (e.g. `⌘\`)? Or also a CLI verb (`duo split `)? Recommend all three; confirm.
  2. Replacement confirm. If aux is dirty (unsaved markdown / canvas edits) and the user opens new aux content, do we (a) auto-save and replace, (b) prompt with the existing pinned-close confirm pattern, or (c) refuse to replace until the current is closed? Recommend (b) — matches existing destructive-confirm UX.
  3. Aux when no main. If the user closes their last main tab while aux is open, do we (a) promote aux to main, (b) keep aux open with empty main, or (c) close aux too? Recommend (a) — promotion preserves work.
  4. Width persistence. Per-session (resets on restart) or persistent (saved to ~/.claude/duo/session-state.json)? Recommend persistent.
  5. Aux on session-restore. If the user had aux content open on quit, restore it on relaunch? Recommend yes.
  6. Pin behavior. Can an aux tab be pinned? If yes, where does the pin metadata live (shared with main pin set, or aux-specific)? Recommend: NO pinning in v1 (aux is conceptually "transient companion"; pinning fights replacement).
  7. Same path in main + aux. Allow opening the same file in both panes simultaneously, or de-dupe (BUG-059 logic)? Recommend ALLOW for v1 (split-view is the explicit reason). De-dupe rule applies within a single pane.
  8. Default aux content for FTUX. When a fresh user opens Duo, should the welcome canvas auto-split into "welcome.html in main, intro-to-duo lesson in aux" (per Stage 28)? Recommend yes — but only on first launch; user-controlled afterward.

6. Recommendation

Option A — Slack-style, single aux slot, right-only.

It's what the owner asked for verbatim, it has the lowest implementation risk, and it's the most easily extended (Option B adds tabs later if v1 demand surfaces; Option D pairs with it for specific kinds; Option C remains rejected indefinitely).

The cognitive-ceiling argument from Slack's design is also Duo's argument: one terminal column + one canvas pane + one aux pane is three columns of attention, which is at the edge of what most users can hold. A fourth would compete.

7. Implementation sketch (if Option A is locked)

Plumbing checklist (per CLAUDE.md § 4)

  1. shared/types.ts — extend WorkingPaneState with an optional aux: { tab: WorkingTab | null, splitPct: number } | null field. New IPC channels for aux open / close.
  2. electron/preload.ts — expose window.electron.workingPane.openAux(path) + closeAux().
  3. electron/main.ts — IPC handler dispatches to renderer's working-pane logic.
  4. core/socket-server.ts — new case 'split' handling open / close / get sub-verbs.
  5. cli/duo.ts — duo split <path>, duo split close, duo split (gets state). Rebuild binary.
  6. skill/SKILL.md + agents/duo.md — verb cheat-sheet entries; sync via npm run sync:claude.
  7. docs/CLI-COVERAGE.md — inventory.
  8. renderer/components/WorkingPane.tsx — split into WorkingPaneMain (existing) + WorkingPaneAux (new). Divider component between them. Memory of last splitPct.
  9. renderer/components/WorkingTabStrip.tsx — add "Open in aux" to the tab context menu (only visible when in main pane and aux is closed; or "Replace aux" when aux is open).
  10. Session state: extend ~/.claude/duo/session-state.json with aux fields. Migration is additive (missing aux field treated as no aux).
  11. Smoke-walk item every release: open a file, split it to aux, drag the divider, close aux — confirm survives session restart.
